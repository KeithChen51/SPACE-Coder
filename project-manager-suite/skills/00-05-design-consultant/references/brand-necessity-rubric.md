# 品牌与设计系统必要性判断

目标：判断项目应使用通用视觉基线、轻客制化还是完整独特规范。只要已经进入正式前端设计，三种结论都会在项目本地建立同样的视觉系统目录；差别是客制化深度和所需输入。

## 评分表

从 0 分开始加减：

| 条件 | 分数 |
|---|---:|
| 客户、合作伙伴、公众可见 | +3 |
| 销售、招商、演示、品牌传播场景 | +3 |
| 会长期维护，生命周期超过 3 个月 | +2 |
| 页面类型超过 3 类 | +2 |
| 多团队或多人持续协作 | +2 |
| 有 Logo、品牌色、字体、历史视觉资产 | +2 |
| 用户明确希望形成“自己的风格” | +2 |
| 需要和竞品或其他部门产品区分 | +2 |
| 涉及管理层汇报或高价值决策 | +1 |
| 嵌入宿主产品，需要遵守宿主设计语言 | 0 |
| AI/Agent 过程型界面，含审批、工具调用、产物 | +1 |
| 只是内部 CRUD/配置/数据表 | -3 |
| 一次性脚本、临时页面或实验原型 | -3 |
| 用户没有视觉诉求，只要可用 | -1 |
| 交付极短，设计沉淀会阻碍验证 | -1 |

## 结论阈值

| 总分 | 结论 | 行动 |
|---:|---|---|
| ≤2 | default | 在项目本地固化通用视觉基线；负分也归入 default，不留下未定义区间 |
| 3-6 | customize | 固化通用基线并做轻客制化，保留默认组件结构 |
| 7+ | design-system | 完成完整 intake，再固化品牌、token 与组件决策 |

## 输出模板

```markdown
判断：customize

理由：
- 客户可见 +3
- 生命周期超过 3 个月 +2
- 当前只有 2 类页面，暂不需要完整设计系统

建议：
在项目本地视觉系统中使用通用基线，只改主色、密度和圆角。等页面类型超过 3 类或开始多人协作时，再补全品牌 intake 和组件治理，不需要重建目录。
```

## 注意

- 不要为了“显得专业”而强行升级独特品牌设计；本地视觉系统可以直接使用通用基线。
- 不要因为是内部工具就忽略可用性和一致性。
- 如果已有品牌资产，先询问或读取资产，不要重新生成 Logo、品牌图形或主色。
- 如需品牌锁定，必须收集正例和反例；“高级、简洁、现代”不足以定义品牌。

## 覆盖规则

评分只是初筛，以下情况直接覆盖：

- **宿主环境覆盖**：如果产品嵌入 Obsidian、VS Code、浏览器插件或企业平台，优先进入 `host-native` 横向模式。即使分数高，也不能把独立 SaaS 风格直接套进去。
- **高密度后台覆盖**：内部后台即使不需要品牌系统，也必须使用完整组件状态、表格、筛选、分页、错误恢复和移动端策略。
- **Agent UI 覆盖**：包含助手、审批、工具调用、产物、同步冲突时，进入 `agent-process-ui` 横向模式。不要把过程信息做成普通卡片列表。
- **短期公开原型覆盖**：短期公开演示可以 `customize` 或单页预览，不必直接做完整设计系统。
- **资料不足覆盖**：如果缺少品牌资产、页面范围、正例/反例或技术栈，只能输出设计系统草案，不能最终定 token。
