# delivery-planner smoke test

> 日期：2026-03-31
> 方式：轻量人工 smoke test（基于触发词、结构约束、更新路径与反例检查）
> 结论：3 个正向场景通过，1 个负向场景通过；测试中顺手把 skill 从项目样板锚点收敛为纯方法论层。

## 1. 测试范围

本轮不做完整 benchmark，也不跑子 agent 对比；目标是先确认：
- 这个 skill 会不会被正确触发
- 被触发后是否能指向完整执行计划骨架
- 更新计划 / 局部补 Phase 时会不会漏掉联动回写
- 是否容易误触发到 PRD 或日志类任务

## 2. 用例结果

| 用例 | 场景 | 期望 | 结果 | 结论 |
|---|---|---|---|---|
| E1 | 新建完整执行计划 | 命中 skill；输出完整骨架；Task 字段齐全 | `SKILL.md` 的 description 与正文都覆盖“写开发计划 / 写执行计划 / 按 PRD 拆 Phase / Task”；模板已包含 13 个关键章节与 Task 字段 | 通过 |
| E2 | 更新已有计划 | 命中 skill；在原计划回写状态/闸门/验收口径 | `SKILL.md` 已显式区分“更新计划”路径，并要求同步回写状态、日期、依赖、发布闸门、风险与索引 | 通过 |
| E3 | 只补一个 Phase | 命中 skill；补 Phase 的同时更新看板/风险/索引 | `SKILL.md` 与 `quality-gates.md` 都显式要求局部补 Phase 时联动更新看板、风险、闸门和反向索引 | 通过 |
| N1 | 写 PRD / 改 PRD 文档 | 不应由本 skill 接管 | `SKILL.md` 的“非目标”已排除 PRD 写作类任务，降低误触发概率 | 通过 |

## 3. 本轮发现与修正

### 发现 1：之前的 skill 仍被项目样板名称污染

风险：
- 容易让后续使用者误以为这是某个具体计划模板，而不是可迁移的方法论
- 触发描述和引用路径会把模型引向某个项目实例，而不是抽象协议

处理：
- 去掉项目样板名、项目名与项目专属模板命名
- 模板重命名为 `delivery-plan-template.md`
- 将“规则源 / 计划样本 / PRD 导航 / 代码与验证资产”改写为通用类别

## 4. 仍然存在的限制

### 限制 1：本轮是轻量 smoke test，不是完整带基线对比的 eval

当前验证到的是：
- 触发覆盖是否合理
- 模板/引用/更新路径是否完整
- 负向边界是否清晰

还没有验证：
- 与“无 skill”基线相比，计划输出质量提升多少
- 实际多轮迭代下是否会出现章节缺失或完成标准退化
- 时间 / token 成本

## 5. 下一步建议

如果要继续强化这个 skill，下一轮建议做：
1. 按 `evals/evals.json` 跑真实 with-skill / baseline 对比
2. 给每个 eval 补 assertions，例如“是否包含 13 个章节”“是否包含 Task 必填字段”“是否出现抽象完成标准”
3. 把结果沉淀到 `delivery-planner-workspace/iteration-1/`
