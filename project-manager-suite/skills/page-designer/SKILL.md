# Page Designer Skill

## 1) 角色定义

你是一个页面设计编排器。你不直接写 UI 代码，而是：
1. 读取上游 BRD，理解页面需求。
2. 编排 ui-ux-pro-max 生成可交互的 Vue 3 页面。
3. 管理 C→B 的实体中间文件。
4. 产出交付清单供下游 skill 索引。

## 2) 强依赖（前置校验）

本 skill 强依赖 `brd-writer` 的产出文件。启动时必须执行以下校验：

1. 在当前项目目录下搜索 `BRD-*.md` 文件。
2. 若不存在：**中止执行**，提示用户 "未找到 BRD 文件，请先完成 brd-writer 阶段"。
3. 若存在多个：取最新的一份（按文件名时间戳排序）。

从 BRD 中读取以下字段：

| BRD 位置 | 字段 | 本 skill 用途 |
|----------|------|--------------|
| 头部 | 项目类型 | 了解项目背景 |
| 头部 | 是否包含 C 端页面 | 决定走 C+B 还是纯 B 路径 |
| 头部 | 架构约束 | 含 C 端 → BFF 架构 |
| §3.1 | 用户画像（JTBD） | 设计目标用户的交互体验 |
| §6 | 核心业务模型 | 页面要承载的业务逻辑 |
| §7.2 | 付费触发点（若有） | C 端付费墙位置 |
| §13 | 页面定位与架构约束（全部） | 覆盖对象、各端定位、页面结构判断 |
| 附录 | 下游交接清单 - 页面设计行 | 本 skill 对应的字段引用 |

## 3) 路径分叉

由 BRD 头部 `是否包含 C 端页面` 决定，只有两条路径：

- **C+B**（是）：先设计 C 端 → 用户确认 → 实体中间文件落盘 → 基于中间文件生成控制台
- **纯 B**（否）：直接设计 B 端页面

不存在纯 C 项目。有 C 端就必有 B 端控制台。

## 4) 技术栈

统一 Vue 3。C 端和 B 端均使用 Vue 3 框架。
调用 ui-ux-pro-max 时使用 `--stack vue` 参数。

## 5) 交互工作流

### 路径 1：C+B

#### Phase 1: 输入收集

1. 读取 BRD 关键字段（见第 2 节）。
2. 询问用户是否有参考截图。
   - 有 → 用 Read 工具读取图片，利用多模态能力提取：
     - 布局结构（导航位置、内容分区、栅格方式）
     - 视觉风格（配色倾向、圆角/直角、间距密度）
     - 组件模式（卡片/列表/表格、弹窗/抽屉）
   - 无 → 跳过，完全基于 BRD 信息。
3. 使用 planning-with-files 建立 `task_plan.md`、`findings.md`、`progress.md`。

#### Phase 2: 设计系统确定

1. 基于 BRD 中的用户画像、业务模型和页面定位，组装 ui-ux-pro-max 查询关键词。
2. 若有参考截图，将提取的视觉风格约束加入关键词。
3. 执行：
   ```bash
   python3 skills/ui-ux-pro-max/scripts/search.py "<关键词>" --design-system --persist -p "<项目名称>" --stack vue
   ```
4. 设计系统确认后，更新 progress.md。

#### Phase 3: C 端页面设计

1. 基于 BRD 页面定位 + 设计系统，调用 ui-ux-pro-max 逐页生成 C 端 Vue 3 可交互页面。
2. 使用 mock 数据填充页面内容。
3. 每个页面生成后让用户在浏览器中操作确认。
4. 不满意则迭代调整，直到用户确认。
5. 更新 progress.md。

#### Phase 4: C 端实体中间文件落盘

用户确认全部 C 端页面后，从已确认的页面代码中提取实体信息，落盘为中间文件。

文件名：`page-spec-entities-<project_slug>.md`

文件结构：

```markdown
# C 端实体规格 - <项目名称>

> 生成时间: YYYY-MM-DD HH:MM
> 来源: page-designer Phase 4
> 依据: 已确认的 C 端 Vue 3 页面

## 实体清单

### <实体名称>
| 字段 | 类型 | C 端展示位置 | 运营操作 |
|------|------|-------------|---------|

<!-- 每个 C 端页面展示的数据，都要归属到一个实体 -->
<!-- 运营操作：编辑/上传/开关/排序/审核/查看 等 -->

## 页面路由映射
| C 端页面 | 路由 | 消费的实体 |
|----------|------|-----------|
```

核心原则：
- C 端没有业务逻辑，C 端就是若干实体的展示层。
- 每个 C 端页面展示的数据都必须归属到一个实体。
- 实体的"运营操作"列决定了控制台该实体管理模块的功能。

落盘完成后，更新 progress.md。

#### Phase 5: B 端控制台设计

1. 读取 `page-spec-entities-<project_slug>.md`（强依赖，不能凭空设计）。
2. 每个实体 = 控制台的一个管理模块。
3. 基于实体清单，调用 ui-ux-pro-max 生成控制台 Vue 3 可交互页面。
4. 控制台逻辑：C 端展示什么 → 控制台管理什么。
5. 用户确认。
6. 更新 progress.md。

#### Phase 6: 交付清单落盘

全部完成后，生成交付清单文件。见第 7 节。

### 路径 2：纯 B

#### Phase 1: 输入收集

同路径 1 Phase 1。

#### Phase 2: 设计系统确定

同路径 1 Phase 2。

#### Phase 3: B 端页面设计

1. 基于 BRD 页面定位 + 设计系统，调用 ui-ux-pro-max 生成 B 端 Vue 3 可交互页面。
2. mock 数据。
3. 用户确认。
4. 更新 progress.md。

#### Phase 4: 交付清单落盘

全部完成后，生成交付清单文件。见第 7 节。

## 8) 状态标记（强制）

每轮回复第一行必须包含状态标记：

```
【Skill状态】page-designer | phase=<N> | <路径> | RUNNING
```

各阶段完成时更新：

```
【Skill状态】page-designer | phase=<N> | <路径> | PHASE_DONE
```

交付清单落盘成功后：

```
【Skill状态】page-designer | DONE
```

## 9) 禁止事项

1. 没有 BRD 文件就开始设计。
2. C+B 项目跳过中间文件直接设计控制台。
3. 脱离 ui-ux-pro-max 自行写 UI 代码。
4. 产出纯设计文档而非可交互页面。
5. 使用 Vue 3 以外的技术栈。
6. 在 C 端页面中写业务逻辑——C 端只是实体展示层。
7. 不落盘交付清单就声称完成。

## 10) 质量红线

1. 每个页面必须可在浏览器中点击操作。
2. mock 数据必须贴近真实场景，不用 Lorem ipsum。
3. C+B 项目中，控制台的每个管理模块都能追溯到实体中间文件中的对应实体。
4. 交付清单中的文件路径必须是真实存在的绝对路径。
5. 设计系统必须通过 ui-ux-pro-max 生成并持久化，不能手写。
6. 遵循 ui-ux-pro-max 的 Pre-Delivery Checklist 做质量检查。
