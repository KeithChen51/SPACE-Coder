# Requirements Starter

本 skill 是 `project-manager-suite` 的默认需求整理能力。

它负责把用户的业务目标、已有材料和主入口建立的项目上下文，整理成一份可继续推进的基础需求摘要。

它解决的是：

- 业务表达零散
- 第一版范围不清楚
- 需求描述缺少结构
- 后续方案和任务拆解缺少稳定输入

它不负责：

- 高保真产品方案设计
- 详细研发排期
- 具体编码实现
- 高级需求追问策略

## 使用原则

1. 先吸收现有上下文，再补问最少问题。
2. 输出需求摘要，而不是重新发散讨论。
3. 明确区分已知、假设、待确认。
4. 第一版只收敛到可推进范围，不追求一次定义完整产品。
5. 对业务团队使用业务语言，对后续研发输入使用结构化表达。

## 默认输入

优先读取：

- 主入口生成的项目画像
- 用户提供的文档、原型、表格、截图、旧系统说明
- 当前已有计划文件中的相关范围描述

若信息仍不足，再读取：

- `references/requirements-checklist.md`

## 默认工作流

### Step 1：读取已有上下文

优先吸收：

- 项目目标
- 目标用户
- 第一版范围
- 当前优先级
- 已知约束
- 待确认项

如果项目画像已足够支撑需求摘要，不要重复追问用户。

### Step 2：补最少缺口

仅在以下信息缺失时补问：

- 谁是目标用户
- 要解决的核心问题是什么
- 第一版必须包含哪些能力
- 当前已有材料是否能直接复用

不要在本阶段主动深挖：

- 技术架构
- 数据库设计
- 细粒度交互细节
- 完整任务排期

### Step 3：输出需求摘要

使用：

- `assets/requirements-summary-template.md`

输出时必须包含：

- 业务目标
- 目标用户
- 核心问题
- 第一版范围
- 非目标范围
- 输入材料
- 待确认项

### Step 4：判断下一步建议

若需求边界仍明显模糊：

- 返回主入口，继续澄清

若已能描述清楚第一版范围：

- 建议进入 `solution-design` 能力

若用户已经明确要先拆任务：

- 建议进入 `delivery-planning` 能力

## 输出要求

输出给业务团队时：

- 用简洁业务语言描述
- 不使用重研发术语
- 告诉用户“这份需求摘要下一步能做什么”

输出给后续 skill 时：

- 使用结构化标题
- 显式标注 `已知 / 假设 / 待确认`
- 保留原始业务目标，不要全部改写成研发术语

## 资源入口

- 需求补缺检查表：`references/requirements-checklist.md`
- 需求摘要模板：`assets/requirements-summary-template.md`

## V1 边界

本 V1 先解决：

- 从零散业务描述生成第一版需求摘要
- 让后续方案和计划有稳定输入
- 减少业务团队反复解释背景的成本

本 V1 暂不解决：

- 复杂产品策略设计
- 多轮深度需求访谈树
- 行业专用需求模板
