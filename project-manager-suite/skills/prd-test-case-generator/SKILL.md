# PRD 驱动的测试用例生成器

## 核心理念

这些理念是整个 skill 的地基。每条规则都源于实际踩坑经验，理解它们比记住模板更重要。

### 1. PRD 目标态是唯一基准

测试用例验证的是 PRD 说系统"应该是什么样"，不测变更差异（"删除了什么字段""新增了什么"），不测旧态到新态的迁移过程。PRD 说返回 7 个字段，就验证"响应包含这 7 个字段"，而不是"旧版的 24 个字段已经删掉了 17 个"。

### 2. 预期行为来自 PRD，数据链路只解决"往哪写数据"

PRD 告诉你 API"应该返回什么"（预期行为），后端代码告诉你"API 从哪些表读数据"（数据准备）。写 SQL 必须读后端 Service 代码确认：读哪些源表、用什么条件查询、有哪些降级默认值。**但预期结果必须从 PRD 获取**——代码可能有 bug，按代码写预期 = 用 bug 验 bug。**永远往源表构造数据，不要往缓存/预计算表塞数据**——API 可能根本不读那些表。

**Oracle 优先级**（预期值从哪来）：`PRD 验收标准` > `API 契约文档 / Schema` > `代码实现（仅用于数据链路，不用于预期）`。两个源冲突时，以高优先级源为准；PRD 缺失时逐级降级查找，仍无法确定则标 `[待确认-需产品明确]`。

**可配置字段特殊规则**：管理台可配置的展示值（如 statusText、defaultText、icon）不属于上述任何一层——它们的运行时值由管理台配置决定，PRD 和 API 契约只定义字段名和类型，不定义具体内容。对于这类字段，测试验证的是**机制**（API 从 config 表读取并返回），不是某个具体文案字符串。预期写法：引用测试数据准备（如 `与 SEED SQL 中 X 行的 Y 字段一致`），不硬编码具体值。

**计算字段禁写规则（强制）**：先做字段分层，再写 SQL。每个域都要先列 `输入源字段` 与 `服务端计算字段` 两类清单。测试 SQL 只能写输入源字段，禁止写任何服务端计算字段（即使这些字段存在于某张表里，也不作为该接口判定输入）。验证计算逻辑的正确方式是：构造驱动条件（工单/阈值/配置/权益源数据）并断言接口输出，而不是预置输出值。

### 3. 测试颗粒度是业务域

一个聚合 API（如 basic-info）可能汇聚状态计算、徽章、按钮、进度条等多个业务域。按域拆分，每条用例只聚焦一个域的逻辑，只验证该域的字段，SQL 也只构造该域需要的源表数据。这样每条用例的上下文 = 一个域的 PRD 章节 + 对应的后端函数。

### 4. 文件按业务域组织，不按执行方式分割

每个业务域对应一个测试文件。文件内按验证方式分三组：API 验证（curl → 验 JSON）、UI 验证（浏览器 → 验渲染）、管理台配置闭环（管理台改配置 → C 端验证生效）。三组共用同一套 SQL 数据准备。

### 5. 每条用例是完整可执行的闭环

四段式：`数据准备 → 测试执行 → 结果验证 → 数据清理`。"假设数据库里有某条记录"不是测试用例，那是人肉备忘录。

### 6. 用例是因果验证关系，不是功能清单

测试用例必须体现"输入条件 → 操作 → 期望输出"的验证关系。每条用例本质是一个可证伪的命题："在 X 条件下执行 Y 操作，系统应产出 Z 结果"。如果写出来的东西更像功能点列表（"系统支持车辆切换""页面展示徽章"），说明还没完成从需求到用例的转化。

### 7. 管理台配置闭环嵌入域文件

PRD 的管理台配置章节（如 §4.5 StatusConfig）通常紧跟在业务逻辑章节之后。管理台配置闭环测试（改配置 → C 端生效）与该域的 API/UI 验证共用相同的数据环境和 PRD 上下文，因此放在同一个域文件内作为第三组，而不是拆到独立的"跨端联动"文件。

## Phase 1: 需求分析与分类

### 1.1 输入确认

1. **PRD 文档路径** — 一个或多个 PRD 文件
2. **数据链路文件** — 如已有 `dc-*.md` 文件
3. **输出目录** — 测试用例文件的存放位置
4. **编号前缀规则** — 项目使用的编号体系
5. **已有测试用例** — 是否有已完成的文件可作为参考样本

### 1.2 PRD 阅读与验收标准提取

逐份阅读 PRD，重点关注：

- **验收标准章节**（通常在 PRD 末尾的 §验收标准 或 §验收矩阵）
- **管理台配置章节**（如 §X.5，包含可编辑字段、接口定义）
- **异常与兜底章节**（如 §X.4 异常与兜底）
- **数据链路章节**（如 §X.3 数据链路）

**提取产出物**：每份 PRD 生成一个验收点清单，并标注每个验收点涉及的验证方式：

```
PRD: prd-区块2-保养卡片区.md
验收点:
  1. [§14#1] 日常-未到期 → API + UI
  2. [§14#2] 日常-在窗口（天数）→ API + UI
  3. [§14#27] 改状态文案→C端生效 → 管理台+API
  4. [§4.5] 改dueDays阈值→状态变化 → 管理台+API
  ...
```

### 1.3 测试类型分类

| 测试类型 | 验证对象 | 执行方式 | 在文件中的位置 |
|---------|---------|---------|--------------|
| **API 验证** | 业务逻辑计算 | curl | 域文件第一组（编号 01~） |
| **UI 验证** | 前端渲染和交互 | 浏览器 | 域文件第二组（编号 11~） |
| **管理台配置闭环** | 改配置→C端生效 | 管理台+curl | 域文件第三组（编号 21~） |
| **管理台 CRUD** | 配置页面增删改查 | 浏览器 | 独立管理台文件 |
| **缺陷回归** | 已知 bug 修复验证 | 按原缺陷场景 | 独立回归文件 |

### 1.4 方法论匹配

读 [references/methodology.md](references/methodology.md) 获取详细指南。速查：

| 场景特征 | 推荐方法 |
|---------|---------|
| 参数校验、空值、分页 | 等价类 + 边界值 |
| 多条件组合判定（如状态判定） | 决策表 |
| 状态流转、模式切换 | 状态迁移法 |
| 端到端用户操作链路 | 场景法 |
| 历史 bug、已知薄弱点 | 错误推测法 |

## Phase 2: 测试架构设计

### 2.1 文件规划

每个业务域拥有独立子文件夹，域内的 markdown 文件和 sql/ 放在一起。

```
output-dir/
├── 主文档.md                           ← 权威索引
├── client/                             ← C 端用例
│   ├── {domain-a}/                     ← 域文件夹
│   │   ├── {domain-a}.md               ← 索引层（或单文件）
│   │   ├── {domain-a}-用例详情.md      ← 详情层（超 200 行时拆分）
│   │   └── sql/                        ← 本域测试数据 SQL
│   │       ├── {PREFIX}-SEED.sql       ← 种子数据（配置表共用）
│   │       ├── {PREFIX}-{NN}.sql       ← 场景数据（与用例一一对应）
│   │       └── ...
│   ├── {domain-b}/
│   │   ├── {domain-b}.md
│   │   └── sql/
│   │       └── ...
│   └── ...
├── admin/                              ← 管理台用例
│   └── {config-page}.md
└── 缺陷回归集.md
```

**文件拆分原则**：
- 文件按**业务域**组织，与 PRD 模块一一对应，每个域一个子文件夹
- 每个域文件同时包含 API 验证、UI 验证、管理台配置闭环三组
- 单个文件超过约 200 行时，拆为**2 层结构**（见下文 §2.4）
- SQL 文件放在域文件夹内的 `sql/` 子目录，不跨域共享

本项目的具体目录结构和文件名见 [project-conventions.md](references/project-conventions.md) §1。

### 2.2 编号方案

每个文件分配独立编号前缀，文件内按验证方式分号段：

| 号段 | 验证方式 | 说明 |
|------|---------|------|
| **01~09** | API 验证 | curl 调接口验 JSON 字段 |
| **11~19** | UI 验证 | 浏览器验渲染和交互 |
| **21~29** | 管理台配置闭环 | 管理台改配置 → C 端验证生效 |

编号规则：
- 使用两位数字：01, 02, ..., 99
- **号段预留**：从编号就能看出用例属于哪个验证组
- 编号一旦进入报告/缺陷单，不得重排
- 新增用例在对应号段内顺延

每个域文件分配一个独立的编号前缀，在项目权威索引中注册。本项目的编号前缀表见 [project-conventions.md](references/project-conventions.md) §2。

### 2.3 SQL 数据文件分离

测试数据 SQL 不内嵌在 markdown 中，独立为 `.sql` 文件：

| 文件类型 | 命名 | 说明 |
|---------|------|------|
| 种子数据 | `{PREFIX}-SEED.sql` | 配置表初始数据，所有用例共用，只需执行一次 |
| 场景数据 | `{PREFIX}-{NN}.sql` | 与用例编号一一对应，含"数据准备"和"数据清理"两段 |

- SQL 文件放在域文件夹内的 `sql/` 子目录中（如 `client/{domain}/sql/`）
- markdown 中的`数据准备`段写引用（相对于同目录下的 markdown 文件）：`> 执行 [sql/{PREFIX}-{NN}.sql](sql/{PREFIX}-{NN}.sql) 中的"数据准备"段`
- UI 验证用例可复用同域 API 验证的 SQL：`> 复用 [sql/{PREFIX}-{NN}.sql](sql/{PREFIX}-{NN}.sql)`
- 参数校验类用例无需 SQL 文件

**SEED SQL 编写原则**：
- **自包含**：每个 SEED 必须独立可执行，不依赖其他 SEED 先执行过。对共用配置表用 `INSERT ... ON DUPLICATE KEY UPDATE` 而非裸 `UPDATE`——后者在目标行不存在时静默影响 0 行，基线不成立
- **最小破坏半径**：模拟"无数据"场景时，优先用等效非破坏操作（如 `UPDATE isActive=0`）代替 `DELETE FROM 全表`。判断等效性：代码查询条件相同（如 `WHERE isActive=1`），0 行命中 = 空表效果。非破坏操作的清理只需一条 UPDATE 还原，不依赖重跑 SEED
- **数据源聚合**：当多条用例需要同一用户的多种状态叠加（如 API 验共现、UI 验渲染、UI 验滚动），应提取为独立 SQL 文件被这些用例共用。避免"复用 SQL-A + 额外插入 B"的散装模式——它增加执行步骤且容易遗忘清理

本项目的 SQL 文件命名示例见 [project-conventions.md](references/project-conventions.md) §3。

### 2.4 2 层结构（索引 + 详情）

当单个域文件的用例详情超过约 200 行时，拆为两个文件：

**索引层**（`{domain}.md`，约 70~80 行）：
- 文件头元信息 + 用例详情文件链接
- 测试范围表（编号/重点/验证方式/PRD验收#）
- 前置条件（种子数据）
- 用例详情的引用说明
- 验收矩阵
- 版本历史

**详情层**（`{domain}-用例详情.md`）：
- 回链到索引文件
- 全部用例的完整步骤、数据准备、预期结果
- 按三组分节：API 验证 → UI 验证 → 管理台配置闭环

两层之间**双向引用**：
- 索引层头部：`> **用例详情**: [{domain}-用例详情.md]({domain}-用例详情.md)`
- 详情层头部：`> **索引文件**: [{domain}.md]({domain}.md)`

用例数较少（总详情 ≤ 200 行）的域文件不需要拆分，索引和详情合在一个文件中。

本项目的 2 层文件名约定见 [project-conventions.md](references/project-conventions.md) §4。

### 2.5 与权威索引对齐

在规划文件结构前，**必须读取项目的权威索引文件和编号规则文件**。确认：
- 当前域文件的编号前缀与索引一致（如不一致，以实际域文件为准并更新索引）
- 文件名与索引登记的文件名一致
- 不与已有文件的编号前缀冲突

本项目的权威文件路径见 [project-conventions.md](references/project-conventions.md) §5。

### 2.6 与项目编码规范对齐

本 skill 的用例生成规则与 `docs/coding-standards/11-test-case-design.md` 对齐。该文件是项目编码规范体系中关于测试用例设计的权威子文档。skill 中的规则已涵盖该规范的核心要求，无需在生成过程中重复读取。如需确认某条规则的强制等级或项目约定细节，可按需查阅。

### 2.7 与用户确认

在开始生成用例之前，将文件规划、编号方案、覆盖范围呈现给用户确认。

## Phase 3: 逐文件生成用例

这是核心执行阶段。**每次只处理一个域文件**，完成后等用户确认再处理下一个。

### 3.1 文件级流程

```
1. 重读对应 PRD 模块的验收标准章节（刷新上下文）
2. 数据链路研究：读后端 Service 代码或已有的 dc-*.md 文件
   - 读哪些源表？（区分源表 vs 缓存表）
   - 用什么条件查询？
   - 关键计算函数是什么？
   - 有哪些降级/默认值？
   - 产出本域`计算字段禁写清单`（后续 SQL 禁止出现）
3. 从 PRD 验收标准提取全部验收点，分为 API / UI / 管理台三组，并按 BCDE 检查每组是否覆盖边界/正常/规则/异常四条路径——缺口在此时补齐，不要等评审再加
4. 生成文件头部（元信息 + 测试范围表）
5. 生成 API 验证用例（01~）
6. 生成 UI 验证用例（11~）
7. 生成管理台配置闭环用例（21~）— 如 PRD 有管理台配置章节
8. 生成验收矩阵
9. 生成版本历史
10. 判断是否需要 2 层结构（总详情 > 200 行则拆分）
11. 更新项目权威索引：将该域文件状态从"待编写"改为"已完成"，同步编号前缀和文件名（索引文件路径见 project-conventions.md §5）
```

### 3.2 单条用例生成规则

每条用例必须回答 5 个问题：
1. **测什么** → 标题 + 目标
2. **需要什么数据环境** → 前提条件（人类可读的状态描述）
3. **怎么造出这个环境** → 数据准备（可执行的 SQL 引用 / 管理台操作）
4. **怎么测** → 步骤
5. **结果算通过还是失败** → 预期结果（表格化，具体到字段值/颜色/数值/可追溯引用）

**关键规则**：

1. **目标态原则** — 只验证 PRD 描述的目标态，不测变更差异
2. **单一验证点** — 一条用例只验一个逻辑点
3. **可判定预期** — 预期必须能直接判定 PASS/FAIL，禁止"看起来正常""基本符合"
4. **可复现前提** — 前提条件足够明确，任何人都能照着复现
5. **数据准备可执行** — 每条用例的`数据准备`和`数据清理`都是必填段
6. **PRD 回链** — 每条用例标注 `PRD：文档名 §章节`
7. **AIR 原则** — Automatic（优先可自动执行）、Independent（不依赖前一条）、Repeatable（可重复）
8. **PRD 不完备时升级** — 当 PRD 不足以给出唯一预期值时（如"返回 200 或 400"），先查 API 契约文档或后端代码确认实际行为；仍无法确定则在预期列标注 `[待确认-需产品明确]`，禁止写"A 或 B"式模糊预期
9. **BCDE 覆盖** — 每个验证组（API/UI/管理台闭环）的用例集必须覆盖 Border（边界值）、Correct（正常路径）、Design（PRD 规则对应）、Error（异常兜底）四个维度。生成用例时主动按 BCDE 检查缺口，不要等评审阶段才发现
10. **组合覆盖** — 当一个域有多个互相独立的判定条件（如多种徽章各有各的触发规则），单因子用例只验证"每个条件是否独立工作"，还需要至少一条组合用例验证"多个条件同时满足时的输出完整性和顺序"。组合用例的数据天然适合作为 UI 验证和交互验证的共用数据源
11. **计算字段禁写门** — 写 SQL 后必须自查：是否写入了由服务端计算的结果字段。发现即回退，改为构造计算输入。常见禁写示例：`vehicle_cache.daily_status`、`vehicle_sync.status`（当接口 status 来自实时计算链路时）。

### 3.3 按测试类型加载模板

根据当前生成的文件类型，读取对应参考文件：

| 测试类型 | 参考文件 | 何时读取 |
|---------|---------|---------|
| C 端业务域 | [references/type-domain.md](references/type-domain.md) | 生成 tc-区块N-xxx.md 时 |
| 管理台 CRUD | [references/type-config.md](references/type-config.md) | 生成管理台测试文件时 |
| 缺陷回归 | [references/type-regression.md](references/type-regression.md) | 生成回归测试文件时 |

**每次只读当前要生成的文件类型对应的参考文件**，不要一次性加载所有类型。

### 3.4 管理台配置闭环用例的特殊模式

管理台配置闭环用例遵循"基线验证 → 改配置 → 再验证"三步模式：

```
1. 先验基线：curl 确认当前 API 返回值
2. 管理台操作：改配置 + 保存
3. 再验变化：curl 确认 API 返回新值
```

数据清理必须将配置还原到原始值。

## Phase 4: 测试数据反向归堆与样本稳定化

全部域文件完成后，遍历所有用例的数据需求，合并为最小样本字典。详见 [references/templates-shared.md](references/templates-shared.md) §6。

**样本稳定化原则**：对关键业务状态的样本，应建立长期稳定的数据字典。后续执行测试时优先复用这些固定样本，而不是每次临时拼装数据。稳定样本是测试资产，避免的成本是"每轮回归都重新造数据"。本项目的关键样本类型见 [project-conventions.md](references/project-conventions.md) §6。

## Phase 5: 评审与验收

### 5.1 自检清单

对每个生成的文件执行自检。读 [references/checklist.md](references/checklist.md) 获取完整清单。

### 5.2 覆盖率验证

将 PRD 验收标准逐条对照验收矩阵，确认每条验收标准至少被一条用例覆盖。

### 5.3 缺陷回归与最小回归集

如果项目有已知缺陷记录，从已修复的缺陷中沉淀**最小回归集**：每个已知缺陷至少绑定一条回归用例（可复用已有用例编号，也可新增到 `tc-缺陷回归集.md`）。最小回归集的价值是在每次版本更新时快速跑一遍，确认历史 bug 没有复发。

## Phase 6: PRD-TC 交叉核查

Phase 5 是"自查"，Phase 6 是"独立核查"——用全新视角逐条比对 PRD 原文与 TC 写法，发现生成阶段的盲区。

**为什么需要独立核查**：Phase 3 生成用例时，AI 对 PRD 的理解已固化为用例断言；Phase 5 自检也是在同一上下文内审视。Phase 6 的核心价值是**切换上下文**：不从"用例写了什么"出发，而从"PRD 说了什么"出发，逐条反查用例是否准确反映了 PRD 语义。这个过程会暴露三类问题：
1. **TC 错误**：用例断言了 PRD 中不存在的逻辑（如引用不存在的字段、自创回退路径）
2. **PRD 口径冲突**：PRD 正文与验收矩阵矛盾，或不同章节对同一规则描述不一致
3. **TC 遗漏**：PRD 验收点未被任何用例覆盖

**何时执行 Phase 6**：当项目的全部域文件已完成 Phase 5 评审后，即可进入 Phase 6。如果项目只有 1-2 个简单域且 PRD 结构清晰、无验收矩阵，可以将 Phase 6 简化为快速抽查（只做 6.1 的断言比对，跳过完整的问题记录流程）。但对于多域项目、PRD 有验收矩阵、或业务逻辑复杂的场景，完整 Phase 6 不可省略。

详细核查方法论见 [references/phase-verification.md](references/phase-verification.md)。

### 6.1 逐域交叉比对

**每次只核查一个域**，完成后处理下一个。

对每个域执行以下步骤：

```
1. 重新读取该域对应的 PRD 章节（刷新上下文，不复用生成阶段的记忆）
2. 逐条读取 TC 的预期结果，与 PRD 原文逐句比对
   - TC 断言的字段/值/条件/逻辑，PRD 是否有明确支撑？
   - TC 使用的术语与 PRD 是否一致？（如"固定颜色"vs"默认颜色"）
   - TC 引用的 PRD 章节号是否正确？内容是否匹配？
3. 检查 PRD 验收矩阵 vs PRD 正文是否一致
   - 验收矩阵的描述是否与正文规则吻合？
   - 有无验收矩阵自创了正文没有的限制？（如"最多5个"）
4. 检查验收覆盖完整性
   - PRD 验收矩阵的每条是否至少被一条 TC 覆盖？
   - 覆盖方式（API/UI/管理台）是否与场景性质匹配？
```

### 6.2 问题分类与记录

发现的问题按以下 3 类记录：

| 类型 | 定义 | 示例 | 处理方式 |
|------|------|------|---------|
| **TC 错误** | TC 断言了 PRD 中不存在的逻辑 | TC 引用 sortOrder 字段，但 PRD 未定义；TC 描述"双层查询回退"，但 PRD 只有单数据源 | 修正 TC，必要时修正 PRD |
| **PRD 口径冲突** | PRD 内部不同位置的描述相互矛盾 | 正文写"位置为 null"，验收矩阵写"位置为服务门店"；§9.2 写"返回空数组"，§9.4 写"回退通用利益点" | 提交产品裁定 |
| **TC 遗漏** | PRD 验收点无 TC 覆盖 | 验收矩阵 #15 无任何用例映射 | 补充用例 |

**记录格式**——生成 `待裁定问题清单.md`：

```markdown
## TC-ERR-XX：[简述]

**TC 写法**（文件名 第 N 行）：
> [TC 中的具体文字]

**PRD 原文**（文件名 §章节）：
> [PRD 中的具体文字]

**问题本质**：[分析两者差异的根本原因]

**裁定**：
- [ ] 选项 A
- [ ] 选项 B
- [ ] 其他：___
```

### 6.3 产品裁定与修复闭环

将问题清单提交产品（或用户），逐条获取裁定结论。

**裁定后的修复流程**：

1. **TC 错误 → 修正 TC**：
   - 修改用例详情文件中的断言/标题/PRD引用
   - 同步更新索引层测试范围表
   - 同步更新验收矩阵中对应行
   - 如涉及 SQL 修改，同步更新 SQL 文件
   - 更新版本历史

2. **PRD 口径冲突 → 按产品裁定修正 PRD**：
   - 修改 PRD 正文或验收矩阵
   - 更新 PRD 文件头 `@meta baseline` 版本号
   - 更新 `prd-changelog.md` 追加变更条目
   - 更新 `prd-baseline.md` 版本号和基线历史
   - TC 侧如需同步调整则一并修改
   - 更新 tc-主文档的 PRD 基线引用

3. **TC 遗漏 → 补充用例**：
   - 在对应域文件的合适号段新增用例
   - 更新索引层测试范围表和验收矩阵
   - 补充 SQL 数据准备文件
   - 更新 tc-主文档的用例统计

### 6.4 核查完成标准

- [ ] 每个域都完成了逐条 PRD-TC 比对
- [ ] 所有发现的问题已分类记录到待裁定问题清单
- [ ] 所有问题已获得产品裁定
- [ ] 所有裁定结论已执行修复（TC 修正 / PRD 版本升级 / 用例补充）
- [ ] 待裁定问题清单的裁定汇总表已填写完整
- [ ] 权威索引（tc-主文档）的 PRD 基线引用与最新 PRD 版本一致

## 常见陷阱

详见 [references/checklist.md](references/checklist.md) §5 常见陷阱速查表。核心 5 条：

1. **往缓存表塞数据** — 必须查后端实现确认数据链路，往源表构造数据
2. **用代码行为定义预期** — 预期必须从 PRD 获取，代码可能有 bug
3. **漏掉管理台配置闭环** — PRD 有管理台配置章节时，域文件必须包含第三组用例
4. **SEED 隐式依赖执行顺序** — 每个 SEED 必须自包含，对共用配置表用 upsert 而非裸 UPDATE
5. **全局破坏性测试操作** — 用等效非破坏操作（如 `UPDATE isActive=0`）替代 `DELETE FROM 全表`
