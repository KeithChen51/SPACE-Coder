# Phase 6: PRD-TC 交叉核查方法论

## 1. 核查定位

Phase 5（评审与验收）验证的是"用例本身写得对不对"——结构完整、编号正确、预期可判定。

Phase 6（交叉核查）验证的是**"用例与 PRD 是否语义一致"**——用例断言的每个字段、值、条件、逻辑，在 PRD 原文中是否有明确支撑，且没有曲解或自创。

**核心原则**：以 PRD 原文为真理源，逐条反查 TC。不是从 TC 出发看"写得合不合理"，而是从 PRD 出发看"TC 有没有准确反映"。

---

## 2. 核查范围

### 2.1 必查项（每个域都要做）

| 核查维度 | 核查内容 | 发现问题类型 |
|---------|---------|------------|
| **断言准确性** | TC 预期结果中的每个断言是否有 PRD 原文支撑 | TC 错误 |
| **字段存在性** | TC 引用的字段名是否在 PRD API 定义中存在 | TC 错误 |
| **逻辑一致性** | TC 描述的业务逻辑（回退、优先级、条件）是否与 PRD 一致 | TC 错误 / PRD 冲突 |
| **PRD 内部一致性** | PRD 正文 vs 验收矩阵 vs 数据链路章节是否一致 | PRD 口径冲突 |
| **覆盖完整性** | PRD 验收矩阵的每条是否被 TC 覆盖 | TC 遗漏 |

### 2.2 选查项（视复杂度按需）

| 核查维度 | 核查内容 | 适用场景 |
|---------|---------|---------|
| **术语一致性** | TC 使用的术语是否与 PRD 术语表一致 | 术语表较复杂的项目 |
| **SQL 数据链路** | SQL 构造的数据是否确实能触发 PRD 描述的场景 | 数据链路复杂的域 |
| **跨域引用** | TC 中引用其他域的断言是否与被引用域的 PRD 一致 | 多域交叉的场景 |

---

## 3. 逐域核查流程

### 3.1 准备阶段

```
1. 列出待核查的域清单（按业务域组织）
2. 确认每个域对应的 PRD 文件和章节
3. 确认每个域对应的 TC 文件（索引层 + 详情层）
```

### 3.2 单域核查步骤

**每次只核查一个域**。对每个域按以下步骤执行：

#### Step 1: 重读 PRD 原文

重新读取该域对应的 PRD 章节。关键是**刷新上下文**，不能复用 Phase 3 生成阶段的理解——当时可能已形成了固化认知。

重点关注：
- 验收标准章节（通常在 §14 或 §验收矩阵）
- 业务规则正文（条件判定、字段映射、降级逻辑）
- 异常兜底章节
- 管理台配置章节

#### Step 2: 逐条比对 TC 断言

逐条读取 TC 的预期结果表格，对每个断言问：

| 核查问题 | 期望答案 | 不通过的处理 |
|---------|---------|------------|
| 这个字段在 PRD 的 API 响应定义中存在吗？ | 是 | 标记为 TC 错误（引用不存在的字段） |
| 这个值/条件在 PRD 正文中有明确描述吗？ | 是 | 标记为 TC 错误（自创逻辑） |
| TC 的逻辑表述与 PRD 原文语义一致吗？ | 是 | 标记为 TC 错误（曲解 PRD） |
| TC 引用的 PRD 章节号正确吗？内容匹配吗？ | 是 | 标记为 TC 错误（章节引用错误） |

**常见 TC 错误模式**（来自实践经验）：

1. **引用不存在的字段**：TC 断言了 PRD 未定义的响应字段（如 `sortOrder`），可能来自后端实现但 PRD 未暴露
2. **自创回退路径**：TC 描述了"先查 A 再回退查 B"的逻辑，但 PRD 只定义了单数据源
3. **混淆独立概念**：如将"门店信息"（store_name）和"位置信息"（startLocation/endLocation）混为一谈
4. **从 mock 数据推断限制**：如从 mock 数据中的 5 个节点推断"最多 5 个"
5. **用"固定"描述"默认"**：PRD 写"固定颜色"，实际上是数据库可配字段的默认值

#### Step 3: 检查 PRD 内部一致性

PRD 通常有多个位置描述同一规则：
- **正文**：业务规则的详细描述（权威源）
- **验收矩阵**：验收场景的简要描述（容易与正文脱节）
- **数据链路**：字段来源和计算逻辑

逐条对比：
```
PRD 正文描述 ←→ PRD 验收矩阵描述
   ↕                 ↕
 是否一致？        是否一致？
```

**经验规则：PRD 正文 > 验收矩阵**。当两者矛盾时，通常是验收矩阵简述时遗漏了正文的细节或限制条件。但最终需要产品裁定。

**常见 PRD 冲突模式**：

1. **正文 vs 验收矩阵**：正文写"位置为 null，不显示"，验收矩阵写"位置为服务门店"
2. **同文件不同章节**：§9.2 写"直接返回空数组"，§9.4 写"先查通用配置再返回空"
3. **描述 vs 表结构**：正文写"固定颜色"，但数据表 color 字段是可编辑的
4. **公式变量未定义**：公式引用了 `total` 变量，但未说明 total 的取值来源
5. **枚举值不完整**：验收矩阵只列了部分状态值，遗漏了正文定义的其他状态

#### Step 4: 检查覆盖完整性

将 PRD 验收矩阵的每一条与 TC 验收矩阵逐行对照：

```
PRD 验收#1  →  TC 有覆盖？  →  覆盖方式合理？（API/UI/管理台）
PRD 验收#2  →  TC 有覆盖？  →  覆盖方式合理？
...
```

未覆盖的验收点需要分析原因：
- **可通过数据准备复现**：标记为 TC 遗漏，需补充用例
- **前端交互/网络异常**：标记为已知缺口（⚠️），说明原因
- **需要特殊环境**：标记为条件性缺口，说明前提

## 4. 问题记录规范

### 4.1 待裁定问题清单结构

```markdown
# 待裁定问题清单

> **来源**：Phase 6 PRD-TC 交叉核查
> **日期**：YYYY-MM-DD
> **裁定人**：产品（角色名）

---

## 一、TC 错误（N 项，M 项已裁定）

### TC-ERR-01：[简述]

**TC 写法**（文件名 第 N 行）：
> [TC 中的具体文字]

**PRD 原文**（文件名 §章节 第 N 行）：
> [PRD 中的具体文字]

**问题本质**：[分析两者差异的根本原因，1-3 句]

**裁定**：
- [ ] 选项 A：[具体修复方案]
- [ ] 选项 B：[具体修复方案]
- [ ] 其他：___

**处理结果**：[裁定后填写，记录实际执行的修复动作]

---

## 二、PRD 口径冲突（N 项，M 项已裁定）

### PRD-C-01：[简述]

[同上格式]

---

## 三、裁定汇总表

| 编号 | 类型 | 域 | 裁定结果 | 备注 |
|------|------|------|---------|------|
| TC-ERR-01 | TC错误 | CTC-XXX | | |
| PRD-C-01 | PRD冲突 | 域名 | | |
```

### 4.2 问题编号规则

| 类型 | 前缀 | 编号格式 |
|------|------|---------|
| TC 错误 | TC-ERR- | TC-ERR-01, TC-ERR-02, ... |
| PRD 口径冲突 | PRD-C- | PRD-C-01, PRD-C-02, ... |
| TC 遗漏 | TC-GAP- | TC-GAP-01, TC-GAP-02, ... |

### 4.3 记录要求

1. **必须引用原文**：不能只写"TC 和 PRD 不一致"，必须贴出 TC 写法和 PRD 原文的具体文字
2. **必须标注行号**：方便定位和核实
3. **必须分析本质**：不是简单罗列差异，要分析差异的根本原因（如"可能来自 mock 数据""可能来自后端实现"）
4. **必须给出裁定选项**：每个问题至少提供 2 个明确的修复方案选项

## 5. 裁定后修复流程

### 5.1 TC 错误修复

修改范围（按需）：
1. TC 详情文件：修正断言/标题/PRD引用
2. TC 索引文件：同步更新测试范围表中的"测试重点"描述
3. TC 验收矩阵：同步更新覆盖状态/说明
4. SQL 文件：如断言变化导致数据准备需要调整
5. TC 版本历史：追加变更记录

### 5.2 PRD 口径冲突修复

按产品裁定修正 PRD，需完成 4 步版本管理：

```
1. 修改 PRD 文档内容（正文或验收矩阵）
2. 更新文件首行 @meta 中的 baseline 版本号
3. 在 prd-changelog.md 顶部追加变更条目
4. 更新 prd-baseline.md 的"当前基线"和"基线历史"
```

PRD 修正后，如 TC 侧需同步调整：
- 修改 TC 文件
- 更新 tc-主文档的 PRD 基线引用

### 5.3 TC 遗漏补充

1. 在对应域文件的合适号段新增用例
2. 编写 SQL 数据准备文件
3. 更新索引层测试范围表
4. 更新验收矩阵
5. 更新 tc-主文档的用例统计

---

## 6. 核查产出物

Phase 6 完成后应产出：

| 产出物 | 说明 |
|--------|------|
| 待裁定问题清单 | 所有发现的问题、分析、裁定选项和结论 |
| 修正后的 TC 文件 | 按裁定结论修改的用例文件 |
| 修正后的 PRD 文件（如有） | 按裁定结论修改的 PRD + 版本升级 |
| 更新后的权威索引 | tc-主文档的 PRD 基线引用和用例统计 |

## 7. 实践经验

以下经验从多个项目的 Phase 6 核查中沉淀而来，具有通用适用性：

### 7.1 高频问题类型

1. **PRD 验收矩阵 vs 正文脱节**：验收矩阵通常是 PRD 最后编写的部分，容易与正文规则不同步。典型表现：正文说"原样透传"，验收矩阵写"最多 N 个"
2. **TC 引用后端实现而非 PRD**：生成 TC 时如果做了数据链路研究，容易不自觉地把后端字段写入断言，但 PRD 可能未在 API 响应中暴露该字段
3. **概念混淆**：不同业务概念被混为一谈（如将"门店信息"和"位置信息"视为同一概念，实际上是两个独立数据源）
4. **"默认值"被误解为"固定值"**：PRD 写"固定 X"，但该字段实际走数据库配置，所谓"固定"只是初始默认值的不严谨表述

### 7.2 核查效率建议

- **批量发现，逐条裁定**：先完成所有域的核查，生成完整的待裁定问题清单，再逐条提交产品裁定。避免核查一个域就暂停等裁定
- **分类处理**：TC 错误通常可以直接修复（不需要产品裁定）；PRD 口径冲突必须等产品裁定
- **关联问题合并**：如果一个 PRD 修正同时解决了多个问题（如一处正文修正同时解决了 TC 错误和 PRD 冲突），应合并处理以减少版本变更次数

### 7.3 PRD 正文优先原则

当 PRD 正文与验收矩阵矛盾时：
- **默认以正文为准**：正文是详细的业务规则描述，验收矩阵是简要验收条件
- **但必须经产品确认**：不能自行判断，必须提交产品裁定
- 裁定后无论结果如何，都需要修正 PRD 使正文和验收矩阵一致
