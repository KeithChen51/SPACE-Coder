# C 端业务域测试 — 生成策略 + 模板 + 示例

> 每个业务域对应一个测试文件，文件内按验证方式分三组。

## 核心思想

每个业务域（如"状态判定""徽章计算"）对应一个测试文件。文件内按验证方式分三组：

- **API 验证组**（编号 01~09）：curl 调接口 → 验 JSON 字段（测业务计算逻辑）
- **UI 验证组**（编号 11~19）：浏览器打开页面 → 验渲染和交互（测前端展示逻辑）
- **管理台配置闭环组**（编号 21~29）：管理台改配置 → C 端 API 验证生效（测配置生效链路）

三组共用同一套 SQL 数据准备。API 验证是重头戏（需理解后端实现的计算逻辑），UI 验证相对轻量（只看渲染是否正确），管理台闭环测 PRD 管理台配置章节中每个可编辑字段的端到端生效。

**编号号段**：从编号就能一眼看出用例属于哪个验证组。号段之间的空位为后续新增预留。

## 数据链路研究（必做前置步骤）

在编写任何 SQL 之前，必须读后端 Service 代码或已有的 `dc-*.md` 数据链路文件确认该域的数据链路：

1. **找到 Controller → Service 实现**（如 `BasicInfoController` → `BasicInfoServiceImpl`）
2. **列出读取的所有表**（区分源表 vs 缓存表，只往源表构造数据）
3. **识别关键计算函数**（如 `resolveStatus()`、`buildBadges()`）
4. **记录降级/默认值逻辑**（如 config 缺失时的 fallback 颜色）
5. **产出本域禁写字段清单**（服务端计算字段、缓存快照字段、同步结果字段）

将研究结果记录到 `dc-*.md` 中。这一步产出的"源表 → 计算 → 输出"映射是编写正确 SQL 的唯一依据。写 SQL 前必须先过一遍禁写字段清单，确保没有把计算结果字段当输入构造。

```markdown
### {PREFIX}-{NN}：{用例标题}

> PRD：`{文档名}` §{章节号}
> 目标：验证{业务条件下的计算结果}
> 执行方式：curl

**数据准备**：
> 执行 [sql/{PREFIX}-{NN}.sql](sql/{PREFIX}-{NN}.sql) 中的"数据准备"段

**步骤**：
1. `curl "{完整URL}"`
2. 解析响应 JSON

**预期结果**：

| 检查项 | 预期 |
|:---|:---|
| HTTP 状态码 | {200 / 400 / ...} |
| code | {0 / 非0} |
| data.{字段} | {具体值或类型约束} |

**数据清理**：
> 执行 [sql/{PREFIX}-{NN}.sql](sql/{PREFIX}-{NN}.sql) 中的"数据清理"段
```

**特殊情况**：
- 参数校验类用例通常不需要数据准备
- 空结果类用例的数据准备是确保目标数据不存在

## 管理台配置闭环用例模板

管理台配置闭环用例遵循**"基线验证 → 改配置 → 再验证"**三步模式：

```markdown
### {PREFIX}-{NN}：改 {配置项} → C 端 {字段} 生效

> PRD：`{文档名}` §{管理台配置章节}
> 目标：验证管理台修改 {配置表}.{字段} 后，C 端 API 返回新值
> 执行方式：管理台操作 + curl

**数据准备**：
> 复用 [sql/{PREFIX}-{对应API用例编号}.sql](sql/{PREFIX}-{对应API用例编号}.sql)

**步骤**：
1. 记录当前 {配置项} 原始值（备用于还原）
2. 先验证基线：`curl "{API URL}"` → 确认 {字段}={原始值}
3. 管理台打开 `{配置页面}` 页面（{路径}）
4. 将 {配置项} 从 {原始值} 改为 **{新值}**
5. 点击保存
6. 再次 `curl "{API URL}"`
7. 解析响应 JSON

**预期结果**：

| 检查项 | 预期 |
|:---|:---|
| 管理台保存 | 成功（{API} 返回 200） |
| 步骤 2 基线 | {字段}=`"{原始值}"` |
| data.{字段} | `"{新值}"`（已更新） |
| 其他字段 | 不变（本用例只改 {配置项}） |

**数据清理**：
> 1. 管理台将 {配置项} 还原为 {原始值}
> 2. 执行 {对应SQL} 中的"数据清理"段
```

**何时需要管理台闭环用例**：检查 PRD 的管理台配置章节，每个可编辑字段都应有对应的闭环测试。例如 §4.5 StatusConfig 有 `defaultText`、`color`、`dueDays`、`dueMileage` 四个可编辑项 → 4 条管理台闭环用例。

### 示例 — 管理台配置闭环用例（详情层片段）

```markdown
### CTC-STA-24：改 NOT_DUE 状态颜色 → C 端 themeColor 生效

> PRD：`prd-区块2-保养卡片区.md` §4.5（color 字段为下拉：green / gold / red）
> 目标：验证管理台修改 daily_status_config 的 color 后，C 端 API 返回新 themeColor
> 执行方式：管理台操作 + curl

**数据准备**：
> 复用 [sql/CTC-STA-01.sql](sql/CTC-STA-01.sql)（NOT_DUE 状态用户）

**步骤**：
1. 记录当前 NOT_DUE 的 color 原始值（green，备用于还原）
2. 先验证基线：`curl "http://localhost:8080/api/basic-info?phone=13800002001&vin=LVTESTSTA010000001"` → 确认 themeColor=green
3. 管理台打开 `状态参数配置` 页面（/status-config）
4. 将 NOT_DUE 行的 color 从 green 改为 **gold**
5. 点击保存
6. 再次 `curl "http://localhost:8080/api/basic-info?phone=13800002001&vin=LVTESTSTA010000001"`
7. 解析响应 JSON

**预期结果**：

| 检查项 | 预期 |
|:---|:---|
| 管理台保存 | 成功（PUT /api/admin/status-config 返回 200） |
| 步骤 2 基线 | themeColor=`"green"` |
| data.status | `"NOT_DUE"`（状态不变） |
| data.themeColor | `"gold"`（颜色已更新） |
| data.statusText | 不变（本用例只改颜色不改文案） |

**数据清理**：
> 1. 管理台将 NOT_DUE 的 color 还原为 green
> 2. 执行 CTC-STA-01.sql 中的"数据清理"段
```
