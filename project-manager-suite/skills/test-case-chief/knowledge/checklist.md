# 测试用例评审清单

## 1. 单条用例评审（6 项自检）

每条用例提交前必须通过以下检查：

### 1.1 PRD 回链 ✓

- [ ] 用例标注了 PRD 来源（`PRD：文档名 §章节`）
- [ ] PRD 引用的章节号确实存在且内容匹配
- [ ] 如果 PRD 章节变更过，用例已同步更新

**反例**：`PRD：略` 或 `PRD：prd-xxx.md`（没有章节号）

### 1.2 可复现前提 ✓

- [ ] 前提条件足够明确，非作者也能照着复现
- [ ] 测试数据指向明确实体（VIN/phone/配置项等）
- [ ] 如果依赖特定数据库状态，写明了数据来源

**反例**：`前提条件：准备一辆车` — 什么状态的车？什么数据特征？

### 1.2b 数据准备可执行 ✓

- [ ] 包含`数据准备`段，且内容是可直接运行的 SQL 或 API 调用
- [ ] 数据准备的结果能满足"前提条件"中描述的数据状态
- [ ] 包含`数据清理`段，确保测试后环境可还原
- [ ] 数据清理覆盖了数据准备中插入/修改的所有记录
- [ ] 没有假设"数据已存在"而不说明怎么造

**反例**：`前提条件：数据库中存在 phone=13800138000 的 3 条记录` — 怎么造这 3 条记录？用什么 SQL？

### 1.2c 计算字段禁写 ✓

- [ ] 已先完成本域字段分层：`输入源字段` vs `服务端计算字段`
- [ ] SQL 仅写入输入源字段，未写入任何服务端计算字段
- [ ] 没有通过预置结果字段来"伪造正确输出"
- [ ] 若该域存在计算快照字段（如缓存/同步快照），已确认其在本接口链路中不是判定输入

**反例**：接口 `status` 由工单+阈值实时计算，却在 SQL 里写入 `vehicle_sync.status='REPAIRING'` 作为"前提"。

### 1.3 可判定预期 ✓

- [ ] 预期结果可直接判定 PASS/FAIL
- [ ] 具体到字段值、颜色代码、数量、布尔值、或可追溯的数据引用（如 SEED SQL 行引用）中的至少一类
- [ ] 没有使用模糊词汇

**禁止词汇清单**：
- ❌ "看起来正常"
- ❌ "基本符合"
- ❌ "页面正常展示"
- ❌ "数据正确"
- ❌ "应该有值"
- ❌ "符合预期"
- ❌ "A 或 B"式模糊预期（如"200 或 400""null 或空字符串"）— 查 API 契约确认唯一预期，无法确认则标注 `[待确认]`

### 1.4 BCDE 覆盖 ✓

- [ ] 同组用例覆盖了 Border（边界）
- [ ] 同组用例覆盖了 Correct（正常）
- [ ] 同组用例覆盖了 Design（PRD 规则对应）
- [ ] 同组用例覆盖了 Error（异常/兜底）

### 1.5 单一验证点 ✓

- [ ] 一条用例只验证一个逻辑点
- [ ] 没有"多个逻辑点混在一条用例"的问题
- [ ] 如果 PRD 规则影响多状态/多模块，已拆成多条用例

### 1.6 目标态原则 ✓

- [ ] 用例验证的是 PRD 的目标态描述
- [ ] 没有测试变更差异（如"旧字段已删除""新增字段 X"）
- [ ] 没有引用 PRD 的"现状差异"或"变更说明"章节

## 2. 文件级评审（8 项检查）

每个测试文件完成后检查：

### 2.1 结构完整性

- [ ] 文件头包含 `@meta` 标签（docId/status/baseline）
- [ ] 文件头包含基线版本、编号前缀、PRD 引用、设计方法
- [ ] 有测试范围表
- [ ] 有验收矩阵
- [ ] 有版本历史

### 2.2 编号正确性

- [ ] 编号前缀与主文档索引一致
- [ ] 编号按号段组织：01~09 API、11~19 UI、21~29 管理台闭环
- [ ] 各号段内连续无跳号
- [ ] 编号格式统一（两位数字：01, 02, ...）

### 2.3 分组组织

- [ ] 用例按功能模块/接口分组
- [ ] 不同类型的用例没有混写
- [ ] 每组有清晰的标题

### 2.4 分工边界

- [ ] 域文件内 API 验证用例（01~09）只验 JSON 字段值（不验 UI 渲染）
- [ ] 域文件内 UI 验证用例（11~19）只验渲染和交互（不验 API 数据逻辑）
- [ ] 域文件内管理台闭环用例（21~29）遵循"基线验证→改配置→再验证"三步模式
- [ ] 同一条用例没有混合两种验证角度
- [ ] PRD 管理台配置章节中的每个可编辑字段都有对应的闭环用例
- [ ] 管理台闭环用例的数据清理包含"将配置还原为原始值"

### 2.5 PRD 覆盖率

- [ ] PRD 验收标准的每条都有对应用例
- [ ] PRD 异常兜底章节的每条都有对应用例
- [ ] 没有遗漏的验收点

### 2.6 验收矩阵

- [ ] 矩阵覆盖全部 PRD 验收标准（每条验收标准至少一行）
- [ ] 矩阵按业务场景组织（不是按字段平铺）
- [ ] 覆盖正常/边界/异常三条路径
- [ ] 每行的用例编号可追溯

### 2.7 数据声明与数据准备

- [ ] 每条用例的前提条件足够具体
- [ ] 每条用例包含可执行的`数据准备`段（SQL/API 调用）
- [ ] 每条用例包含`数据清理`段
- [ ] 使用样本标识（如"车辆 A"）时，样本在数据字典中有定义
- [ ] 没有硬编码不可变更的具体 ID

### 2.8 方法论匹配

- [ ] 设计方法与场景匹配（不是全部用同一种方法）
- [ ] 文件头标注的设计方法与实际使用一致

---

## 3. 体系级评审（5 项检查）

全部文件完成后做整体检查：

### 3.1 跨文件一致性

- [ ] 不同域文件之间没有重复测试同一逻辑
- [ ] 同一业务域的 API 验证、UI 验证、管理台配置闭环在同一个域文件中（不分散到多个文件）
- [ ] 编号前缀全局唯一（没有两个文件用同一前缀）

### 3.2 主文档更新

- [ ] 主文档索引表中的状态已更新
- [ ] 用例统计表已填写
- [ ] 验收矩阵汇总已更新

### 3.3 测试数据完整性

- [ ] 数据样本字典覆盖了所有用例的数据需求
- [ ] 每个样本标识在至少一条用例中被引用
- [ ] 没有用例引用了不存在的样本

### 3.4 缺陷映射

- [ ] 每个已知缺陷有对应的回归用例
- [ ] 缺陷映射表已更新
- [ ] 回归用例编号可在文档中找到

### 3.5 覆盖率统计

- [ ] 全部 PRD 验收标准的覆盖率已计算
- [ ] 未覆盖的验收点已标注原因
- [ ] 总体覆盖率达到目标（通常 >= 90%）

---

## 4. Phase 6 交叉核查检查项

全部域文件完成 Phase 5 评审后，进入 Phase 6 独立核查。详细方法论见 [phase-verification.md](phase-verification.md)。

### 4.1 逐域比对（每个域都要做）

- [ ] 重新读取了 PRD 原文（刷新上下文，不复用生成阶段记忆）
- [ ] TC 预期结果中的每个断言都有 PRD 原文支撑
- [ ] TC 引用的字段名在 PRD API 响应定义中存在
- [ ] TC 描述的业务逻辑（回退、优先级、条件）与 PRD 一致
- [ ] TC 引用的 PRD 章节号正确且内容匹配
- [ ] PRD 正文与验收矩阵对同一规则的描述一致
- [ ] PRD 验收矩阵的每条至少被一条 TC 覆盖

### 4.2 问题记录

- [ ] 每个发现的问题已分类（TC 错误 / PRD 口径冲突 / TC 遗漏）
- [ ] 每个问题引用了 TC 和 PRD 的原文（不是摘要）
- [ ] 每个问题标注了文件名和行号
- [ ] 每个问题分析了差异根本原因
- [ ] 每个问题提供了至少 2 个裁定选项

### 4.3 裁定与修复闭环

- [ ] 所有问题已提交产品裁定
- [ ] 所有裁定结论已执行修复
- [ ] TC 修正后版本历史已更新

## 5. 常见陷阱速查表

> 这些是实践中验证过的真实问题。生成用例前务必通读一遍。

| # | 陷阱 | 症状 | 修复 |
|---|------|------|------|
| 1 | 测变更差异而非目标态 | 用例标题含"已删除""新增"；验证"旧版的 17 个字段已被删除" | 改为验证目标态："响应只包含 PRD 规定的 7 个字段" |
| 2 | 自上而下预设测试数据 | 先设计数据字典再写用例，覆盖率严重不足 | 先写用例再归堆数据（Phase 4） |
| 3 | API 验证和 UI 验证混在一条用例 | 一条用例里既验 JSON 字段值又验 UI 渲染 | 拆为两条：一条 curl 验 JSON，一条浏览器验渲染。两条可在同文件同域，但不同用例 |
| 4 | 模糊预期 | 预期含"正常""基本""页面正常展示" | 改为可判定值。PRD 固定值直接写（如 `status=NOT_DUE`）；管理台可配置值引用数据准备（如 `与 SEED SQL 中 NOT_DUE 行的 defaultText 一致`）|
| 5 | 从旧文件搬运 | 用例结构和旧文件一模一样，没基于 PRD 重新设计 | 旧文件结构和覆盖范围可能已过时，必须从 PRD 出发重写 |
| 6 | 编号混乱 | 两个文件都用 CTC-01，跨文件引用无法定位 | 每个文件必须有独立前缀 |
| 7 | 数据准备缺失 | 前提写"数据库中存在 X"但无 SQL | 补充可执行的 INSERT/UPDATE + DELETE 清理 |
| 8 | 往缓存/预计算表塞数据 | 直接构造 `vehicle_cache.daily_status='NOT_DUE'` 然后验证 API 返回 NOT_DUE | API 可能不读缓存表。必须查后端实现确认数据链路，往**源表**构造数据让 API 自己算 |
| 9 | 多逻辑混写 | 一条用例有 5+ 个检查项且覆盖不同规则 | 拆分为多条，每条只验一个逻辑点 |
| 10 | 前提模糊 | "准备一辆车"——什么状态？什么数据特征？ | 指定具体数据特征（VIN/状态/数值） |
| 11 | 缺 PRD 回链 | 用例没有标注 PRD 来源 | 补充 `PRD：文档名 §章节` |
| 12 | 缺异常覆盖 | 全部用例都是正常路径 | 补充 Error/Border 用例（BCDE） |
| 13 | 数据清理缺失 | 测试后遗留脏数据影响后续用例 | 补充 DELETE/还原 SQL |
| 14 | 用代码行为定义预期结果 | 按代码逻辑写 expected（如"全程养护阈值 ≥5 年"），但代码本身有 bug | 预期行为**必须从 PRD 获取**。数据链路文档只解决"往哪写数据"，不定义预期 |
| 15 | 漏掉管理台配置闭环 | PRD 有 §X.5 管理台配置章节，但域文件只有 API + UI 两组，没有第三组管理台闭环用例 | 检查 PRD 管理台配置章节，每个可编辑字段都需要一条闭环用例（改配置→C端API验证生效） |
| 16 | 枚举值杜撰 | SQL 中插入了不存在的枚举值（如 order_status="维修中"，实际系统只有"进行中"） | 写 SQL 前查 Schema 确认枚举字段的全部合法值，PRD 引用的枚举值也必须与 Schema 一致 |
| 17 | 单文件过长 | 用例详情超过 200 行，编辑卡顿、上下文爆炸 | 拆为 2 层结构（索引层 + 详情层），双向引用 |
| 18 | 一次性生成所有域 | 试图一次性生成 7 个域的用例，上下文爆炸卡死 | 每次只处理一个域，完成并经用户确认后再处理下一个 |
| 19 | "A 或 B"式模糊预期 | PRD 没明确定义参数缺失时返回 200 还是 400，就写"200 或 400" | 查 API 契约/后端代码确认唯一预期；仍不确定则标注 `[待确认-需产品明确]` |
| 20 | 硬编码管理台可配置值 | 把 SEED SQL 中的展示文案（如 statusText="爱车状态满分，建议定期保养"）直接写进预期结果 | 管理台可配置字段（statusText、defaultText、icon 等）的运行时值由管理台配置决定，不是 PRD 固定值。测试验证的是**机制**（API 读 config → 返回），不是具体文案。预期应引用数据准备：`与 SEED SQL 中 X 行的 Y 字段一致` |
| 21 | SEED 隐式依赖执行顺序 | SEED-A 对共用配置表只有 `UPDATE`，假设 SEED-B 已先跑过并插入了该行；单独跑 SEED-A 时 UPDATE 影响 0 行，基线不成立 | SEED 必须自包含：对共用配置表用 `INSERT ... ON DUPLICATE KEY UPDATE`，无论环境状态都能建立基线 |
| 22 | 全局破坏性测试操作 | 用 `DELETE FROM 配置表` 模拟"无数据"，清理依赖人工重跑 SEED，忘记则后续用例全挂 | 用等效非破坏操作（如 `UPDATE isActive=0`）。判断等效性：代码查询路径相同（`WHERE isActive=1`），0 行命中 = 空表效果。清理只需一条 UPDATE 还原 |
| 23 | 散装数据复用 | "复用 SQL-A + 额外在步骤中插入 B"，执行步骤散落、容易遗忘清理 B | 当多条用例需同一用户的多种状态叠加时，提取为独立 SQL 文件，被这些用例共用 |
| 24 | 预置服务端计算结果字段 | 测试 SQL 写入 `vehicle_sync.status` / `vehicle_cache.daily_status` 等结果字段，并据此断言接口输出 | 先做字段分层。只构造驱动计算的输入源数据（工单/阈值/配置/权益源），禁止预置结果字段 |
| 25 | TC 断言引用 PRD 未定义的字段 | TC 预期中出现 `sortOrder`、`totalSteps` 等字段，但 PRD API 响应定义中无此字段 | Phase 6 逐条比对 TC 断言与 PRD API 字段定义，删除或标注无源断言 |
| 26 | TC 自创回退/降级路径 | TC 描述"先查 A 再回退查 B"，但 PRD 只定义了单数据源查询 | Phase 6 核查 TC 逻辑描述是否有 PRD 原文支撑，无支撑则按 PRD 修正 |
| 27 | PRD 验收矩阵与正文脱节 | 验收矩阵写"最多 5 个"，正文写"原样透传可滚动"；矩阵写"位置为服务门店"，正文写"位置为 null" | Phase 6 逐条对比正文与验收矩阵，冲突时提交产品裁定（通常以正文为准） |
| 28 | 从 mock 数据推断业务限制 | mock 数据有 5 个节点，就在 TC 中写"最多 5 个节点" | 区分 mock 数据样本与业务规则。PRD 正文未声明的限制不应出现在 TC 断言中 |
| 29 | 混淆"默认值"与"固定值" | PRD 写"固定颜色 #999"，TC 断言颜色硬编码为 #999，但该字段实际走数据库配置 | 检查字段是否来自可编辑的配置表。"固定"可能只是默认值的不严谨表述，需产品确认 |
