# 测试用例设计规范

> 适用范围：测试用例文档、验收用例清单、回归用例清单、测试矩阵
> 配套文档：`10-testing.md`（测试代码与自动化规范）、测试计划、PRD、设计文档、缺陷单、测试报告

---

## 1. 目标与边界

1. 【强制】本规范用于约束**测试用例文档**的设计与编写，不替代单元测试代码规范。
2. 【强制】测试用例必须能回答 4 个问题：
   - 测什么
   - 在什么前提下测
   - 怎么测
   - 结果算通过还是失败
3. 【强制】每条用例必须可以回链到具体 PRD 规则、缺陷或测试报告。
4. 【推荐】功能测试文档关注“业务规则与验收闭环”，单元测试文档关注“代码行为与断言闭环”。

---

## 2. 设计原则

### 2.1 基础原则

1. 【强制】遵循 `AIR`：
   - `Automatic`：优先可自动执行
   - `Independent`：每条用例独立，不依赖前一条执行结果
   - `Repeatable`：相同环境下可重复得到相同结果
2. 【强制】遵循 `BCDE`：
   - `Border`：覆盖边界值
   - `Correct`：覆盖正确输入
   - `Design`：与 PRD / 设计文档逐条对应
   - `Error`：覆盖异常与兜底
3. 【强制】测试用例不是功能清单，必须体现“输入条件 -> 操作 -> 期望输出”的验证关系。

### 2.2 设计方法选型

1. 【强制】接口参数、分页、计数、空值校验优先使用**等价类 + 边界值**。
2. 【强制】多条件组合规则优先使用**决策表**。
3. 【强制】状态切换、流程推进、节点流转优先使用**状态迁移法**。
4. 【推荐】用户端到端操作链路使用**场景法**。
5. 【推荐】历史线上问题和已知薄弱点使用**错误推测法**补充回归用例。

### 2.3 常见场景推荐映射

| 场景 | 推荐方法 |
|---|---|
| 表单字段校验 | 等价类 + 边界值 |
| 列表筛选、分页、排序 | 等价类 + 边界值 |
| 多条件组合判定 | 决策表 |
| 状态流转、审批流、任务流 | 状态迁移法 |
| 页面联动、端到端业务流程 | 场景法 |
| 缺陷回归 | 错误推测法 + 最小回归集 |

## 3. 用例文档结构

1. 【强制】每份测试用例文档必须包含以下章节：
   - 文档标题
   - PRD 依据
   - 测试日期或版本
   - 模块分组
   - 逐条测试用例
   - 验收矩阵
2. 【强制】按模块分组组织用例，不得把 API、UI、跨模块用例混写成无序列表。
3. 【推荐】建议按以下层级组织：
   - API 与单元测试
   - 页面 / 模块 UI
   - 跨模块联动
   - 验收矩阵

---

## 4. 用例编号规范

1. 【强制】用例编号必须稳定、唯一、可追踪。
2. 【强制】编号格式应采用固定前缀 + 顺序号，例如：
   - 通用格式：`TC-001`、`TC-002`
   - 按模块分前缀：`USER-TC-001`、`ORDER-TC-001`
   - 按系统分前缀：`WEB-TC-001`、`ADMIN-TC-001`
3. 【强制】同一项目内不得混用多套无规则编号体系。
4. 【强制】编号一旦进入测试报告或缺陷单，不得随意重排；新增用例顺延编号。
5. 【推荐】一个模块内保留连续编号，便于报告和缺陷引用。

---

## 5. 单条用例模板

### 5.1 标准模板

每条用例至少包含以下信息：

- 用例编号与标题
- PRD 依据
- 测试目标
- 前提条件
- 测试数据
- 测试步骤
- 预期结果
- 执行方式

推荐模板：

```md
### TC-XXX：用例标题

> PRD：`xxx.md` §x.x
> 目标：验证……
> 执行方式：curl / 单元测试 / 浏览器 UI / 联调验证

**前提条件**：
- ...

**测试数据**：
- ...

**步骤**：
1. ...
2. ...
3. ...

**预期结果**：
| 检查项 | 预期 |
|:---|:---|
| ... | ... |
```

### 5.2 简化模板

1. 【推荐】对于结构简单、稳定的 API 校验，可使用“命令 + 断言 + 预期”简化模板。
2. 【强制】即便简化，也必须包含：
   - 输入
   - 断言
   - 通过标准

---

## 6. 前提条件与测试数据规范

1. 【强制】每条用例必须写明可执行前提，禁止默认“测试者自己猜”。
2. 【强制】测试数据必须指向明确实体，例如：
   - 指定用户 `id / account`
   - 指定订单 `id / type`
   - 指定配置项 `key / value`
3. 【强制】如果用例依赖特定数据库状态，必须写明数据来源：
   - 初始化脚本
   - mock 数据
   - 手工配置步骤
4. 【推荐】多状态场景优先使用固定测试样本，不建议执行时临时拼装数据。
5. 【推荐】对关键业务样本建立长期稳定的数据字典或测试夹具。

---

## 7. 预期结果规范

1. 【强制】预期结果必须可判定为 `PASS / FAIL`，禁止使用“看起来正常”“基本符合”。
2. 【强制】预期必须具体到字段、文案、按钮、状态、数量、权限中的至少一类。
3. 【强制】涉及业务规则时，预期必须直接写业务结果，不只写“接口成功”。
4. 【推荐】复杂展示场景用“检查项表格”表达，避免段落式模糊描述。

错误示例：

```md
预期：页面正常展示
```

正确示例：

```md
| 检查项 | 预期 |
|:---|:---|
| 页面标题 | `订单详情` |
| 主按钮 | `提交审核` |
| 空态文案 | `暂无数据` |
```

---

## 8. PRD 回链规范

1. 【强制】每条用例必须标注 PRD 来源，格式为 `文档名 + 章节号`。
2. 【强制】一个 PRD 规则如果会影响多个状态或多个模块，必须拆成多条用例，不得只写一条笼统校验。
3. 【推荐】对规则密集区域使用“PRD 章节 -> 用例编号”映射表，便于遗漏检查。
4. 【强制】PRD 变更后，必须检查受影响用例并更新：
   - 前提条件
   - 预期结果
   - 关联缺陷 / 报告引用

---

## 9. 缺陷与回归规范

1. 【强制】每个缺陷至少要补一条回归用例，或绑定到已有用例编号。
2. 【强制】缺陷单中的 `关联 TC` 必须能回指到测试用例文档。
3. 【强制】缺陷修复后，测试报告必须同步更新对应用例状态。
4. 【推荐】对历史高频问题建立“最小回归集”，单独标识。

建议格式：

| 缺陷 | 回归用例 | 说明 |
|---|---|---|
| BUG-003 | TC-024 | 提交后按钮状态回归 |
| BUG-005 | TC-031 | 删除后列表刷新回归 |
| BUG-007 | TC-011 / TC-020 | 状态文案回归 |

---

## 10. 验收矩阵规范

1. 【强制】每份核心 PRD 对应用例文档末尾必须有验收矩阵。
2. 【强制】验收矩阵至少包含：
   - 场景
   - 输入条件
   - 预期输出
   - 对应用例编号
3. 【强制】验收矩阵必须覆盖：
   - 正常路径
   - 边界路径
   - 异常与兜底路径
4. 【推荐】优先用“业务场景”组织矩阵，而不是按接口字段平铺。

推荐模板：

```md
| 场景 | 输入条件 | 预期输出 | 用例编号 |
|---|---|---|---|
| 新建成功 | 字段完整且合法 | 保存成功，列表新增记录 | TC-008, TC-012 |
| 状态超期 | status=OVERDUE | 主按钮显示 `立即处理` | TC-009, TC-011 |
```

---

## 11. 与测试报告、缺陷单的映射关系

1. 【强制】测试报告必须引用同一套用例编号，不得重新发明编号体系。
2. 【强制】缺陷单中的 `关联 TC`、测试报告中的 `TC`、用例文档中的 `TC` 必须一致。
3. 【强制】如果某条用例被拆分或合并，必须同步更新：
   - 测试用例文档
   - 测试报告
   - 缺陷单
4. 【推荐】报告中的状态使用固定集合：`PASS / FAIL / 部分通过 / 未验证`。

---

## 12. 通用落地要求

1. 【强制】核心主流程必须至少覆盖：
   - 正常路径
   - 关键边界路径
   - 失败 / 兜底路径
2. 【强制】核心展示类页面必须覆盖：
   - 主标题 / 关键文案
   - 主按钮 / 关键操作
   - 状态标签 / 徽标
   - 空态 / 错态
   - 列表 / 分页 / 刷新
3. 【强制】跨模块联动场景必须验证上下游联动结果，不得只验单模块。
4. 【推荐】对配置驱动逻辑，至少保留一组“配置变化 -> 展示变化 / 结果变化”的联动用例。

---

## 13. 评审清单

在提交或更新测试用例文档前，至少自检以下问题：

1. 这条用例是否能直接回链到某条 PRD 规则？
2. 前提条件是否足够明确，别人能复现吗？
3. 预期结果是否可以直接判定 `PASS / FAIL`？
4. 是否覆盖了正常、边界、异常至少一种？
5. 是否已经映射到测试报告和缺陷单体系？
6. 是否存在“多个逻辑点混在一条用例里”的问题？

---

## 14. 与 `10-testing.md` 的关系

1. `10-testing.md` 负责“测试代码怎么写、怎么断言、怎么组织”。
2. 本文负责“测试用例怎么设计、怎么编号、怎么回链 PRD、怎么进入报告和缺陷单”。
3. 编写自动化测试代码时，两份文档应同时遵守。
