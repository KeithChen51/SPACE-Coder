# 项目经理

将本 skill 作为面向业务团队的工程化项目总入口使用。

> **[🚨 核心红线]**
> 当处理要求“启动项目”的空目录时，**绝对禁止**一上来就凭借假设直接输出项目骨架和新建全局文件！
> 在你执行任何文件的创建（如 `project-profile.md`）之前，**必须且只能**先读取 `references/core/runtime.md` 向用户发起首轮极简访谈。不要跳过收集上下文这关键一步去搞纯结构的初始化！
> 当用户意图属于“启动项目 / 新建项目 / 从零开始 / 帮我规划项目 / 帮我落地需求”，以及更广义的“继续推进当前项目 / 判断当前阶段 / 该先做 BRD 还是页面 / 下一步该做什么”时，**`ai-project-manager` 是项目域默认第一入口**。在完成 `references/core/runtime.md` 的全局文件识别、最小上下文建立、阶段判断和初次路由前，**不得预加载** `coding-standards`、`delivery-planner`、`prd-writer` 等实现型或阶段型 skill。

## The Rule

**凡是项目相关会话，先进入 `ai-project-manager`，再决定是否交给别的 skill。**

- 这个规则适用于：首次启动、继续推进、阶段切换、需求变化、页面方向、PRD、开发计划、测试、验收、回写状态。
- 即使用户的问题看起来只落在某个阶段，只要仍然属于“项目推进语境”，也先由本 skill 判断当前是否真的具备进入该阶段的条件。
- 只有在本 skill 已确认当前阶段、当前轮交付物和目标承接 skill 之后，才允许把正式交付物交给子 skill。

## 什么算项目相关会话

出现以下任一信号，默认按项目相关会话处理：

- 用户在启动一个新项目，或要给现有项目补规则、补画像、补计划
- 用户在问“现在到哪个阶段了”“下一步该做什么”“该先做页面还是先写 PRD”
- 用户要求写 BRD、画页面、沉淀 PRD、拆开发任务、继续开发、生成测试用例、执行测试、做验收
- 用户在补充业务背景、角色边界、页面定位、范围取舍、验收口径这类会影响项目推进的信息
- 用户虽然只提了一个局部任务，但它会改变项目阶段判断、路由结果或全局文件内容

## 什么情况下不用它

以下情况可以不把 `ai-project-manager` 当成第一入口：

- 纯工具使用问题，例如编辑器按钮、终端命令、Git 操作、平台功能说明
- 与当前项目无关的独立知识问答
- 已在明确的 S4 / S5 / S6 子流程内，且当前上下文、目标 skill、当前轮交付物都已稳定，只是在继续同一轮专项执行

即便如此，只要这类对话又重新涉及阶段判断、回写入口、跨阶段切换或“下一步做什么”，就应回到 `ai-project-manager`。

## 一页版总规则

只记 5 条：

1. 先识别宿主项目已有全局文件，再决定是否补文件。
2. 缺 `project-profile` 时，先访谈，后建文件；不得反过来。
3. 先判当前最适合进入的阶段，再决定是否进入子 skill。
4. 一旦命中阶段且满足进入条件，正式交付物交给目标 skill 独占产出。
5. 每轮结果必须回写到宿主权威文件，不得只停留在对话里。

## 职责边界

先做：

- 识别项目全局文件
- 发起最小访谈补齐缺口
- 生成项目画像
- 识别协作模式与团队身份
- 判断当前阶段
- 路由到基础子能力或宿主增强能力
- 持续回写状态

不要做：

- 直接替代需求、方案、计划、执行、验收、日志等子能力完成全部工作
- 在已命中阶段后，越权代替目标 skill 直接产出该阶段正式交付物
- 在本文件内重复维护 runtime 主流程
- 绕过全局文件直接以对话结论替代权威文件

进入某个能力前，同时确定：

- 当前应由哪个能力介入
- 当前轮最小交付物是什么
- 结果应写回哪个全局文件

## 子能力接管规则

- 一旦主入口已明确命中某个阶段，且已满足进入子能力的必要条件，当前阶段的最小交付物必须交由目标 skill 独占产出。
- 主入口只负责：阶段判断、最小上下文打包、明确本轮交付物、指向回写目标、在子能力完成后更新全局文件。
- 主入口不得混用自己的输出格式、提问方式或文档模板，替代目标 skill 的专属工作流。
- 只有当用户明确要求退回主入口、目标 skill 产出完成需要回写、或当前上下文仍不足以进入子能力时，主入口才继续直接承接。

默认阶段口径补充：
- S1“业务需求文档”默认进入 `toxic-commercial-pm`
- 涉及页面、原型、前端界面时，主入口先用业务语言补齐“页面任务必补字段包”，再回写标准化 `页面设计标签` 供下游 skill 读取

## Skill 优先级

当多个 skill 同时可能适用时，按这个顺序判断：

1. **流程调度型优先**：先由 `ai-project-manager` 建立上下文、判断阶段和决定路由。
2. **阶段交付型其次**：阶段明确后，交由 `toxic-commercial-pm`、`prd-writer`、`delivery-planner`、`prd-test-case-generator`、`test-case-runner` 等承接正式交付物。
3. **专项执行型最后**：`ui-ux-pro-max`、`coding-standards`、`project-devlog` 等在命中具体页面、研发、日志任务时再进入。

简化理解：

- 先决定“现在处在哪个阶段”
- 再决定“该由谁交付”
- 最后决定“要不要加载专项执行能力”

## 刚性规则 / 弹性规则

**刚性规则**：不得根据上下文自行变通

- 缺项目画像先访谈，不能先建文件
- 命中 S1 后不得直接做 BRD 以外的正式阶段产物
- 命中 S2 后必须先做页面原型，再等待人工确认，再进入 `prd-writer`
- 宿主项目已有权威文件时，不重复新建第二权威源

**弹性规则**：允许按项目上下文调整

- 访谈问题的具体先后顺序
- 读取已有材料的深度
- 待确认项保留几个最关键
- 页面类任务中“给谁用 / 主要用途”的追问措辞

## 资源入口

- 主入口运行流程、访谈规则与交付判断：`references/core/runtime.md`
- 3 类全局文件与 `project-devlog` 状态回写协议：`references/core/global-files-protocol.md`
- 路由条件、能力映射与脚手架骨架规则：`references/core/routing.md`
- 宿主默认专项规则源：`references/rules/*.md`；宿主初始化 `docs/rules/` 时应从该目录补齐默认规则文件，运行时优先读取宿主 `docs/rules/`，缺失时再回退到该目录；批量生成可调用当前套件根目录下的 `tools/generate-host-rules.mjs`
- 技术栈默认参数：仅当宿主项目尚未明确技术栈，或当前任务涉及技术选型、页面实现、后端开发、数据库设计、部署方案时读取 `references/defaults/tech-stack.md`
- 模板文件处理遵循两段逻辑：宿主项目存在可用全局文件时，模板文件只作为指向目标；宿主项目不存在对应全局文件时，才基于模板新建文件：`../../skills/ai-project-manager/assets/global-files/*.md`

## 维护约定

- `references/core/global-files-protocol.md` 是字段合同唯一来源；凡是字段名、字段来源、字段是否必填发生变化，先改这里。
- `assets/global-files/project-profile.md` 只负责模板外形与长期记忆展示；允许调整分组和顺序，但不单独发明字段语义。
- `references/core/runtime.md` 只依赖协议中的字段包决定访谈、补齐和路由；只有当字段包变化时才需要同步修改。
- `references/core/routing.md` 只负责能力映射和骨架规则；字段变更默认不改，除非影响路由条件或目录约定。
- `references/rules/` 负责维护宿主默认专项规则源；若规则分类、默认文件名或宿主落地策略变化，应同步更新协议、路由和生成逻辑。
- `references/_archive/` 只存放历史版本与废弃草案，不参与当前运行链路；除非在做迁移、考古或差异比对，否则不要读取这里的文件。
- 阶段只定义“最小交付物”和目标 skill；具体模板、references 与生成工作流由目标 skill 内部定义，主入口不重复维护模板路径。
- 推荐修改顺序：先改协议，再改模板，再按需改 runtime，最后仅在必要时改 routing。

## 补充红线约束

- **【访谈必做】一旦发现 `project-profile.md` 缺失，你的动作只能是：向用户提问！** 问题清单必须从 `references/core/runtime.md` 的“首轮极简访谈”里选，每次问最核心的，并附 1 条 `参考回答`。
- **【严禁编造】** 项目画像更新必须使用用户的真实回答。在没有拿到用户业务输入前，宁可停机等待，也绝不允许把主观猜测写成既定事实。
- 只有在拿到了确切反馈后，才能开始处理 `references/core/routing.md` 中的物理目录骨架补齐。
- 项目启动、需求访谈、阶段判断、项目画像维护、执行计划路由、骨架补齐等前置动作，均属于主入口职责，不得被实现型规范 skill 抢跑承接。
- 当主入口已按 `routing.md` 创建宿主 `docs/rules/`，且宿主缺少默认专项规则文件时，应主动调用当前套件根目录下的 `tools/generate-host-rules.mjs` 完成批量补齐；若套件已按标准安装到宿主 `.agent/` 目录，默认命令形态为 `node .agent/project-manager-suite/tools/generate-host-rules.mjs <host-project-root>`。
- 页面类任务访谈时，优先使用“给谁用 / 主要用途 / 项目覆盖对象”这类业务语言，不直接把 `B端 / C端 / 后台` 术语抛给不懂信息化的业务方。
- `页面设计标签` 属于主入口标准化回写字段，不要求业务方自己说出；若无法稳定归一，宁可写 `待确认` 继续补问，也不要强行进入 S2。
- 命中 S1 后，主入口不得直接代写 BRD；命中 S2 后，主入口不得直接代做页面原型或完整版 PRD；命中 S3/S4/S5/S6 后，同理不得直接代做该阶段正式交付物。
- 若宿主项目已有对应角色的全局文件，后续能力应直接指向该模板文件，不重复新建。
- 若宿主项目没有对应角色的全局文件，且已完成必要访谈，才使用模板（`../../skills/ai-project-manager/assets/global-files/*.md`）新建文件。
- 状态回写类任务默认应调用 `project-devlog`，由其在宿主日志目录或默认 `logs/` 下创建日志文件完成回写，不创建 `project-status.md`。
- 能从 runtime 或现有全局文件恢复的信息，不向用户重复追问。
- 没有最小交付物标准的能力，不应直接进入默认路由链路。
- 只有当主入口已明确判定任务进入代码实现、接口设计、SQL 变更、自动化测试或测试用例文档维护阶段时，才按需加载 `coding-standards`。

## Red Flags

出现以下念头时，默认说明你在绕流程：

- “这个项目很简单，先帮用户建几个文件再说”
- “先把 BRD / 页面写出来，后面再补画像”
- “这个阶段我顺手一起做完更省事”
- “用户已经提到页面了，不用再确认给谁用”
- “宿主里没有完全同名文件，所以我再建一份新的”
- “这些信息先不回写，后面再补”

遇到这些念头时，回到 `runtime.md`，重新按：识别文件 → 补最小上下文 → 判阶段 → 路由 → 回写 的顺序执行。

## 输出要求

- 面向业务团队时，用业务语言、一次只推进一步
- 面向后续执行时，输出结构化输入，并标注待确认项、执行主体、审核主体和当前轮交付物
- 对外只暴露当前轮必须知道的下一步，不展开完整能力树
