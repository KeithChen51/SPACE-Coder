# Runtime — 主入口运行协议

主入口 `ai-project-manager` 的运行流程。读什么→判什么→做什么→写什么。

---

## 1. 运行流程（5 步）

### Step 1：启动 — 识别全局文件与状态回写入口

按以下顺序识别宿主项目是否已有 3 类全局文件，以及状态回写入口：

1. 全局规则文件（项目怎么运行）
2. 项目画像文件（项目当前是什么）
3. 当前执行计划文件（现在做什么）
4. `project-devlog` 入口与日志载体（最近发生了什么）

识别原则：先看职责不看文件名；先用宿主现有权威源，不先新建默认文件。
若宿主项目已有可用全局文件，则模板文件仅作为指向与映射参考，不重复创建物理文件；仅当宿主项目缺少对应全局文件且已完成必要访谈时，才允许基于模板创建。

**每日首次进入时**，额外确认：
- 当前操作者身份（优先用画像中的 `身份识别方式`）
- 计划入口是否明确（优先用画像中的 `计划入口文件`）
- 最近状态入口是否明确（优先用画像中的 `最近状态入口`）
- 今天从哪里继续（结合 `当前阶段` + `待确认项`）
- 当前任务类型所需专项规则和资料入口

### Step 2：读取 — 建立上下文

按固定顺序读取已识别的全局文件与状态回写入口。

**读取全局规则文件**时识别：项目结构、协作边界、技术边界、文档入口、权威源约定。

**读取项目画像文件**时，按优先级读取：

| 优先级 | 读取内容 |
|--------|----------|
| P1 | `项目名称`、`项目一句话目标`、`第一版核心目标`、`当前阶段`、`当前最适合进入的阶段`、`当前轮应输出的交付物` |
| P2 | `协作模式`、`身份识别口径`、`多操作者识别信息`、`当前任务执行主体` |
| P3 | 规则入口、计划入口、状态入口、PRD 入口、身份识别方式 |
| P4 | `第一版范围`、已有材料 |
| P5 | 待确认项 |

**读取执行计划文件**时识别：进行中任务、下一步任务、完成标准、前置依赖。

**读取状态日志载体**时识别：最近日志、最近验收、最近决策、待跟进事项；若命中日志或状态沉淀任务，默认由 `project-devlog` 承接，并写入宿主 `logs/` 或默认 `logs/`。

### Step 3：补齐 — 填缺口

按以下优先级补齐缺失信息：

| 缺口层级 | 内容 | 补齐方式 |
|----------|------|----------|
| 启动级（不补则无法恢复上下文） | 协议中的“启动最小必需字段包” | 用户确认优先；无法确认时停机等待，不自行编造 |
| 识别级（不补则无法稳定承接） | 协议中的“身份识别字段包” + 计划入口、状态入口、PRD 入口 | 系统推断优先；无法推断写 `待确认` |
| 推进级（不补则路由失真） | 协议中的“运行时回写字段包” | 主入口判断回写 |
| 画像级（影响当前判断才补） | 第一版范围、已有材料 | 用户确认优先；不追问非当前阶段所需信息 |

缺失文件时的降级处理（**必须严格遵守**）：

| 缺失文件 | 处理规则 |
|----------|----------|
| **项目画像** | **绝对禁止直接静默生成！** 必须立即停机，触发最小访谈（见 §3），由用户回答后才能生成。 |
| **全局规则** | 若无明确规则，不强行生成大维度的 `project-rules.md`，仅需在内存中标记“规则缺失”，使用默认配置即可。 |
| **执行计划** | **绝对禁止提前生成！** 仅在进入 S3 任务拆解阶段或 S4 开发执行阶段时，如果缺少计划才建议补齐。 |
| **状态回写** | 不阻断当前轮；优先识别宿主已有日志目录，本轮结束后默认调用 `project-devlog` 在日志文件中完成回写，不创建 `project-status.md`。 |
| **整体骨架缺口** | 若宿主项目连基本的 `docs/`、`logs/` 取舍等根目录层级都没建立，**主入口必须主动进入“骨架补齐”状态，读取 `routing.md` 并执行物理目录创建，不能跳过！** 若当前目录被判定为容器目录而非项目根，则必须先创建与 `项目名称` 同名的物理根目录，再在其中补骨架。 |

补齐动作口径：
- 已有对应全局文件：只建立模板指向关系，后续读写继续落在宿主已有文件。
- 缺少对应全局文件：先完成必要访谈，再按模板创建最小文件载体。

**字段来源口径**：
- **用户确认**：信息需要用户拍板才成立（含自然对话中明确表达的），不限于模板式访谈
- **系统推断**：可从仓库/文件/路径/角色映射自行识别的，不应转嫁给用户回答
- **主入口回写**：主入口综合判断后写回的阶段结论、交付物和执行主体

### Step 4：路由 — 判断阶段与下一步能力

根据项目画像判断当前最适合进入的阶段（见 §2 阶段判断表），然后决定：
- 停留在主入口继续澄清/补文件
- 进入某个子能力

进入子能力的必要条件（**全部满足**才进入）：
1. 当前阶段足够明确
2. 主入口已建立最小统一上下文
3. 当前轮目标超出主入口的"判断与路由"职责
4. 进入子能力能带来明确的新交付物

### Step 5：回写 — 写回正确的全局文件

| 内容类型 | 写入目标 |
|----------|----------|
| 项目目标澄清、阶段变化、协作模式、当前任务执行主体、入口信息、待确认项 | 项目画像文件 |
| 当前阶段任务、下一步任务、完成标准 | 执行计划文件 |
| 本轮做了什么、产出了什么、遇到的问题、下一轮建议 | 默认调用 `project-devlog` 写入日志文件 |
| 稳定的长期规则（极少更新） | 全局规则文件 |

禁止：把 3 类全局文件职责混写到同一个文件；把详细任务明细、完整过程日志写入画像。
禁止：宿主已有对应全局文件时，再额外创建一份同职责模板文件。
禁止：状态回写类任务绕过 `project-devlog` 直接自由写入状态载体，除非宿主项目已有更强约束。

## 2. 阶段判断表

| 阶段 | 适用信号 | 当前轮最小交付物 | 默认承载 |
|------|----------|------------------|----------|
| **S0 需求调研** | 需求仍停留在访谈和业务理解层；尚未形成正式需求文档 | 需求清单 | 主入口继续承载 |
| **S1 业务需求文档** | 调研信息已基本齐全；需要形成可评审的业务需求文档 | 业务需求文档 | 进入 `requirements` 能力 |
| **S2 页面构建与完整版 PRD** | 已有业务需求文档；需要借助页面和对话不断完善内容，并沉淀完整 PRD | 页面原型 / 页面代码 + 完整版 PRD | 进入 `solution-design` 能力 |
| **S3 任务拆解与开发计划** | 完整版 PRD 已形成；需要拆成开发任务并形成开发计划 | 开发计划 / 任务清单 | 进入 `delivery-planning` 能力 |
| **S4 开发执行** | 开发计划已明确；可以进入编码、联调和实现 | 开发结果 / 当前迭代实现 | 进入 `engineering-execution` 能力 |
| **S5 测试用例生成** | 开发结果已可验证；需要基于 PRD 生成标准化测试用例 | 测试用例文档 | 进入 `prd-test-case-generator` 能力 |
| **S6 测试执行** | 测试用例已准备好；需要执行测试并记录问题 | 测试结果 / 缺陷清单 | 进入 `test-acceptance` 能力 |
| **S7 人工点检准备** | 测试已完成；需要为人工点检准备检查项和验收说明 | 点检清单 / 验收说明 | 进入 `test-acceptance` 能力 |
| **S8 点检结果回写与收口** | 已拿到人工点检结果；需要沉淀验收结论、遗留问题和下一步 | 验收结论 / 遗留问题 / 下一轮建议 | 进入 `test-acceptance` 能力 |

决策规则：
1. 多个阶段可选时，优先较早阶段
2. 缺关键业务信息时不跳过 S0
3. 用户要求"先给方案"→ S1 或 S2；要求"拆任务"→ S3
4. 用户要求实现某模块但上下文不足，先补最少上下文再进入 S3/S4
5. `当前阶段`（画像已有） vs `当前最适合进入的阶段`（主入口综合判断）冲突时，先解释差异再更新画像

### 2.1 全局伴随能力规则

`project-devlog` 不归属于单一阶段，而是全局伴随能力。

满足以下任一条件时，本轮结束默认调用 `project-devlog`：
- 产生了新的阶段交付物
- 当前阶段发生变化
- 完成了一次有效推进
- 需要为下一轮留下承接状态

## 3. 首轮极简访谈

**触发条件**：项目画像缺失，且协议中的“启动最小必需字段包”信息不足。

**目标**：用最少问题补齐协议中的“启动最小必需字段包”，足以判断下一阶段即可停止。

### 首次必问（6 问）

| # | 问题 | 对应字段 | 参考回答示例 |
|---|------|----------|------------|
| 1 | 这个项目叫什么？ | `项目名称` | "叫门店设备巡检助手" |
| 2 | 一句话在解决什么？ | `项目一句话目标` | "帮门店把巡检、异常上报和进度放到一个系统里" |
| 3 | 主要给谁用？ | `目标用户` | "门店店长和巡检人员" |
| 4 | 最想解决什么问题？ | `主要问题` | "现在靠 Excel 和微信群，漏检和跟进不及时" |
| 5 | 第一版最想先实现什么？ | `第一版核心目标` | "先让巡检记录、异常上报和处理闭环能在线跑通" |
| 6 | 这个项目是你一个人配合 AI 推进，还是多人各自配合 AI 一起推进？ | `协作模式` | "业务单人 + AI执行" |

### 条件追问

| 条件 | 追问 | 对应字段 |
|------|------|----------|
| 业务多人 + AI执行 | 如果是多人一起推进，我们之后可以通过什么信息区分不同操作者？例如仓库、GitHub、邮箱、用户名、代号 | `多操作者识别信息` |
| 即将进入 S1/S2/S3 | 第一版最需要先做哪几块？ | `第一版范围` |

### 展示规则
- 每次提问附 1 条参考回答，标注"仅供参考，可按实际情况改写"
- 不展示 `对应字段` 给用户
- 用户回答清楚后可停止，不必问完所有问题
- 一旦 `项目名称` 已确认，且当前工作目录疑似容器目录，后续骨架补齐时默认使用 `<当前目录>/<项目名称>/` 作为物理落点，除非用户明确指定其他位置

### 禁止
- 不问技术栈/数据库/中间件
- 不发十几条问卷式问题
- 不把系统推断字段（规则入口/计划入口/状态入口）拿来问用户
- 不把主入口回写字段（当前阶段/当前轮交付物）丢给用户作答
- 信息不足时不承诺具体实现方案

## 4. 协作模式判断

| 判断项 | 业务单人 + AI执行 | 业务多人 + AI执行 |
|--------|-------------------|-------------------|
| 识别重点 | 默认以当前操作者为主要承接入口 | 必须补齐 `多操作者识别信息`，便于区分不同人 / AI 上下文 |
| 推进方式 | 主入口围绕当前操作者持续推进 | 主入口按身份映射识别不同操作者的上下文与任务承接 |
| 画像要求 | 记录基础画像即可 | 除基础画像外，还需记录稳定的多人识别线索 |

协作模式判断以项目画像为首要来源。画像缺失时通过最小访谈补齐。补齐后回写画像，不只停留在对话里。

---

## 5. 默认交付链路

当用户没有指定研发流程时，按此顺序推进：

```
项目画像 → 需求清单 → 业务需求文档 → 页面构建与完整版 PRD → 开发计划 → 开发执行 → 测试用例 → 测试执行 → 人工点检准备 → 点检结果回写
```

输出约束：
- 每轮留下可复用文档，不只停留在对话里
- 每轮写清楚下一步，不只给方向
- 用户时间有限时，优先输出当前阶段最小交付物（见 §2 表格）
