# 宿主项目脚手架构建参考

本文件服务 `ai-project-manager` 的“宿主项目脚手架构建能力”。

当主入口触发到该能力时，应按本文件定义对宿主项目执行目录和文件骨架补齐。

主入口需要具备以下能力：

1. 识别宿主项目当前是否已有可映射的项目骨架
2. 判断宿主项目缺少哪些关键目录和文件
3. 按条件补齐应创建的目录和文件
4. 对当前阶段不应提前创建的目录保持延后

## 使用边界

本文件一旦被主入口命中，就不应只停留在“给建议”。

这意味着：

- 应先识别宿主项目已有结构
- 再按缺口补齐目录和文件
- 不应因为其它目录还不到触发阶段，就一次性建满完整工程目录
- 不应覆盖宿主项目已有权威文件

## 触发时机

当满足以下任一条件时，可读取本文件：

- 初始访谈完成，项目画像已基本成型
- 用户希望知道“这个项目应该怎么搭目录”
- 主入口识别到宿主项目缺少稳定项目骨架
- 当前阶段继续推进已经需要稳定目录和文件载体

## 构建目标

主入口读取本文件后，应优先输出：

1. 宿主项目当前已有骨架的识别结果
2. 当前缺失的关键文件和目录
3. 本轮实际补齐了哪些目录和文件
4. 哪些目录因阶段未到而暂不创建
5. 当前创建结果对后续入口恢复的影响

## 核心原则

### 1. 先识别，再构建

- 先扫描宿主项目已有文件和目录
- 能做角色映射时，不把已有结构视为“缺失”
- 只有无法映射的关键骨架，才执行补齐

### 2. 先补最小骨架，不一次性铺满完整工程目录

- 启动阶段只补最小可持续推进骨架
- 文档目录按阶段补建
- 实现目录按真实开发需要补建

### 3. `execution-plan` 是当前激活计划角色

- 允许宿主项目存在多份计划文件
- 任一时刻只认一个当前主计划入口
- 当前主计划入口应记录在 `project-profile.md`
- 在未确定当前主计划入口前，不应在多份计划之间来回混写

### 4. 触发后就应执行补齐

- 本文件不是纯说明文档
- 一旦主入口因骨架缺口命中本文件，就应按条件补齐宿主项目目录和文件
- 只有未到触发阶段的目录，才应继续延后

## 三层目录规划模型

### 第一层：启动必建骨架

适用标准：

- 没有这些目录和文件，主入口无法稳定恢复上下文和继续推进下一轮

默认补齐骨架：

```text
<项目名称>/
├── project-profile.md
├── project-rules.md
├── docs/
│   ├── plans/
│   │   └── execution-plan.md
│   └── rules/
├── logs/
└── .agent/
    └── skills/
```

构建口径：

- `project-profile.md`：项目快照与当前主计划入口
- `project-rules.md`：长期规则与计划组织规则
- `docs/plans/execution-plan.md`：初始主计划载体
- `docs/rules/`：专项规则沉淀位
- `logs/`：状态回写与开发日志目录
- `.agent/`：宿主项目本地 AI 配置根目录，作为后续本地能力挂载位
- `.agent/skills/`：宿主项目沉淀本地 skill、覆盖默认实现或补充宿主增强能力的统一入口
- 宿主项目根目录命名默认以项目名称为准；本文中的 `<项目名>` 与根目录项目名称使用同一命名锚点

### 第二层：阶段触发目录

适用标准：

- 只有进入对应阶段后才有必要创建

满足条件时补齐：

```text
docs/
├── prd/
├── decisions/
├── test-case/
└── architecture.md
```

触发口径：

- `docs/prd/`：进入需求整理、需求持续迭代时
- `docs/decisions/`：进入方案选型、关键决策沉淀时
- `docs/test-case/`：进入测试设计、验收设计时
- `docs/architecture.md`：确有架构总览需要时

### 第三层：实现触发目录

适用标准：

- 只有进入真实开发或工程化协作后才有必要创建

满足条件时补齐：

```text
src/
tools/
```

触发口径：

- `src/`：确认进入真实开发阶段时
- `tools/`：出现脚本、自动化、迁移需求时

`src/` 内部结构默认参考：

```text
src/
├── <项目名>-Toc/
│   ├── frontend/
│   └── backend/
├── <项目名>-Config/
│   ├── frontend/
│   └── backend/
└── shared/
```

其中 `shared/` 只在两端确有共享需求时建议使用。

`.agent/` 内部最小结构参考：

```text
.agent/
└── skills/
```

其中：

- `.agent/skills/` 不是套件源码目录，而是宿主项目沉淀本地 skill 的位置
- 启动初始化时就应补齐 `.agent/` 与 `.agent/skills/`，避免宿主项目后续落地本地能力时没有稳定挂载位
- 不要求首次就把所有 skill 子目录建满；该目录先作为宿主增强能力和本地覆写的统一入口

## 主入口执行结果模板

当主入口基于本文件执行补齐后，建议输出：

1. 当前宿主项目已识别到的骨架
2. 本轮实际补齐的第一层目录和文件
3. 当前阶段暂不创建的第二层、第三层目录
4. 现在可供后续文件和能力使用的入口路径

推荐表达方式：

- “当前已经识别到的目录角色：……”
- “本轮已补齐的最小骨架：……”
- “当前阶段暂不创建：……”
- “后续可直接使用的入口路径：……”
