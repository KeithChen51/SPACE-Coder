# 首轮极简访谈

只在项目刚启动、信息明显不足、用户没有技术背景时读取本文件。

## 对用户展示规则

- 本文件中的示例不是仅供内部理解；首轮访谈默认可直接展示给用户作为 `参考回答`
- 展示时必须明确标注：`参考回答：仅供你参考，你可以按实际情况改写，不需要照抄`
- 每次提问默认附 1 条参考回答，不要把整份示例清单一次性发给用户
- 若用户已经回答得很清楚、当前轮目标只是快速确认，不强制重复补发参考回答
- 参考回答应保持口语化、短句化，长度以 1 句话为主，不要写成完整方案

## 访谈目标

首轮访谈的唯一目的，是用最少问题补齐项目画像中的 `用户确认字段`。

当前默认的 `用户确认字段` 包括：

- `项目名称`
- `项目一句话目标`
- `协作模式`
- `第一版核心目标`
- `目标用户`
- `主要问题`
- `第一版范围`
- `其他成员`
- `任务拆分方式`

但首轮不要求一次补齐全部字段，而是分为：

1. 首次必问字段
2. 条件追问字段
3. 可延后确认字段

达到“足以生成项目画像并判断下一阶段”即可停止，不要一次问尽所有细节。

## 字段分层

### 1. 首次必问字段

这些字段决定是否能生成最小项目画像：

- `项目名称`
- `项目一句话目标`
- `目标用户`
- `主要问题`
- `第一版核心目标`
- `协作模式`

### 2. 条件追问字段

这些字段只在满足条件时追问：

- `第一版范围`
  - 当用户已经能描述第一版边界，或主入口判断即将进入 `S1 / S2` 时再问
- `其他成员`
  - 当用户明确是多人协作时再问
- `任务拆分方式`
  - 当主入口即将进入任务拆解，且确实需要按人 / 按角色拆分时再问

### 3. 可延后确认字段

以下内容若当前轮不影响阶段判断，可先写入 `待确认`：

- 更细的第一版范围
- 更完整的成员清单
- 更明确的任务拆分方式

## 推荐问题

优先使用以下 6 问，按顺序逐步推进：

1. 这个项目叫什么，或者我该怎么称呼它？
   - 对应字段：`项目名称`
   - 参考回答：`叫“门店设备巡检助手”，后面你就这么称呼它。`
2. 你希望这个项目一句话是在解决什么？
   - 对应字段：`项目一句话目标`
   - 参考回答：`帮门店人员把巡检、异常上报和处理进度放到一个系统里。`
3. 这个系统主要给谁用？
   - 对应字段：`目标用户`
   - 参考回答：`主要给门店店长和巡检人员用，管理层偶尔会看汇总。`
4. 你们现在最想解决什么问题？
   - 对应字段：`主要问题`
   - 参考回答：`现在靠 Excel 和微信群推进，漏检和跟进不及时。`
5. 如果只做第一版，你最想先实现什么结果？
   - 对应字段：`第一版核心目标`
   - 参考回答：`先让巡检记录、异常上报和处理闭环能在线跑通。`
6. 这是你一个人推进，还是多人一起协作？
   - 对应字段：`协作模式`
   - 参考回答：`产品和业务一起推进，开发由两个人配合。`

若用户已明确是多人协作，追加以下问题：

7. 如果是多人协作，分别是谁负责业务确认、谁负责执行、谁负责审核？
   - 对应字段：`其他成员`
   - 参考回答：`业务确认是运营负责人小王，执行是我和开发同事，审核是老板。`

若主入口判断当前已经需要形成第一版范围，再追加：

8. 第一版你觉得最需要先做哪几块？
   - 对应字段：`第一版范围`
   - 参考回答：`先做巡检任务、异常上报、处理状态跟踪这三块。`

若主入口判断即将进入任务拆解，再追加：

9. 后面任务更适合按人拆，还是按角色拆？
   - 对应字段：`任务拆分方式`
   - 参考回答：`先按角色拆，产品负责确认，开发负责实现，测试负责验收。`

## 推荐展示格式

首轮访谈默认优先使用以下格式：

```md
这个项目叫什么，或者我该怎么称呼它？

参考回答：比如“叫门店设备巡检助手，后面你就这么称呼它”。仅供参考，你可以按实际情况改写。
```

不要把 `对应字段` 直接展示给用户；那部分是主入口内部映射信息。

## 追问与停止规则

- 如果用户回答很模糊，只追问当前最影响阶段判断的那一项。
- 如果主入口已经能据此生成最小项目画像并判断下一阶段，就停止访谈。
- 如果某个字段当前不影响阶段判断，优先写 `待确认`，不要继续深挖。
- 如果用户已有材料，优先让其提供材料，再减少口头追问。
- 如果用户表达出“我不懂这些”，改用更口语化问法，不要抛术语。
- 如果用户说是多人协作，但角色不清楚，至少追问出“谁拍板、谁执行、谁验收”。
- 不要把 `系统推断字段` 和 `主入口判断回写字段` 混进首轮访谈里要求用户手填。

## 禁止事项

- 不要一上来问技术栈、数据库、中间件。
- 不要发十几条问卷式问题。
- 不要把研发流程责任推给用户判断。
- 不要把规则入口、计划入口、状态入口、PRD 入口这类本应由系统先推断的信息拿来首轮就问用户。
- 不要把当前阶段、当前最适合进入的阶段、当前轮交付物这类本应由主入口判断回写的信息直接丢给用户作答。
- 不要在信息不足时直接承诺具体实现方案。
- 不要在未识别协作模式时直接输出多人任务拆分。
