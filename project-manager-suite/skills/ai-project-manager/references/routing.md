# 路由条件与项目骨架

本文件定义主入口的路由决策条件、能力映射以及宿主项目骨架补齐规则。

---

## 1. 路由条件表

主入口根据以下条件决定其动作。**核心原则：先补骨架再补内容；先做判断再做执行。**

| 当前上下文状态 | 主入口动作 | 是否进入子能力 | 默认输出 |
|----------------|------------|----------------|----------|
| **缺项目画像文件（新项目首次启动）** | **停留在主入口，向用户发起首轮极简访谈** | 否 | 发送访谈问题 |
| **初始访谈结束，但宿主项目缺少目录骨架** | **立即按 §3 执行物理骨架构建，不能跳过！** | 否 | 已建骨架 + 暂缓创建项 |
| **缺全局规则文件，但可从现有文件推断** | 使用内存默认推断，不强行生成物理文件 | 否 | 仅在后台标记 |
| **画像存在，但用户意图/入口/阶段判断等有缺口** | 停留主入口澄清并补齐 | 否 | 更新后的项目画像 |
| **当前阶段为 S0（考虑孵化）** | 停留主入口澄清想法 | 否 | 画像初稿 / 待确认问题 |
| **当前阶段为 S1（方案成型）** | 路由到需求/方案能力 | **是** | 需求摘要 / 方案设计 |
| **当前阶段为 S2（研发拆解）** | 路由到计划能力 | **是** | 最小执行计划 / 任务清单 |
| **当前阶段为 S3（开发执行）** | 路由到执行能力 | **是** | 当前任务输入 |
| **当前阶段为 S4（验收收口）** | 路由到验收/回写能力 | **是** | 验收结论 / 状态回写 |
| **本轮结束，不需要子能力承接大单体任务** | 直接统一回写 | 否 | 更新后的全局文件 |

> **只补文件，不进子能力的条件（归纳）**：缺骨架、缺基础画像、缺入口信息、阶段无法判断、或本轮只为对齐信息不需直接执行。
> **进入子能力的必要条件**：阶段明确、上下文统一、目标已超出主入口判断职责、且能带来具体交付物。

## 3. 宿主项目脚手架构建规则

当主入口因缺少骨架或用户要求而触发项目构建时（**前提：必须已完成首轮极简访谈，拿到最核心的画像上下文！**），执行目录体检不应盲目铺满。

### 第一层：启动必建骨架（基础续航）
只要初始化即构建。不应覆盖宿主已有对应层。

```text
<项目名称>/
├── project-profile.md     (项目快照与主计划入口)
├── project-rules.md       (长期规则与计划组织规则)
├── docs/plans/
│   └── execution-plan.md  (初始主计划载体)
├── docs/rules/            (专项规则沉淀位)
├── logs/                  (状态回写与开发日志目录)
└── .agent/skills/         (宿主项目本地 AI 配置和扩充能力挂载位)
```

### 第二层：阶段触发目录（按需创建）
只在进入对应阶段后补建：
- `docs/prd/` (进入需求阶段)
- `docs/decisions/` (发生方案选型决策)
- `docs/test-case/` (进入测试设计)
- `docs/architecture.md` (有架构总览要求)

### 第三层：实现触发目录（真实开发前建）

适用标准：

- 只有进入真实开发或工程化协作后才有必要创建

满足条件时补齐：

```text
src/
tools/
```

触发口径：

- `src/`：确认进入真实开发阶段时
- `tools/`：出现脚本、自动化、迁移需求时

`src/` 内部结构默认参考：

```text
src/
├── <项目名>-Toc/
│   ├── frontend/
│   └── backend/
├── <项目名>-Config/
│   ├── frontend/
│   └── backend/
└── shared/
```

其中 `shared/` 只在两端确有共享需求时建议使用。

> **操作纪律**：先扫描，能映射的映射，识别到真缺失再补。若只是某个次要阶段还没到，其所属目录不要提前建立。在操作结束后，给出已建和延后建的总结单。
