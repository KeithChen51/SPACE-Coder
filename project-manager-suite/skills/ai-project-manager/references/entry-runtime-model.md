## 1. 目的

本文件定义 `project-manager-suite` 的主入口 `ai-project-manager` 在宿主项目中的运行协议。

本文件不解释“项目经理是什么”，而专门回答：

1. 主入口启动时先读什么
2. 主入口如何识别宿主项目已有文件
3. 主入口在缺少文件时如何补齐
4. 主入口如何处理 `solo / 团队协作`
5. 主入口把哪些结果写回哪些全局文件

具体读写边界见：

- `global-files-readwrite-protocol.md`

---

## 2. 运行目标

`ai-project-manager` 的运行目标不是直接完成全部工作，而是：

- 建立当前项目的统一上下文
- 判断当前阶段
- 确认执行主体
- 决定下一步进入哪个能力
- 决定当前应由哪个岗位能力介入
- 明确当前轮最小交付物和交付要求
- 把本轮结果写回正确的全局文件

它始终是：

**编排入口**

不是：

- 全部规则的唯一承载者
- 全部执行细节的唯一承载者

---

## 3. 运行输入

主入口运行时依赖两类输入：

### 3.1 用户输入

- 用户当前请求
- 用户提供的业务描述
- 用户提供的现有材料

### 3.2 项目全局文件

按 `global-files-model.md` 约定，主入口应优先识别以下 4 类全局文件：

1. 全局规则文件
2. 项目画像文件
3. 当前执行计划文件
4. 项目状态回写文件

### 3.3 套件默认文件路径

当宿主项目没有现成权威文件、需要使用套件默认骨架时，主入口默认读取或生成以下文件：

- 全局规则文件：`skills/ai-project-manager/assets/global-files/project-rules.md`
- 项目画像文件：`skills/ai-project-manager/assets/global-files/project-profile.md`
- 当前执行计划文件：`skills/ai-project-manager/assets/global-files/execution-plan.md`
- 项目状态回写文件：`skills/ai-project-manager/assets/global-files/project-status.md`

主入口运行时还会引用以下协议与路由文件：

- 全局文件角色模型：`global-files-model.md`
- 最小字段合同：`global-files-minimum-shared-protocol.md`
- 全局文件读写协议：`global-files-readwrite-protocol.md`
- 主入口路由条件：`entry-routing-conditions.md`
- 项目推进工作流：`docs/design/project-progression-workflow.md`

若需要进入套件内置基础能力，默认路由目标位于：

- 主入口：`skills/ai-project-manager/`
- 需求整理：`skills/requirements-starter/`
- 方案整理：`skills/solution-designer/`
- 任务拆解：`skills/delivery-planner/`
- 开发执行：`skills/engineering-executor/`
- 测试验收：`skills/test-and-acceptance/`
- 状态回写：`skills/project-devlog/`
- 编码规范：`skills/coding-standards/`

### 3.4 能力解析与默认实现

主入口在运行时，不应直接把“当前任务”硬绑定到某个固定 skill 路径，而应先经过一层稳定能力名解析。

最小解析顺序固定为：

1. 先识别当前轮需要哪类能力
2. 再读取 `entry-routing-conditions.md` 判断该能力此时是否应被触发
3. 若应触发，再使用 runtime 中声明的默认实现进入对应 skill
4. 若项目画像、项目规则或宿主项目已有更高优先级入口，则允许覆盖套件默认实现

这里的稳定对象优先是“能力名”，而不是“具体 skill 路径”。

一致性约束：

- 本文件只声明主入口何时进入能力解析，以及当前套件默认提供哪些实现入口
- 具体“稳定能力名 -> 默认实现”的命名基线，以 `entry-routing-conditions.md` 为准
- 本文件中出现的 `skills/...` 路径都属于当前默认实现，不属于上层公开能力名

例如：

- 需求成型阶段优先识别为“需求整理能力”
- 研发拆解阶段优先识别为“计划拆解能力”
- 开发执行阶段优先识别为“开发执行能力”
- 当任务涉及代码编写、代码修改、重构、接口设计、SQL 变更、自动化测试或测试用例文档维护时，还应额外识别“编码规范能力”

这样设计的目的不是增加抽象层，而是保证：

- 主入口上层路由口径稳定
- skill 实现可在后续迭代中替换
- 开源版与增强版可以共用同一能力名，但挂载不同实现

## 4. 项目画像依赖总览

`project-profile.md` 不是主入口“顺手读一下”的附属文件，而是主入口建立项目上下文时最重要的快照载体。

主入口依赖项目画像，主要是为了回答：

1. 当前项目是什么
2. 当前应处在哪个阶段
3. 该由谁推进、谁确认
4. 当前项目应从哪里继续读、往哪里继续写

主入口对项目画像的依赖可按以下字段簇理解：

| 画像信息 | 主要字段 | 主入口使用时机 | 缺失时处理 | 成功推进后回写点 |
|---|---|---|---|---|
| 项目基础判断 | `项目名称`、`项目一句话目标`、`第一版核心目标` | 建立项目快照、判断当前轮是否仍在同一项目语境 | 优先从现有规则、计划、需求资料推断；仍不明确时最小访谈补齐 | 项目目标澄清结果 |
| 阶段与推进判断 | `当前阶段`、`当前最适合进入的阶段`、`当前轮应输出的交付物`、`当前最大不确定项` | 判断当前阶段、决定今日继续点、决定是否进入子能力 | 无法确认时写 `待确认`；阶段仍不明确时回退到更靠前阶段继续澄清 | 当前阶段变化、当前最适合进入的阶段、当前轮应输出的交付物、当前最大不确定项 |
| 协作与身份判断 | `协作模式`、`业务负责人`、`执行负责人`、`审核 / 验收负责人`、`当前任务执行主体`、`当前任务审核主体`、`身份识别口径` | 判断 `solo / 团队协作`、确认执行主体与审核主体、判断任务是否可进入执行 | 优先从画像与宿主项目成员信息推断；仍缺失时最小访谈补齐 | `solo / 团队协作`、团队成员与身份识别、当前任务执行主体 / 审核主体 |
| 范围与优先级判断 | `第一版范围`、`最优先模块`、`时间要求` | 判断当前轮范围是否收敛、决定推进优先级与是否先补画像 | 缺失但不阻断当前轮时暂不追问；确实影响判断时再补 | 第一版范围、当前优先级 |
| 项目入口与识别信息 | `规则入口文件`、`计划入口文件`、`最近状态入口`、`PRD 总入口`、`身份识别方式`、`任务类型规则入口`、`最近状态定位口径` | 每日首次进入项目时恢复上下文、确定从哪读计划 / 状态 / PRD / 专项规则 | 优先用画像层；缺失时退回规则层、计划层、状态层做角色映射；仍无法确认则写 `待确认` | 入口与识别信息补齐结果 |
| 待确认与补齐线索 | `待确认 1/2/3`、`已有文档`、`已有原型 / 截图`、`已有系统 / Excel / 流程`、`其他可用材料` | 判断最小访谈该追问什么、决定还能从哪些资产推断 | 能从现有资产推断的不重复问；不能推断的保留在 `待确认` | 待确认项变化、当前资产补充结果 |

这张总表的作用不是重复协议，而是把：

- 画像里有哪些信息
- 主入口在哪一步使用它们
- 缺失时怎么降级
- 推进后该写回什么

收成一套运行时可直接引用的口径。

### 4.1 `用户确认` 与 `系统推断` 的判定口径

在主入口运行中，`用户确认` 和 `系统推断` 的区别，不应按“信息是否来自对话”来判断，而应按“这个信息是否需要用户拍板才成立”来判断。

判定原则固定为：

- `用户确认`
  - 只要某个信息的成立依赖用户明确表达、确认或认可，它就是 `用户确认`
  - 即使这个信息是在自然对话里顺手提到的，而不是通过模板式访谈逐题回答得到的，它仍然属于 `用户确认`
- `系统推断`
  - 只要某个信息不依赖用户拍板，而是可以由主入口根据仓库、文件、路径、身份、已有材料和权威源角色映射自行识别，它就是 `系统推断`
  - 即使主入口最终在对话里把这个推断结果告诉用户，它也不因此变成 `用户确认`

因此，主入口需要遵守两条运行约束：

- `用户确认字段` 可以来自用户自然对话，也可以来自极简访谈模板；访谈模板只是标准采集工具，不是唯一输入形式
- `系统推断字段` 必须优先尝试由系统自行识别，不应默认转嫁给用户回答

例如：

- 用户说“第一版先做管理台登录和工单列表”，这属于 `用户确认`
- 主入口从仓库中识别当前唯一执行计划文件，这属于 `系统推断`
- 用户说“我们现在两个人协作，我负责业务确认，另一个人负责开发”，这属于 `用户确认`
- 主入口通过 `git config user.email`、日志文件名或现有规则入口识别当前操作者和入口路径，这属于 `系统推断`

## 5. 默认运行顺序

主入口默认按以下顺序运行。

### 5.0 每日首次进入项目的默认启动流程

当 AI 在当天第一次进入某个项目时，应先完成一轮最小启动检查，再进入后续阶段判断和能力路由。

推荐顺序如下：

1. 识别当前操作者
2. 确认计划入口
3. 确认最近状态入口
4. 判断今天应从哪里继续
5. 加载当前任务类型对应的专项规则
6. 按计划补读当前任务所需依据资料
7. 与用户确认今日继续点

其中：

- 第 1-4 步用于恢复项目上下文，不得跳过
- 第 5-6 步用于按任务类型渐进加载，不得一次性展开全部资料
- 第 7 步用于在继续推进前，对齐今日起点与范围

这 7 步与项目画像的对应关系应固定为：

1. 识别当前操作者
   - 优先使用：`身份识别方式`、`身份识别口径`
2. 确认计划入口
   - 优先使用：`计划入口文件`
3. 确认最近状态入口
   - 优先使用：`最近状态入口`、`最近状态定位口径`
4. 判断今天应从哪里继续
   - 结合：`当前阶段`、`当前最适合进入的阶段`、`当前轮应输出的交付物`、`待确认项`
5. 加载当前任务类型对应的专项规则
   - 优先使用：`任务类型规则入口`
6. 按计划补读当前任务所需依据资料
   - 优先使用：`PRD 总入口`
7. 与用户确认今日继续点
   - 用画像中的阶段判断、交付物和待确认项收口

若宿主项目已在项目画像中提供了具体入口信息，主入口应优先使用画像层提供的规则入口、计划入口、状态入口、PRD 入口和身份识别口径。
若画像未提供，则退回规则层、计划层、状态层做角色映射。
若缺少其中任一入口：

- 能从现有权威文件推断的，优先推断
- 不能推断的，写入 `待确认`
- 不因局部入口缺失而整体阻断启动

完成这轮最小启动检查后，再进入以下默认运行顺序。

### 5.1 宿主项目目录结构能力的触发条件

当满足以下条件时，主入口应进入“宿主项目目录结构构建”：

1. 初始访谈已完成，且项目画像已基本成型
2. 宿主项目缺少稳定的项目骨架，导致后续阶段无法找到清晰的规则入口、计划入口、状态入口或资料沉淀位置
3. 用户明确希望确认“这个项目应如何搭建目录和文件结构”

触发后，主入口应读取：

- `project-scaffold.md`

该能力在运行时主要解决：

- 宿主项目当前已有目录和文件能否映射为项目骨架角色
- 当前缺少哪些关键目录和文件
- 当前应实际补齐哪一层骨架
- 哪些目录应延后到后续阶段再补

触发边界：

- 若宿主项目现有结构已足以支撑规则入口、计划入口、状态入口和资料入口恢复，则不必额外进入该能力
- 若当前轮只需要继续已有计划和状态，不因存在可优化空间就强行进入目录结构构建

### Step 1：识别宿主项目是否已有全局文件

先判断宿主项目是否已经存在：

- 全局规则文件
- 项目画像文件
- 当前执行计划文件
- 项目状态回写文件

识别原则：

- 先看职责，不看文件名
- 先用宿主项目现有权威源，不先新建默认文件

### Step 2：读取全局规则文件

目标：

- 先建立项目运行边界

主入口需要从全局规则文件中识别：

- 项目结构
- 协作边界
- 技术边界
- 文档入口
- 权威源约定
- 是否已有现成 skill 体系

如果宿主项目没有全局规则文件：

- 进入套件默认规则兜底模式
- 必要时生成最小 `project-rules.md`

### Step 3：读取项目画像文件

目标：

- 建立当前项目快照
- 建立启动所需入口信息
- 建立阶段判断与协作判断基线

主入口读取项目画像时，优先级应固定为：

第一优先：

- 项目基础判断与阶段判断
- 也就是：`项目名称`、`项目一句话目标`、`第一版核心目标`、`当前阶段`、`当前最适合进入的阶段`、`当前轮应输出的交付物`

第二优先：

- 协作模式、执行主体、审核主体
- 也就是：`solo / 团队协作`、`当前任务执行主体`、`当前任务审核主体`、相关团队身份信息

第三优先：

- 入口与识别信息
- 也就是：规则入口、计划入口、状态入口、PRD 入口、身份识别方式、任务类型规则入口

第四优先：

- 范围、优先级、已有资产
- 也就是：第一版范围、优先级信息、已有文档与材料

第五优先：

- 待确认项

这里需要额外注意：

- `用户确认` 信息不要求必须来自模板式访谈
- 只要用户已经在自然对话中明确表达并被主入口确认，就可以直接写入对应的 `用户确认字段`
- 极简访谈只在关键 `用户确认字段` 缺失时才作为补齐手段启用
- `系统推断` 信息则应优先由主入口自行识别，不应因为正在对话就默认改为向用户发问

主入口需要从项目画像文件中识别的最小内容包括：

- 项目目标
- 当前阶段
- 当前最适合进入的阶段
- 当前轮应输出的交付物
- 第一版范围
- 当前优先级
- `solo / 团队协作`
- 当前执行主体 / 审核主体
- 项目入口与识别信息
- 待确认项

如果宿主项目没有项目画像文件：

- 由主入口发起最小访谈
- 生成默认项目画像文件

若项目画像存在但部分字段缺失：

- 必要字段可从现有文件推断时，先推断
- 无法推断时，通过最小访谈补齐
- 暂不影响本轮推进的信息，写入 `待确认`
- 若阶段仍不明确，回退到更靠前阶段继续澄清

### Step 4：读取当前执行计划文件

目标：

- 识别当前阶段的具体任务
- 识别本轮任务依赖的资料入口

主入口需要读取：

- 当前进行中的任务
- 下一步任务
- 完成标准
- 前置依赖
- `PRD依据` 或等价资料入口

如果宿主项目没有执行计划文件：

- 允许先只依赖项目画像推进
- 在后续需要进入拆解阶段时，再建议生成最小 `execution-plan.md`

### Step 5：读取项目状态回写文件

目标：

- 识别最近推进状态
- 恢复最近一次中断前的继续起点

主入口需要读取：

- 最近日志
- 最近验收
- 最近决策或变更
- 最近待跟进事项或等价继续线索

如果宿主项目没有状态回写文件：

- 允许继续推进
- 但在本轮结束时应建议生成最小 `project-status.md`

### Step 6：补齐缺失信息

在完成 4 类文件识别后，主入口判断缺失项。

优先补齐顺序：

1. 项目画像关键信息
2. 协作模式与身份识别
3. 当前阶段判断
4. 当前执行计划缺口
5. 状态回写缺口

补齐方式：

- 能从现有文件中推断的，不重复问用户
- 无法推断的，通过最小访谈追问
- 仍无法确认的，写入 `待确认`

这里的补齐逻辑应进一步固定为：

- 需要用户拍板才成立的信息，归入 `用户确认`，可以直接从自然对话采集；缺失时再用极简访谈追问
- 不需要用户拍板、但可由仓库和权威文件识别的信息，归入 `系统推断`，应先由主入口自行推断
- 不得因为用户正在对话中，就把本应 `系统推断` 的信息默认转成对用户的追问

其中，“项目画像关键信息”应继续细分为以下 3 层：

1. 启动级缺口
   - `身份识别方式`
   - `计划入口文件`
   - `最近状态入口`
   - `PRD 总入口`
   - `任务类型规则入口`
2. 推进级缺口
   - `当前阶段`
   - `当前最适合进入的阶段`
   - `当前轮应输出的交付物`
   - `当前任务执行主体 / 审核主体`
3. 画像完善级缺口
   - 目标用户
   - 主要问题
   - 第一版范围
   - 已有材料
   - 优先级信息

补齐优先级应固定为：

- 启动级缺口优先补，避免主入口找不到入口文件或无法恢复上下文
- 推进级缺口在进入子 skill 前补，避免路由或交付判断失真
- 画像完善级缺口只在确实影响当前判断时才追问

若当前是每日首次进入项目，还应优先补齐以下启动缺口：

- 当前操作者身份是否可识别
- 计划入口是否明确
- 最近状态入口是否明确
- 今日继续起点是否已从最近状态或计划中恢复
- 当前任务类型所需专项规则和资料入口是否明确

若在补齐启动级缺口时发现：

- 项目画像虽然可补，但宿主项目整体缺少稳定的目录和文件骨架
- 入口信息无法在现有结构中稳定落位
- 当前阶段继续推进会反复遇到“没有合适载体可写”的问题

则主入口应转入“宿主项目目录结构构建”，读取 `project-scaffold.md` 后执行对应层级的骨架补齐。

### Step 7：判断当前阶段

在上下文足够后，主入口判断当前最适合进入：

- `S0` 想法澄清
- `S1` 方案成型
- `S2` 研发拆解
- `S3` 开发执行
- `S4` 验收收口

这里至少依赖项目画像中的以下信息：

- `当前阶段`
- `当前最适合进入的阶段`
- `当前轮应输出的交付物`
- `当前最大不确定项`

其中：

- `当前阶段` 是已有判断输入，不是唯一真相
- `当前最适合进入的阶段` 是主入口综合当前上下文后的更强信号

若仅凭项目画像和当前上下文仍无法稳定判断阶段，主入口应补读：

- `stage-router.md`

当两者冲突时：

- 主入口应先解释差异来自哪里
- 再更新项目画像中的阶段判断
- 不应静默覆盖原记录

### Step 8：决定下一步能力

根据阶段和信息完整度，决定是否：

- 停留在主入口继续澄清
- 进入默认基础子能力
- 进入宿主项目已有增强 skill

这里的“能力”应理解为：

- 项目推进中的岗位职责能力
- 而不是零散功能点集合

因此主入口在这一步不仅决定进入哪个 skill，也要同时判断：

- 当前该由哪个岗位能力承担
- 该岗位当前轮需要产出什么交付物
- 该交付物应该写回哪一类全局文件

若当前需要先收口“这一轮最小应该交付什么”，再决定是否进入子能力，主入口应补读：

- `default-delivery-flow.md`

路由时至少依赖项目画像中的以下信息：

- `当前最适合进入的阶段`
- `当前轮应输出的交付物`
- `当前任务执行主体`
- `当前任务审核主体`
- `当前最大不确定项`

### Step 9：回写结果

主入口本轮结束前，必须将结果写回正确的全局文件类型。

## 6. `solo / 团队协作` 处理规则

主入口必须在早期明确识别：

- 当前是 `solo`
- 还是 `团队协作`

这组判断以项目画像为首要来源。

默认读取来源：

- `协作模式`
- `执行负责人`
- `审核 / 验收负责人`
- `当前任务执行主体`
- `当前任务审核主体`
- `是否要求执行与审核分离`

若项目画像缺失这些信息，才通过最小访谈补齐。
补齐后应回写项目画像，而不是只停留在计划或对话里。

### `solo` 模式

主入口至少要确认：

- 当前执行人是谁
- 当前审核是否仍由同一人承担

默认处理：

- 若画像未明确要求执行与审核分离，则执行主体与审核主体可以同一人
- 任务拆分以阶段和功能为主

### `团队协作` 模式

主入口至少要确认：

- 谁负责业务确认
- 谁负责执行
- 谁负责审核 / 验收
- 是否要求执行与审核分离
- 是否需要按人拆任务

默认处理：

- 项目画像必须记录角色边界
- 后续计划与任务拆分必须带执行主体
- 没有执行主体的任务不能视为有效拆分

---

## 7. 缺失补齐规则

### 7.1 缺少项目画像文件

处理方式：

- 立即触发最小访谈
- 生成默认 `project-profile.md`

### 7.2 缺少全局规则文件

处理方式：

- 进入套件默认规则兜底模式
- 同时标记“规则入口缺失”
- 若宿主项目整体还没有稳定项目骨架，应进一步进入目录结构构建

### 7.3 缺少当前执行计划文件

处理方式：

- 先允许主入口推进到需求 / 方案阶段
- 在进入任务拆解前，建议补齐计划文件
- 若计划文件缺失只是宿主项目骨架整体缺失的一部分，应优先进入目录结构构建

### 7.4 缺少状态回写文件

处理方式：

- 不阻断当前轮推进
- 但本轮结束后应补一个最小状态回写载体
- 若状态回写缺口与计划、规则、资料目录同时缺失，应将其视为宿主项目骨架缺口，而不是单一文件缺口

---

## 8. 回写规则

主入口不应把所有结果都写进同一个文件。

推荐回写规则如下：

### 写回项目画像文件

适合写入：

- 项目目标澄清结果
- 当前阶段变化
- `solo / 团队协作` 变化
- 团队成员与身份识别
- 入口与识别信息补齐结果
- 当前优先级变化
- 待确认项变化
- 当前最适合进入的阶段
- 当前轮应输出的交付物
- 当前任务执行主体 / 审核主体

不应写入：

- 详细任务明细
- 前置依赖明细
- 完整过程日志
- 本轮完整执行记录

### 写回当前执行计划文件

适合写入：

- 当前阶段任务
- 下一步任务
- 完成标准
- 执行主体 / 审核主体

### 写回项目状态回写文件

适合写入：

- 本轮做了什么
- 本轮输出了什么
- 遇到了什么问题
- 下一轮建议做什么

### 不应写回全局规则文件

除非形成稳定、长期有效的新规则，否则主入口不应频繁回写全局规则文件。

---

## 9. 宿主项目映射示例

以当前项目经验为例：

- `docs/ai-rules.md` -> 映射为全局规则文件
- `docs/plans/hajimi-V6.md` -> 映射为当前执行计划文件
- `logs/` -> 映射为项目状态回写文件
- 项目画像文件当前缺失 -> 由套件默认补齐

这说明：

主入口进入当前项目时，不需要重构已有规则体系，只需要：

1. 识别已有权威源
2. 补齐缺失的项目画像层

---

## 10. 对后续子 skill 的要求

后续每个子 skill 都应遵循本运行协议。

至少应写清：

1. 自己在主入口之后的触发条件
2. 自己依赖哪些全局文件
3. 自己的输出应回写到哪一类全局文件

这意味着：

- 子 skill 不直接重定义入口流程
- 子 skill 只消费主入口已经建立好的上下文

---

## 11. 一句话结论

`ai-project-manager` 的运行方式不是“先问问题再随便推进”，而是：

**先识别宿主项目的全局文件角色，再补齐缺失上下文，再判断阶段，再把结果写回正确文件。**
