# Entry Routing Conditions

## 1. 目的

本文件用于明确 `ai-project-manager` 在不同上下文下应如何决定：

- 只补文件
- 继续访谈
- 停留在主入口
- 进入某类子 skill

它解决的问题不是“完整 workflow 长什么样”，而是：

**主入口每一轮到底依据什么做路由决定。**

---

## 2. 判断总原则

主入口路由时遵循以下优先级：

1. 先判断全局文件是否缺失
2. 再判断当前阶段是否足够明确
3. 再判断当前轮是否需要最小交付物
4. 只有在主入口不应继续承载时，才进入子 skill

一句话原则：

**先补骨架，再补内容；先做判断，再做执行。**

当主入口依赖项目画像做路由判断时，应同时遵守字段来源口径：

- 用户确认字段优先承接项目事实与业务意图
- 系统推断字段优先承接入口识别、资产扫描和角色映射结果
- 主入口判断回写字段优先承接阶段判断、当前轮交付物和执行主体结论

因此：

- 不能因为用户确认字段暂缺，就阻断所有推进
- 也不能把本应由主入口判断回写的字段重新转嫁给用户手填
- 真正需要继续访谈的，应优先是影响当前阶段判断或路由判断的关键缺口

---

## 3. 主入口路由条件表

| 当前情况 | 主入口动作 | 是否进入子 skill | 默认输出 |
|---|---|---|---|
| 初始访谈已完成，但宿主项目缺少稳定项目骨架 | 进入宿主项目目录结构构建 | 否 | 已补齐的最小骨架 / 暂缓创建项 |
| 用户明确希望确认项目目录和文件结构 | 进入宿主项目目录结构构建 | 否 | 已创建目录结构 / 分层结果 |
| 缺全局规则文件，但当前轮仍可推进 | 补最小规则入口或标记规则缺失 | 否 | 最小 `project-rules.md` 或缺口标记 |
| 缺项目画像文件 | 先做最小访谈并生成项目画像 | 否 | `project-profile.md` |
| 画像存在，但用户确认字段仍不足以表达项目目标 | 继续停留主入口澄清 | 否 | 更新后的项目画像 + 待确认项 |
| 画像存在，但系统推断字段缺失，导致无法恢复入口或识别上下文 | 主入口优先补入口与识别信息 | 否 | 更新后的项目画像 |
| 当前阶段无法判断 | 主入口继续补最少关键信息 | 否 | 阶段判断所需最小上下文 |
| 当前阶段可初步判断，但主入口判断回写字段尚不足以支撑路由 | 主入口先补阶段结论、交付物或执行主体 | 否 | 更新后的项目画像 |
| 当前阶段已明确为 `S0`，但仍需澄清想法 | 主入口继续推进澄清 | 否 | 项目画像初稿 / 待确认问题列表 |
| 当前阶段已明确为 `S1`，且需要形成需求摘要 | 路由到需求类能力 | 是 | 需求摘要 |
| 当前阶段已明确为 `S1`，但仍只缺少少量上下文 | 主入口先补上下文 | 否 | 更新画像 / 待确认项 |
| 当前阶段已明确为 `S2`，且需要进入任务拆解 | 路由到计划类能力 | 是 | 最小执行计划 / 任务清单 |
| 当前阶段已明确为 `S2`，但执行计划文件缺失 | 先补最小计划载体 | 视情况而定 | `execution-plan.md` |
| 当前阶段已明确为 `S3`，且已有清晰当前任务 | 路由到执行类能力 | 是 | 当前任务输入 |
| 当前阶段已明确为 `S4`，且需要沉淀本轮结果 | 路由到状态 / 验收类能力 | 是 | 验收 / 状态回写 |
| 当前轮已经形成结果，但不需要额外子能力 | 主入口直接回写 | 否 | 更新后的全局文件 |
| 当前轮只有缺口识别，没有形成可执行内容 | 主入口停留并补缺 | 否 | 待确认项 / 下一步建议 |

---

## 4. 只补文件，不进子 skill 的条件

出现以下情况时，默认只补文件，不进入子 skill：

- 初始访谈已完成，但宿主项目缺少稳定项目骨架
- 用户当前轮的目标是先补齐目录和文件骨架，再继续后续阶段
- 项目画像缺失
- 系统推断字段缺失，导致计划入口、状态入口或 PRD 入口无法恢复
- 当前阶段无法判断
- 当前最适合进入的阶段或当前轮交付物尚未形成
- 当前轮只缺少少量关键上下文
- 当前轮的目标只是建立统一项目快照
- 当前轮的主要价值是明确“下一步做什么”，而不是直接执行

这类场景中，主入口本身就是正确承载者。

补充说明：

- 当主入口判断问题已不再是“某个单文件缺失”，而是“宿主项目整体缺少稳定骨架”时，应优先读取 `project-scaffold.md`
- 此时主入口需要先完成对应层级的骨架补齐，再进入后续阶段子能力

---

## 5. 继续访谈，不进子 skill 的条件

出现以下情况时，默认继续访谈：

- 用户确认字段中，项目目标仍无法表达
- 用户确认字段中，目标用户或主要问题仍不清楚
- 用户确认字段中，第一版范围仍不清楚
- 用户确认字段中，协作模式仍不清楚
- 推进已经需要角色边界，但执行主体 / 审核主体仍无法确认

约束：

- 只问当前阶段判断最依赖的问题
- 不一次性深挖所有细节
- 能从文件推断的，不重复追问
- 属于系统推断字段和主入口判断回写字段的，不默认转嫁给用户手填

---

## 6. 进入子 skill 的条件

只有同时满足以下条件，才建议进入子 skill：

1. 当前阶段已经足够明确
2. 主入口已经建立了最小统一上下文
3. 当前轮目标已经超出主入口的“判断与路由”职责
4. 进入子 skill 能带来明确的新交付物

进一步说，至少需要满足：

- 用户确认字段已足以说明当前轮为什么要做这件事
- 系统推断字段已足以恢复入口和必要资料
- 主入口判断回写字段已足以说明当前应进入哪个阶段、当前轮要交付什么、由谁推进

换句话说：

**进入子 skill 不是因为“我们有这个 skill”，而是因为当前轮确实需要它。**

### 6.1 能力名、默认实现与替换原则

为了支持后续能力深化和版本分层，主入口进入子 skill 前，应先完成“能力路由”，再进入“具体实现”。

固定口径如下：

- 路由判断优先命中稳定能力名，不优先命中具体 skill 路径
- `entry-routing-conditions.md` 负责说明“什么情况下需要某类能力”
- `entry-runtime-model.md` 中声明的默认 skill 入口，负责承接“当前默认实现”
- 当宿主项目已有更高优先级入口，或开源版 / 增强版存在不同实现时，可以替换默认实现，但不应改动上层能力名

当前可按以下口径理解：

| 稳定能力名 | 默认实现 | 说明 |
|---|---|---|
| `requirements` | `skills/requirements-starter/` | 承接需求整理与需求成型产出 |
| `solution-design` | `skills/solution-designer/` | 承接方案整理与方案设计产出 |
| `delivery-planning` | `skills/delivery-planner/` | 承接任务拆解、计划整理与研发拆解产出 |
| `engineering-execution` | `skills/engineering-executor/` | 承接开发执行相关产出 |
| `test-acceptance` | `skills/test-and-acceptance/` | 承接测试、验收与补缺相关产出 |
| `project-devlog` | `skills/project-devlog/` | 承接开发日志与状态沉淀相关产出 |
| `coding-standards` | `skills/coding-standards/` | 承接编码、接口、SQL、测试与测试用例文档等任务的规范加载，不直接替代执行类能力 |

其中：

- `coding-standards` 属于辅助能力，不单独代表阶段推进，但在开发类任务中可作为必选补加载能力
- 阶段能力与辅助能力可以同时命中，例如开发执行阶段既进入 `engineering-execution`，也补加载 `coding-standards`
- 后续若增强版为某个能力提供更强实现，应优先替换默认实现映射，而不是在上层规则新增另一套能力名

兼容说明：

- `requirements_writer`、`solution_designer`、`delivery_planner`、`engineering_executor`、`test_acceptance`、`devlog_writer` 仅作为历史命名参考
- 新文档和后续运行规则统一使用稳定能力名，不再以上述旧称作为主口径

### 6.2 规则层能力与阶段能力的边界

稳定能力名并不都在同一层承载。

主入口运行时，应先区分：

- 哪些能力属于规则层需要长期声明的“强约束性辅助能力”
- 哪些能力属于 runtime 按阶段判断并加载的“阶段能力”

当前固定口径如下：

#### 规则层长期声明的强约束性辅助能力

- `coding-standards`

这类能力的特点是：

- 不单独代表阶段推进
- 主要作用是提供规范约束、质量门禁或执行校准
- 一旦命中相关任务类型，应作为长期有效规则被补加载

因此，这类能力适合在 `project-rules.md` 中声明“不得跳过”，但不在规则层中维护其具体阶段路由和实现细节。

#### runtime 按阶段判断并加载的阶段能力

- `requirements`
- `solution-design`
- `delivery-planning`
- `engineering-execution`
- `test-acceptance`
- `project-devlog`

这类能力的特点是：

- 代表当前轮的主承接能力
- 与阶段推进和当前轮主交付物直接绑定
- 是否命中、何时命中，应由主入口结合当前阶段、缺口和交付物在 runtime 中判断

因此，这类能力不在 `project-rules.md` 中逐项写成长期路由结论，而由本文件和 `entry-runtime-model.md` 共同承接“当前为何进入该能力”的判断。

一句话边界：

- `project-rules.md` 负责声明“哪些辅助能力不能跳过”
- runtime 负责判断“当前阶段由哪个阶段能力主承接”

## 7. 各阶段默认路由

### `S0` 想法澄清

默认由主入口继续承载。

当前轮输出优先是：

- 项目画像初稿
- 待确认问题清单

此阶段优先补：

- 用户确认字段中的项目目标、主要问题、第一版核心目标
- 主入口判断回写字段中的当前最适合进入的阶段

### `S1` 方案前置 / 需求成型

默认优先进入：

- `requirements`

前提：

- 业务目标、目标用户、第一版范围已基本可表达
- 当前轮应输出的交付物已能由主入口判断并写回项目画像
- 当前默认实现：`skills/requirements-starter/`

### `S2` 研发拆解

默认优先进入：

- `delivery-planning`

前提：

- 需求范围已稳定
- 已能描述当前阶段任务与完成标准
- 当前任务执行主体 / 审核主体已足以支撑后续拆解
- 当前默认实现：`skills/delivery-planner/`

### `S3` 开发执行

默认优先进入：

- `engineering-execution`

前提：

- 当前任务清晰
- 执行主体清晰
- 当前最适合进入的阶段和当前轮交付物已不再停留在待确认
- 当前默认实现：`skills/engineering-executor/`
- 若当前任务涉及代码编写、代码修改、重构、接口设计、SQL 变更、自动化测试或测试用例文档维护，还应补加载 `coding-standards`

### `S4` 验收收口

默认优先进入：

- `test-acceptance`
- `project-devlog`

前提：

- 已有可验证结果
- 当前重点是验证、补缺或沉淀状态
- 主入口已能明确当前轮结果应沉淀到状态或验收文件
- 当前默认实现：
  - `test-acceptance` -> `skills/test-and-acceptance/`
  - `project-devlog` -> `skills/project-devlog/`

---

## 8. 渐进式披露约束

为了避免主入口过早膨胀，路由时必须遵守：

- 不因为存在某个 skill 就默认调用
- 不因为某个阶段理论上存在就提前展开其细节
- 不因为要追求完整度就一次性补所有全局文件
- 不因为用户说“我想做项目”就立即进入需求 / 方案 / 开发能力

---

## 9. 一句话结论

主入口路由的本质不是“把用户分发给 skill”，而是：

**先建立可持续推进的最小项目骨架，再在必要时把工作交给正确能力。**
