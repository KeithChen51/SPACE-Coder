## 1. 目的

本文件定义 `project-manager-suite` 使用的“项目全局文件模型”。

这里讨论的不是某个具体项目现有文件名，而是一组在任何项目中都应存在的**全局文件角色**。这些文件角色为套件中的主入口和各基础子 skill 提供共同输入。

本文件的目标是统一回答 5 个问题：

1. 什么叫“项目全局文件”
2. 项目全局文件分哪几类
3. 每一类文件负责什么，不负责什么
4. 四类文件之间是什么关系
5. 这套模型对子 skill 的约束是什么

配套协议与默认模板见：

- `docs/design/global-files-architecture.md`
- `global-files-minimum-shared-protocol.md`
- `global-files-readwrite-protocol.md`
- `skills/ai-project-manager/assets/global-files/project-rules.md`
- `skills/ai-project-manager/assets/global-files/project-profile.md`
- `skills/ai-project-manager/assets/global-files/execution-plan.md`
- `skills/ai-project-manager/assets/global-files/project-status.md`

## 2. 定义

项目全局文件，指的是：

**对整个项目都成立，并会被多个任务、多个 skill、多个阶段反复读取的顶层上下文文件。**

它和普通任务文件的区别在于：

- 普通任务文件只服务某一个局部任务
- 项目全局文件服务的是整个项目的持续推进

项目全局文件不要求必须使用固定文件名，但必须具备固定职责。

### 2.1 产品目标约束

这 4 类全局文件的定义，不是从传统项目管理文档清单倒推出来的，而是从 `project-manager-suite` 的产品目标倒推出来的。

当前产品目标要求这套模型必须做到：

- 帮业务方把想法整理清楚
- 让项目经理模型推动项目持续往前走
- 让开源版具备最小可用闭环
- 为增强版保留判断力和经验层
- 在不同 AI IDE 中仍然可复用、可移植

因此，全局文件模型必须满足以下约束：

1. 对业务方友好
   - 字段设计应少而关键
   - 文件职责应直观，不依赖复杂研发术语

2. 对主入口可读
   - 主入口必须能从这些文件中判断阶段、缺口、执行主体和下一步动作

3. 对持续推进有支撑
   - 文件体系必须覆盖“怎么运行 / 当前是什么 / 现在做什么 / 最近发生了什么”

4. 对分层商业化有边界
   - 公开版文件模板只承载基础上下文和基础闭环
   - 增强 heuristics、复杂追问逻辑、高级判断规则不直接写进公开文件模板

5. 对跨工具复用有支撑
   - 关键能力应优先沉淀在仓库文件、模板和协议中
   - 不应把核心运行依赖绑定在单一 AI IDE 的私有能力上

也就是说：

**全局文件模型首先是产品骨架，其次才是文档模型。**

## 3. 四类全局文件

`project-manager-suite` 默认将项目全局文件划分为 4 类。

### 3.1 项目画像文件

作用：

- 描述项目当前最重要的统一上下文

负责：

- 项目目标
- 目标用户
- 第一版范围
- 当前阶段
- 当前优先级
- `solo / 团队协作`
- 团队成员与身份识别
- 当前执行主体 / 审核主体
- 待确认项

不负责：

- 长期规则定义
- 详细任务排期
- 开发日志过程记录

统一公共文件名：

- `project-profile.md`

这是当前很多项目最缺的一类文件，也是 `ai-project-manager` 最优先依赖的全局文件。

### 3.2 全局规则文件

作用：

- 定义项目长期有效的工作规则

负责：

- 命名规范
- 文档入口
- 技术边界
- 协作边界
- 权威源约定
- 必须遵守的流程
- 技能 / workflow 使用原则

不负责：

- 当前阶段任务清单
- 当前项目优先级快照
- 最近一轮推进状态

统一公共文件名：

- `project-rules.md`

### 3.3 当前执行计划文件

作用：

- 定义当前阶段具体做什么

负责：

- 当前做到哪
- 下一步做什么
- 当前阶段任务清单
- 每项任务完成标准
- 任务前后依赖关系

不负责：

- 项目长期规则
- 团队基础画像
- 长期状态回写沉淀

统一公共文件名：

- `execution-plan.md`

### 3.4 项目状态回写文件

作用：

- 记录推进结果与状态变化

负责：

- 开发日志
- 验收记录
- 方案变更记录
- 决策记录
- 当前阶段总结

不负责：

- 项目基础画像定义
- 长期规则定义
- 全量任务计划定义

统一公共文件名：

- `project-status.md`

补充说明：

- `logs/` 可作为详细过程日志目录存在，但不替代公共状态文件名

## 4. 四类文件的关系

推荐关系如下：

```text
全局规则文件
    ↓ 约束
项目画像文件
    ↓ 提供当前项目上下文
当前执行计划文件
    ↓ 推进具体阶段任务
项目状态回写文件
    ↓ 记录推进结果并反馈给项目画像与计划
```

补充说明：

- 全局规则文件决定项目“如何运行”
- 项目画像文件决定项目“当前是什么”
- 当前执行计划文件决定项目“现在做什么”
- 项目状态回写文件决定项目“最近发生了什么”

这 4 类文件可以互相引用，但不应相互吞并职责。

## 7. 当前建议

对于 `project-manager-suite`：

- 应优先把“项目画像文件”明确成套件默认能力的一部分
- 应把 4 类全局文件模板视为主入口的默认路由骨架
- 应用 `global-files-readwrite-protocol.md` 约束后续主入口和子 skill 的读写行为
- 应在后续子 skill 设计中持续沿用本文件的 4 类模型

---

## 8. 一句话结论

`project-manager-suite` 复用的不是某个项目的固定文件名，而是：

**项目全局文件的角色模型。**

这个角色模型至少包括：

- 全局规则文件
- 项目画像文件
- 当前执行计划文件
- 项目状态回写文件
