# Global Files Starter Pack

`global-files/` 是 `project-manager-suite` 开源版优先交付的项目骨架。

它不依赖具体子 skill 是否已经补齐，也不要求用户先理解完整能力树。

它与 `references/` 中运行时文档的分工是固定的：

- `references/` 中的运行时文档负责定义全局文件模型、最小字段合同和读写协议
- `global-files/` 只负责提供默认模板骨架
- `global-files/` 不重复维护运行时规范文本

它只解决一件事：

**给任何新项目提供一套最小、稳定、可持续读写的全局文件体系。**

---

## 包含内容

当前 starter pack 包含 4 类全局文件的默认载体：

- `project-rules.md`
- `project-profile.md`
- `execution-plan.md`
- `project-status.md`

这 4 个文件分别回答：

1. 项目怎么运行
2. 项目当前是什么
3. 现在做什么
4. 最近发生了什么

其中前两类文件的边界应特别明确：

- `project-rules.md`
  - 只承载长期有效的运行规则、结构约束、协作原则、交付底线
  - 不承载当前项目的具体负责人、当前执行主体、当前审核主体等项目事实

- `project-profile.md`
  - 承载当前项目快照，包括协作模式、当前业务确认主体、当前执行主体、当前审核主体、待确认项
  - 不承载长期运行规则，也不承载详细任务清单或完整日志

---

## 什么时候初始化

满足以下任一情况时，应优先初始化这套骨架：

- 新项目启动，还没有稳定的项目上下文文件
- 宿主项目虽然已有零散文档，但没有统一权威入口
- 希望让 AI 输出从“聊天临时记忆”转成“仓库内可持续上下文”

如果宿主项目已有现成文件，不必强行替换，可先做角色映射。

---

## 最小使用顺序

建议顺序：

1. 先补 `project-profile.md`
2. 再确认 `project-rules.md`
3. 进入推进阶段后维护 `execution-plan.md`
4. 每轮结束回写 `project-status.md`

其中：

- `project-profile.md` 是启动阶段最关键的文件
- `execution-plan.md` 不必在项目最初就写得很完整
- `project-status.md` 必须在每轮推进后更新

---

## 与主入口的关系

`ai-project-manager` 应围绕这 4 个文件工作：

- 先识别是否已存在
- 再读取最小必要上下文
- 再判断当前阶段与缺口
- 再决定是否进入某个子能力
- 最后将结果回写到对应文件

因此，这套 starter pack 是主入口的运行骨架，不是附属模板集合。

---

## 对外交付建议

开源版第一批交付时，建议优先保证：

- 这 4 个文件模板可直接复制使用
- 文档明确每个文件的职责与边界
- 至少有一个真实项目示例能跑通初始化和回写

如果这几点还没成立，就不要宣称“完整开箱即用”。
