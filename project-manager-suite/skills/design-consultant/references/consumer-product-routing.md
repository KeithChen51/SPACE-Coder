# C 端产品设计路由

这份路由用于识别面向普通用户的产品属于哪一类设计问题，并据此加载页面模板、增长模式和体验约束。它不是行业模板库，也不覆盖已有项目事实：如果项目已经有 Token、共享组件、主题机制或明确的品牌规范，先执行既有设计系统审计，再在 `preserve / augment / migrate` 结论内使用本路由。

## 选择规则

1. 根据核心用户任务选择一个主类型；不要按公司所属行业或页面外观判断。
2. 只有当另一类任务真实存在于主流程中时，才添加次级叠加类型，最多两个。
3. 后台管理、运营配置和内部数据工作台继续走后台与数据密集型设计路线，不因同一项目包含 C 端页面而套用本路由。
4. 类型只决定应检查什么，不直接决定视觉风格。品牌表达、默认基线和既有系统分别按其原有门禁处理。

## 叠加和冲突处理

- 主类型定义核心旅程、默认导航和必须交付的页面族；次级类型只补充局部规则，不重写主流程。
- 电商加订阅时，结算仍遵守电商交易完整性，订阅叠加周期、续费和取消规则。
- 内容加社区时，内容消费仍是主任务，社区叠加发布范围、治理和关系安全规则。
- 健康或金融只要作为次级类型出现，其安全、证据和不可逆操作约束仍具有最高优先级。
- 当类型规则与真实业务、法律要求或已确认设计系统冲突时，记录冲突并请求确认，不自行覆盖项目事实。

完成类型选择后，读取 `consumer-product-manifest.json` 获得稳定 ID 和关联项，再按需加载 `consumer-page-templates.md`、`growth-conversion-patterns.md` 与 `consumer-ux-contract.md`。正式产物仍由当前阶段负责人维护。
