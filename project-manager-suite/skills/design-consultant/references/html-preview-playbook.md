# HTML 预览决策与生成规则

HTML 预览用于对齐理解，不是每次设计建议都要做。

它是 `preview_decision`，不是和 `default/customize/design-system/review` 平级的主模式。只有当预览能明显降低沟通成本、比较方案风险或验证复杂状态时，才主动询问用户。

## 何时主动询问

当出现以下情况，向用户询问是否生成 HTML 预览：

- 页面布局、导航结构、信息架构较复杂。
- 需要比较两个以上方案。
- 涉及视觉风格、组件样式、动效、响应式。
- 包含多状态：加载、空、错误、成功、权限不足。
- 文字说明不足以让用户判断成本或效果。
- 用户处在产品定义阶段，还没进入代码实现。

成本门槛：

- 能帮助用户在 10 分钟内判断方向。
- 能减少后续返工或争论。
- 预览范围能控制在单页、单流程或组件族。
- 不会伪装成正式代码交付。

询问模板：

```text
这里建议做一个单文件 HTML 预览，因为需要对齐[布局/状态/方案比较]。要我先做预览，还是先继续文字方案？我会重点展示页面结构、关键组件和主要状态，不会写进正式项目代码。
```

## 何时不要问

- 只是改文案。
- 只是解释交互原则。
- 只是轻量代码修复。
- 用户明确说先不要视觉稿。
- 已有成熟设计文件，当前只需要实现。
- 预览会比直接给判断更耗时，且不会降低风险。

## 预览内容要求

单文件 HTML 至少展示：

1. 页面主结构。
2. 核心组件。
3. 关键状态。
4. 响应式断点。
5. 使用的 token：颜色、字体、间距、圆角。

对后台/数据产品：

- 展示导航、筛选、表格、详情、空状态、错误状态。
- 不做营销化 hero。

对营销页/展示页：

- 展示首屏、价值说明、关键证据、行动入口。
- 不使用假 logo wall 或无意义装饰。

对设计系统预览：

- 展示按钮、输入框、表格、卡片、状态色、弹窗或抽屉。
- 展示 light/dark 或说明为什么暂不做暗色。

## 交付边界

- 预览不等于正式实现。
- 默认生成本地单文件 HTML。
- 不引入远程依赖，除非用户允许。
- 不静默使用第三方图片或字体。
- 如果需要品牌素材，先列出需要的文件。
