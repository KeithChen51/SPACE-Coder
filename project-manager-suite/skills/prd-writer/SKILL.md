# prd-writer

面向 AI 编程的 PRD（产品需求文档）撰写方法论。产出的 PRD 不是给人看的传统产品文档，而是 **AI 拿到后能直接编码的基准规格文件**。

## 页面确认后反推 PRD

当项目处于“先页面、后 PRD”的推进模式时，`prd-writer` 承担以下职责：

- 读取已确认的页面原型、页面代码和需求摘要
- 从页面结构、模块边界、交互流程和字段展示反推完整 PRD
- 将页面中已经稳定下来的信息沉淀为 AI 可直接编码的规格文档

在这种模式下，`prd-writer` 的前置条件是：

- 页面原型已经产出
- 页面原型已经获得人工确认
- 需要把确认后的页面固化为完整 PRD

禁止：

- 页面原型未确认前直接产出权威 PRD
- 脱离页面原型凭空扩写 PRD
- 把低保真想法稿或纯文字模块清单当作页面确认输入

体系分五层：
- **主文档**：建立全局语境（产品定位、架构、术语、数据全景、设计修正）
- **子文档**：按功能区块展开（每个区块一份，字段级可追溯，严格边界控制）
- **全局应用文档**：跨区块共享的基础设施定义（数据库表结构、术语表、接口总览），所有子 PRD 引用而非重复定义
  - **数据库 Schema**：全系统表结构唯一权威源，子 PRD 数据链路表引用它
  - **术语表**：全系统名词定义唯一权威源，统一前后端和文档用语
  - **接口总览**：全系统 HTTP 接口唯一总览，子 PRD 接口契约引用它
- **版本管理**：基线版本清单（`prd-baseline.md`）+ 变更日志（`prd-changelog.md`）+ 每篇 PRD 的机器可读元信息头

## Prerequisites

撰写前需建立对项目的全面理解。根据当前阶段，读取不同范围的材料：

### 写主文档时（从零开始）

主文档是第一份产出，此时没有 PRD 可读，需要从代码和原始文档中提炼：

| 必读材料 | 目的 |
|----------|------|
| 数据库表结构（schema / DDL / 初始化 SQL） | 理解数据全景 |
| AI 编程规则文件（如有） | 了解技术栈、术语、编码规范 |
| 旧需求文档 / PRD（如有） | 理解产品设计意图（不照搬） |
| 前后端核心代码 | 理解实际实现（与设计意图做对比） |

### 写子文档时（主文档已存在）

| 必读材料 | 目的 |
|----------|------|
| 主文档 | 确认区块边界、术语、架构原则 |
| 全局应用文档（如 database-schema、术语表） | 引用表结构和术语定义，确保数据链路表的表.字段引用准确 |
| 该区块涉及的前端组件 / composables / adapters | 理解 UI 和数据流 |
| 该区块涉及的服务端 Controller / Service / Entity | 理解接口和业务逻辑 |
| 该区块涉及的管理台页面（如有） | 理解配置能力 |
| 已完成的其他子文档（如有） | 避免边界重叠 |

### 写全局应用文档时（如数据库表结构）

| 必读材料 | 目的 |
|----------|------|
| 主文档 | 理解系统架构和数据全景 |
| 数据库 schema（DDL / migration / ORM 定义 / 初始化 SQL） | 获取完整表清单和字段定义 |
| 所有已完成的子 PRD | 梳理每张表被哪些接口使用 |
| AI 编程规则文件（如有） | 确认术语和技术栈约定 |

### 写 API 接口总览文档时

| 必读材料 | 目的 |
|----------|------|
| 主文档（附录 A 接口清单） | 获取完整接口列表和归属 PRD |
| 数据库表结构文档 | 确认接口读写的表，校验映射关系 |
| 所有已完成的子 PRD（接口契约章节） | 提取每个接口的请求/响应定义和业务规则 |
| 服务端 Controller + Service 代码 | 验证接口实际实现，识别计算链路和现状差异 |
| 管理台页面组件 + API 调用 | 梳理管理台接口的配置能力和存储模式 |

### 材料不足时怎么办

不是所有项目都有完整的历史文档和代码。根据缺失程度采取不同策略：

| 缺失情况 | 策略 |
|----------|------|
| **无旧 PRD / 需求文档** | 向用户提问提炼产品意图：产品解决什么问题？用户是谁？核心场景有哪些？与竞品区别？ |
| **无代码（全新项目）** | 主文档的"差距分析"章节留空或标注"首版设计，无历史实现"；子文档无需写 `> 现状差异` 标注 |
| **无数据库设计** | 根据用户描述的业务实体，在主文档中先设计表结构草案，标注"待确认" |
| **用户口述需求为主** | 多轮提问逐步明确：先确认产品定位 → 再确认页面结构 → 再确认每个区块的数据和交互 |

**核心原则**：材料不足时，用提问代替假设。宁可多问一轮，不要凭猜测填充 PRD。

## How to Use This Skill

### 场景 A：从零建立 PRD 体系

当项目没有 PRD 或需要重写时，按以下顺序执行：

```
Step 1 → 深度研究（代码 + 旧文档 + 数据库）
Step 2 → 撰写主文档
Step 3 → 逐个撰写子文档（从最简单的区块开始）
Step 4 → 交叉验证（链路追溯 + 接口可实现性）
```

### 场景 B：新增/修改单个子文档

当主文档已存在，只需写某个区块的子 PRD 时：

```
Step 1 → 读主文档，确认区块边界
Step 2 → 深度阅读该区块涉及的全部代码
Step 3 → 按子文档模板撰写
Step 4 → 边界自检 + 交付审阅
```

### 场景 C：撰写数据库表结构文档

当需要建立或更新全系统的数据库表结构定义时：

```
Step 1 → 读主文档 + 所有已完成子 PRD，梳理表的使用关系
Step 2 → 查看实际数据库 schema（DDL / migration / ORM 定义）
Step 3 → 按数据源分组，逐表填写字段定义
Step 4 → 交叉验证（表↔接口↔子PRD 链路完整性）
```

### 场景 D：撰写 API 接口总览文档

当需要建立或更新全系统的 HTTP 接口总览时：

```
Step 1 → 读主文档附录 A + 所有子 PRD 的接口契约章节，汇总完整接口清单
Step 2 → 读数据库表结构文档 + 服务端代码，梳理每个接口的数据流
Step 3 → 按 C端/管理台配置类/管理台数据管理类 分组，逐接口撰写契约
Step 4 → 建立接口↔数据表映射 + 调用时序图，交叉验证完整性
```

## Part B：子文档撰写

子文档是功能区块的**详细规格**，AI 读完后能直接写代码。每份子文档只管自己的区块，严格不越界。

## Part D：API 接口总览文档撰写

API 接口总览文档是全系统 HTTP 接口的**唯一集中定义**。子 PRD 的接口契约章节只写该区块调用的接口片段并引用本文档，本文档给出每个接口的完整契约（请求参数 → 响应字段 → 响应示例 → 计算链路）。

模板包含全接口总览表、三类 C 端接口写法（简单直透 / 聚合计算 / 外部接口）、两种管理台模式（固定行 GET+PUT / 可变行 CRUD）、接口↔数据表映射、调用时序图规范、现状差异快速索引（内联标注 + §7 索引）：

```
读取 → .agent/skills/prd-writer/templates/api-prd.md
读取 → .agent/skills/prd-writer/references/anti-patterns.md（动笔前必读）
```

**与其他文档的关系**：

| 文档 | 关系 |
|------|------|
| 主文档附录 A | 附录 A 是接口摘要索引，本文档是完整定义。两者保持一致，冲突时以本文档为准 |
| 数据库 Schema 文档 | 本文档的"接口↔数据表映射"与 Schema 文档的"使用接口"互为校验 |
| 子 PRD 接口契约 | **双向链接**：子 PRD 接口契约引用本文档（正向），本文档每个接口用 `引用 PRD` 行反向指向定义其业务规则的子 PRD。字段定义以本文档为准 |

## Part E：版本管理

PRD 体系使用**基线版本管理**，通过 `prd-baseline.md` 统一管控全部 PRD 的生效版本。

### 机器可读元信息

每篇 PRD 文件第一行必须包含 HTML 注释格式的元信息：

```markdown
<!-- @meta docId="prd-2b" status="active" baseline="v1.0.0" -->
```

| 字段 | 说明 | 可选值 |
|------|------|--------|
| `docId` | 文档唯一标识 | 见 `prd-baseline.md` 的 docId 列 |
| `status` | 文档状态 | `active`（生效）/ `deprecated`（废弃）/ `draft`（草稿） |
| `baseline` | 所属基线版本 | 如 `v1.0.0`、`v1.1.0` |

### 文档头部格式

元信息行之后，blockquote 头部必须包含基线版本：

```markdown
> **基线版本**: v1.0.0 | **最后更新**: 2026-02-27
```

### 每次 PRD 变更的版本管理流程

1. **修改 PRD 文档**：更新内容 + 更新头部 `baseline` 和 `最后更新` 日期
2. **更新 `<!-- @meta -->` 行**：同步 `baseline` 字段
3. **追加 changelog**：在 `prd-changelog.md` 顶部追加版本条目
4. **更新 baseline**：修改 `prd-baseline.md` 的「当前基线」版本号 + 追加「基线历史」行

### Changelog 条目格式

```markdown
## [vX.Y.Z] — YYYY-MM-DD — 简要主题

> **Git Tag**: `prd-vX.Y.Z`

### 新增
- 新文件或新功能描述

### 变更
- 修改的文件和内容

### 修复
- 修正的错误
```

### 版本号判定

| 变更类型 | 版本级别 | 示例 |
|---------|---------|------|
| 新增/删除 API 接口 | MAJOR | 新增 `GET /api/points` |
| 修改表结构（加删字段） | MAJOR | `order_benefit` 新增 `priority` 字段 |
| 修改核心业务规则 | MAJOR | 徽章触发条件从 2 次改为 3 次 |
| 新增功能区块 | MINOR | 新增「积分权益区」PRD |
| 扩展配置项（不破坏现有） | MINOR | 按钮策略新增一种跳转类型 |
| 文案澄清 / 错别字 | PATCH | 修正描述措辞 |
| 章节号重编 / 引用修正 | PATCH | §3.4→§3.5 |

## Part F：通用规则

### 跨文档引用

PRD 中所有对其他文档、章节、表结构的引用，必须使用 **Markdown 超链接**，禁止纯文本引用。

| 场景 | 错误写法 | 正确写法 |
|------|---------|---------|
| 引用其他 PRD | `见 prd-区块2-保养卡片区.md §4.5` | `见 [prd-区块2-保养卡片区 §4.5](prd-区块2-保养卡片区.md)` |
| 引用表结构 | `详见 prd-全局应用-database-schema §3.1` | `详见 [prd-全局应用-database-schema §3.1](prd-全局应用-database-schema.md)` |
| 关联文档头 | `关联文档: prd-主文档.md` | `关联文档: [prd-主文档.md](prd-主文档.md)` |
| 拆分引用 | `已拆分 → 见 prd-区块3-养护档案区-标签体系.md` | `已拆分 → 见 [prd-区块3-养护档案区-标签体系](prd-区块3-养护档案区-标签体系.md)` |
| API 引用 PRD | `引用 PRD：prd-区块2-保养卡片区.md` | `**引用 PRD**：[prd-区块2-保养卡片区](prd-区块2-保养卡片区.md)` |

**原则**：读者在任何 Markdown 渲染器中点击即可跳转到引用位置，零查找成本。

---

### 现状差异标注

PRD 主体写**目标态**（权威规格）。现状偏差用引用块标注：

```markdown
> **现状差异**：[当前实现是什么，关键代码文件路径]。
> 需要：[简述改动方向]。
```

三种情况：

| 情况 | PRD 中怎么写 |
|------|------------|
| 已实现且正确 | 只写目标态，不加标注 |
| 已实现但有偏差 | 目标态 + `> 现状差异` |
| 完全未实现 | 目标态 + `> 现状差异：当前无此实现` |

**时效性声明**（每份 PRD 头部必须包含）：

```markdown
> ⚠️ **现状差异时效性声明**：本文档中的「现状差异」描述基于撰写时的代码快照，
> 随开发推进可能已过时。AI 开发时应**以真实代码为准**，对比代码现状与本文档的
> **目标态需求**，自行判断差异并决定实现路径。
```

**AI 开发者使用指南**：
- PRD 的**目标态描述**是权威规格，始终有效
- PRD 的**现状差异**仅为参考快照，可能已过时
- 开发时应：读目标态需求 → 检查真实代码 → 自行判断 gap → 决定实现路径

**禁止内容**：现状差异只描述产品层面偏差，不涉及：
- 响应码格式（如 `code: 200` vs `code: 0`）
- 代码风格 / 命名规范
- 框架版本 / 依赖选择

### 术语规范

撰写时必须遵守主文档名词定义表。以下是常见易错映射：

| 错误用法 | 正确用法 | 说明 |
|----------|----------|------|
| 后端、配置端 | 服务端 | 避免与"管理台"混淆 |
| 后台 | 管理台 | "后台"歧义太大 |
| 权益、进店权益 | 增值权益 | 明确是"增值"性质 |
| 保养周期 | 保养周期窗口 | "周期"是间隔，"窗口"是提醒范围 |
| 价值标签 | 服务价值标签 | 强调"服务价值" |
| 时间节点 | 服务过程节点 | 不只是时间，还有状态 |

### 文件命名

```
docs/PRD/prd-主文档.md                          ← 主文档
docs/PRD/prd-区块{N}-{区块名}.md                 ← 子文档（N 从 1 开始）
docs/PRD/prd-区块{N}-{区块名}-{子模块名}.md       ← 拆分子文档
docs/PRD/prd-全局应用-{主题}.md                   ← 全局应用文档（跨区块共享）
docs/PRD/prd-管理台-{主题}.md                     ← 管理台专项文档
```

示例：
- `prd-区块1-车辆选择区.md`、`prd-区块2-保养卡片区.md`
- `prd-区块2-保养卡片区-徽章.md`（从区块 2 拆出的子模块）
- `prd-全局应用-database-schema.md`、`prd-全局应用-术语表.md`

## Pre-Delivery Checklist

### 主文档检查

- [ ] 产品定位能通过"3 秒理解"测试
- [ ] 三端架构图清晰展示数据流向
- [ ] 名词定义表覆盖所有专业术语，每个标注作用域
- [ ] 时序图中所有接口格式统一（`GET /api/xxx`），无中文描述混入
- [ ] 差距分析每条都有：设计意图 → 实际实现 → 问题 → 修正
- [ ] 差距分析不含纯开发问题
- [ ] 子 PRD 大纲与实际子文档章节一致
- [ ] 设计修正汇总完整（新接口 + 新表 + 修改项）
- [ ] 附录 A 覆盖所有 C 端 + 管理台接口，每个标注归属子 PRD
- [ ] 附录 B 覆盖所有数据表，新建表有完整 schema
- [ ] 全文无自相矛盾（前文确认的结论，后文不推翻）

### 数据库表结构文档检查

- [ ] §1 总览表覆盖所有表，每行都能跳转到对应章节
- [ ] 每个分组内所有表的数据写入方完全一致，无混合
- [ ] 不同外部系统的表分在不同分组（如外部系统 A ≠ 外部系统 B）
- [ ] 服务端自管的表（聚合/缓存/日志）与外部数据源分开
- [ ] 每张表都有状态行（已有/新建/变更）+ 引用超链
- [ ] 所有标"变更"的表都有变更说明 + 字段表格中有增删标记
- [ ] 字段类型用 MySQL 写法，默认值精确到实际值
- [ ] 枚举型字段的"说明"列穷举了所有合法值（如"订单状态（进行中 / 已完成 / 已取消）"），无模糊描述
- [ ] 固定行数的配置表审查了 isActive 类字段的必要性
- [ ] 每张表都有"使用接口"部分，格式为 `路径 — 角色（见 [超链]）`
- [ ] 使用接口中的 PRD 引用与实际子 PRD 章节对应

## Tips

1. **先简后繁** — 从最简单的区块开始写第一份子 PRD，建立模板范式后再写复杂区块
2. **写完回头对** — 每写完一份子 PRD，回主文档同步更新大纲章节
3. **一个字段一条线** — 数据链路表不要合并行，每个 UI 元素单独一行
4. **用户反馈是金** — 用户指出的边界问题，立刻补充到反模式参考文件
5. **ASCII 图胜千言** — 布局用 ASCII 图，流程用 mermaid，比文字描述清晰 10 倍
6. **管理页跟着数据走** — 管理页展示的数据属于哪个区块，管理页就放在哪个 PRD
7. **改一处同步多处** — 修改任何 PRD 文档的章节号、路由、接口路径、表名等结构性信息时，必须全局搜索所有引用该信息的关联文档并同步更新。重点关注：主文档大纲、DB Schema 交叉引用、API 总览、管理台菜单总览
8. **先读 baseline 再动笔** — 每次修改 PRD 前先读 `prd-baseline.md` 确认当前基线版本，改完后更新版本号、changelog、baseline 三处
