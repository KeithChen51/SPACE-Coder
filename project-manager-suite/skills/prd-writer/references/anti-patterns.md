# PRD 撰写反模式与边界规则

本文档收录 PRD 撰写过程中**实际发生过的错误**，每条附正确做法。撰写和审阅 PRD 时逐条对照。

---

## 1. 字段越界

**反模式**：在本区块的数据字段表或接口响应中，包含了不属于本区块的字段。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| 车辆选择区的 `GET /api/vehicles` 响应包含 `maintenanceCount` | 保养次数是保养卡片区的概念 | 响应只含车辆基础字段（plate/model/vin/svgColor） |
| 车辆选择区的数据字段表包含 `powerType` | 动力类型由 `basic-info` 使用，属于保养卡片区 | 数据字段表只列本区块查询时用到的字段 |
| 车辆选择区列出完整 `vehicle_cache` 表（含 mileage, lastMaintenanceDate 等） | 里程/保养日期是保养卡片区概念 | 只列本区块使用的 7 个字段，注明"完整表见 PRD 2" |

**判断标准**：这个字段如果消失了，本区块的 UI 会受影响吗？如果不会，就不该出现在这里。

---

## 2. 接口越界

**反模式**：在本区块的接口契约章节中，描述了不属于本区块的接口。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| 车辆选择区的接口章节包含 `/api/basic-info` | basic-info 是保养卡片区的接口 | 接口章节只含 `GET /api/vehicles` |
| 车辆选择区描述了管理台 Admin API | 车辆选择区不涉及管理台操作 | 不包含 Admin API |

**判断标准**：本区块的前端代码会直接调用这个接口吗？如果不会，就不该出现在这里。

---

## 3. 管理页越界

**反模式**：把展示其他区块数据的管理页放在了本 PRD。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| 车辆选择区 PRD 包含"车辆缓存数据页"（展示徽章、状态、保养次数） | 徽章/状态/保养次数都是保养卡片区概念 | 移到保养卡片区 PRD |
| 车辆选择区 PRD 包含"同步状态页"（展示外部系统连通性） | 同步的是保养/工单等数据 | 移到保养卡片区 PRD |

**判断标准**：管理页展示的数据主要属于哪个区块，管理页就放在哪个 PRD。

---

## 4. 跨 PRD 引用过细

**反模式**：引用其他 PRD 时使用了具体章节号。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| `见 PRD 2 §11` | 章节号会随修改变化，引用会失效 | `见 PRD 2` |
| 布局图标注 `← PRD 2 §11，仅维保中显示` | 对其他 PRD 的内部结构做了假设 | 只保留区域名称，不标注其他 PRD 章节 |

**正确的跨 PRD 引用**：
```markdown
> `vehicle_cache` 表的完整字段定义（含保养、里程等）见 PRD 2。
```

---

## 5. 布局图过度标注

**反模式**：在页面布局图中为不属于本区块的区域添加详细说明。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| `│ C. 远程视频监控 │ ← PRD 2 §11，仅维保中显示` | 本文档不需要解释远程视频的显示条件 | `│ C. 远程视频监控（条件展示） │` |
| 把其他区域的数据源标注在布局图中 | 超出本文档范围 | 只标注本文档覆盖区域的指向 |

**正确做法**：布局图中，本区块标 `← 本文档 §X-§Y`，其他区块只保留名称。

---

## 6. 现状差异含开发细节

**反模式**：在 `> 现状差异` 标注中包含纯开发层面的问题。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| `> 现状差异：响应码改为 code: 0` | 响应码是开发约定，不是产品规格 | 删除此条 |
| `> 现状差异：变量命名不规范` | 代码风格不是 PRD 关注的 | 删除此条 |
| `> 现状差异：应使用 MyBatis Plus 而非原生 SQL` | 技术选型不是 PRD 关注的 | 删除此条 |

**判断标准**：如果这个差异对用户行为或运营配置没有影响，就不该出现在 PRD 中。

---

## 7. 验收项越界

**反模式**：在本区块的验收标准中，验收了其他区块的行为。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| 车辆选择区验收"切换车辆后保养状态正确刷新" | "保养状态正确"是保养卡片区的职责 | 车辆选择区只验收"切换后触发全页数据刷新（骨架屏）" |
| 车辆选择区验收"管理台缓存数据页展示正确" | 缓存数据页不属于本区块 | 删除此验收项 |

**判断标准**：验收项描述的预期结果，是否100%由本区块代码控制？如果依赖其他区块的实现，就不该出现在这里。

---

## 8. 修正过度

**反模式**：用户要求修改某个具体问题时，顺手修改了更大范围的内容。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| 用户说"把跨 PRD 引用去掉"，直接删除了整个布局图章节 | 用户只想去掉引用，不是删除布局图 | 只删除布局图中的跨 PRD 引用标注 |
| 用户说"这个字段不该在这里"，把整个数据字段章节重写了 | 用户只想删除一个字段 | 只删除指定字段 |

**原则**：修改范围不超过用户指出的问题。不确定时，问用户。

---

## 9. 术语不一致

**反模式**：使用了主文档名词定义表之外的叫法。

常见错误与正确映射：

| 文档中写了 | 应该写 |
|------------|--------|
| 后端 | 服务端 |
| 配置端 | 服务端 |
| 后台 | 管理台 |
| 权益 / 进店权益 | 增值权益 |
| 保养周期 | 保养周期窗口 |
| 价值标签 | 服务价值标签 |
| 时间节点 | 服务过程节点 |

**预防方法**：写完后全文搜索这些错误用法。

---

## 10. 数据字段表与接口响应不一致

**反模式**：数据链路表中提到的 API 字段，在接口契约的响应 JSON 中找不到（或反过来）。

| 错误示例 | 正确做法 |
|----------|----------|
| 数据链路表有 `svgColor`，但接口响应 JSON 中没有 | 两处必须对齐：数据链路表引用的字段，接口响应中必须存在 |
| 接口响应有 `createdAt`，但没有任何 UI 元素使用它 | 如果没有 UI 用到，就不该出现在本区块的接口响应中 |

**验证方法**：把数据链路表的"API 字段"列和接口响应的字段做集合对比，应该一致。

---

## 11. 格式不统一

**反模式**：同一上下文中，同类事物使用了不同格式。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| 时序图中 5 个接口写 `GET /api/xxx`，1 个写"获取车辆列表" | 格式不统一，读者困惑这个接口是否特殊 | 全部统一为 `GET /api/xxx（入参: param）` |
| 附录中有的接口写 `GET/PUT`，有的只写中文名 | 同一张表的同一列格式不一致 | 统一为 `METHOD /path` 格式 |

**判断标准**：同一张表/同一个图中的同类信息，格式是否完全一致？

---

## 12. PRD 自相矛盾

**反模式**：文档前面确认的结论，后面被推翻或变更，且未说明原因。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| 前面说"接口路径不变，只是数据源变了"，后面声明了一个全新路径 `/dfh/vehicle/list` | 前后矛盾，开发者不知道该信哪个 | 保持一致：接口路径不变就用原路径 |
| 前面说"C 端直调迪粉汇"，后面改为"C 端调服务端" | 架构方向矛盾 | 如需修改，先显式声明"修正上文"并说明原因 |

**预防方法**：每次修改前，全文搜索相关关键词，确认不会与已有描述冲突。

---

## 13. 从代码反推 PRD

**反模式**：去代码中查找接口路径/字段名，然后照搬到 PRD 中。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| 在代码中找到迪粉汇调用路径 `/dfh/xxx`，写入 PRD | PRD 是权威定义，不是代码文档。代码可能实现错误 | PRD 定义接口路径，开发者照 PRD 写代码 |
| 从 Controller 中抄响应字段到 PRD | 如果 Controller 实现有偏差，PRD 也跟着错 | PRD 先定义目标态字段，再用 `> 现状差异` 标注实际代码的偏差 |

**核心原则**：PRD 定义"应该是什么"，代码实现"实际是什么"。方向是 PRD → 代码，不是代码 → PRD。

---

## 14. 接口请求参数无数据源

**反模式**：接口契约定义了请求参数（如 `vin`、`phone`），但没有说明这些参数的值从哪里来。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| `GET /api/basic-info?phone={phone}&vin={vin}`，只写了参数名和类型 | 开发者不知道 `vin` 从哪里获取——是用户手动输入的？还是前序接口返回的？ | 在接口契约或数据流说明中明确标注：`vin` 来自 PRD 1 车辆选择区 `GET /api/vehicles` 返回，用户选车后存入全局状态 |
| 子 PRD 的接口用到了 `orderId`，但没说来源 | 参数没有源头，链路断裂，AI 无法自动串联上下游 | 标注"`orderId` 来自订单列表接口 `GET /api/order-list` 响应中的 `orders[].id`" |

**核心原则**：接口的数据链路不只是"响应→UI"，还包括"数据源→请求参数"。请求参数的来源必须可追溯，尤其是跨区块/跨 PRD 的依赖。没有源头的参数等于断裂的链路——AI 编程时无法自动获取正确的值。

---

## 15. 响应示例未标注场景

**反模式**：接口契约中的 JSON 响应块只写"**响应**："，没有标明这是一个示例，也没有说明示例对应的场景条件。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| 直接写"**响应**："然后跟 JSON | 开发者分不清 JSON 中的值是固定的还是动态的，`"maintenanceCount": 6` 看起来像硬编码 | 写"**响应示例**（日常模式 NOT_DUE，有 3 枚徽章，有增值权益）："，明确这是特定场景的样本 |
| JSON 示例中没有字段说明表配套 | 只有示例没有契约，开发者不知道字段类型、取值范围、可选/必填 | JSON 示例之后必须紧跟"**响应字段说明**"表，表中定义字段名/类型/说明 |

**核心原则**：JSON 示例是帮助理解结构的辅助材料，响应字段说明表才是正式契约。两者缺一不可，且示例必须标注场景条件，避免具体值被误读为固定值。

---

## 16. 配置表初始值写成确定性规格

**反模式**：PRD 表格中展示了来自配置表的值（颜色、文案、图标等），但没有标注这些值是可配置的初始值，读起来像硬编码的固定规格。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| 直接写 `颜色: 绿 green`、`文案: 爱车状态满分` 的表格，没有说明来源 | AI 读到后会写 `if (status === 'NOT_DUE') color = 'green'` 的硬编码逻辑，而不是从配置表读取 | 表前说明"以下为 `xxx_config` 表的初始值，运营可通过管理台修改"；表头用字段名（如 `color`、`defaultText`）；表后注明"不是硬编码，服务端查表返回" |
| 徽章规则表里写"颜色: 紫色 #722ED1"，没说来自 `badge_strategy.color` | AI 会把色值硬编码到前端组件里 | 写明"颜色来自 `badge_strategy.color` 配置，以下为初始值"，并指向管理台配置章节 |

**核心原则**：PRD 中出现的具体值，必须让 AI 能分辨两类：**固定规格**（如状态枚举 NOT_DUE/DUE/OVERDUE，这些是代码逻辑）vs **可配置初始值**（如颜色、文案、图标，这些来自配置表）。对后者，必须标注三要素：①值来自哪张配置表 ②运营可通过哪个管理台页面修改 ③服务端查表返回、前端直接渲染。

## 17. 数据源指向缓存而非源头

**反模式**：数据链路表或服务端处理逻辑中，把缓存表（如 `vehicle_cache`）当作数据源，而不是追溯到真正产生数据的原始表。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| `maintenanceCount` 来源写 `vehicle_cache.maintenance_count` | `vehicle_cache` 是定时同步的缓存产出物，不是数据源头。AI 看到后会直接读缓存，不知道这个数怎么算出来的 | 来源写 `bss_work_orders` WHERE `order_status = "已完成"` AND `repair_type ∈ {"免费常规保养", "常规保养"}`，`.size()` 即保养次数 |
| 徽章数据来源写 `vehicle_cache.badges` | badges 是 BadgeCalculationService 的计算产出，缓存的是结果 JSON | 来源写 `bss_work_orders`（保养工单）+ `marketing_insurance_policy`（保险单），经 BadgeCalculationService 实时计算 |

**核心原则**：缓存表是性能优化手段，不是业务逻辑的数据源。PRD 描述的是"数据怎么来的"，不是"数据存在哪"。数据链路必须追溯到产生数据的原始表和计算逻辑，否则 AI 编写服务端代码时会跳过计算直接读缓存，丢失业务规则。

---

## 18. 聚合计算接口缺少计算链路

**反模式**：聚合计算型接口（如 `GET /api/basic-info`、`GET /api/orders`）只写了请求/响应契约，没有展示服务端如何从多张数据表聚合计算出响应字段。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| `GET /api/basic-info` 只写请求参数和 JSON 响应 | 开发者不知道 `dailyStatus`、`badges[]` 是怎么算出来的，从哪些表读数据 | 在接口契约中加 Mermaid flowchart LR 计算链路图：左列数据表 → 中间 Service → 右列配置表 |
| `GET /api/orders` 只列了响应字段 | 开发者不知道 4 种订单怎么聚合、标签怎么匹配 | 计算链路图展示 4 张 BSS 表 → OrderService → 3 张配置表 |

**判断标准**：如果接口的响应字段不是从单张表直透的（即需要跨表查询、计算、规则匹配），就必须有计算链路图。简单直透型接口（如 `GET /api/vehicles`）不需要。

---

## 19. 管理台配置类与数据管理类混合

**反模式**：将管理台的配置操作接口和数据查看/管理接口放在同一分类中，不区分"运营改配置"和"运营看数据"。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| 把 `GET/PUT /api/admin/badge-strategies`（配置）和 `GET /api/admin/vehicle-cache`（数据查看）混在"管理台接口"一组 | 两者的交互模式完全不同：配置类是表单编辑+保存，数据管理类是表格搜索+查看 | 配置类放 §3（管理台接口-配置类），数据管理类放 §4（管理台接口-数据管理类） |
| 配置类接口全写成 CRUD（增删改查） | 固定行数的配置表（如 5 态状态配置）不需要增删，只需要批量读取+批量保存 | 固定行配置用 GET（批量读）+ PUT（批量保存）；可变行配置才需要完整 CRUD |

**核心原则**：配置类接口的目的是"运营调整系统行为规则"，数据管理类接口的目的是"运营查看和管理业务数据"。两者分开写，开发者才能选择正确的页面交互模式。

---

## 20. API 总览文档与子 PRD 接口契约不一致

**反模式**：API 接口总览文档中的接口定义（字段名、类型、说明）与子 PRD 中对同一接口的描述存在冲突。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| API 总览说 `badges[]` 有 5 个字段，子 PRD 数据链路表列了 7 个字段 | 开发者不知道以哪个为准 | API 总览文档是技术契约权威源，字段定义以它为准。子 PRD 写业务上下文（哪个字段用于什么 UI），字段名和类型与 API 文档一致 |
| API 总览说接口路径是 `/api/order-list`，子 PRD 写的是 `/api/orders` | 路径不一致，调用会 404 | 统一路径。写完 API 总览后，全文搜索子 PRD 中的接口引用，逐个核对 |

**预防方法**：API 总览文档写完后，与每个子 PRD 的接口契约章节做交叉校验。§5 接口↔数据表映射也应与数据库 Schema 文档的"使用接口"列互相校验。

---

## 21. 废弃接口缺少替代信息

**反模式**：在接口总览中标记了"废弃"状态的接口，但没有说明废弃原因和替代方案。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| `GET /api/vehicle/list` 状态标"废弃"，无其他说明 | 开发者不知道为什么废弃，该用什么替代 | 废弃接口必须写明：①废弃原因 ②替代接口（如"由 `GET /api/vehicles` 替代"）③迁移注意点（如有） |
| 把废弃接口从文档中直接删除 | 历史接口消失，新成员不知道有过这个接口，可能重新设计出类似路径 | 废弃接口保留在文档中，集中放在"废弃接口"小节，注明废弃原因和替代方案 |

**核心原则**：废弃接口是系统演进的历史记录。保留它们可以避免路径冲突、帮助理解设计变迁。但必须明确标注状态，不能和活跃接口混在一起。

---

## 22. 枚举型字段未明示可枚举值

**反模式**：数据库 Schema 或 PRD 中定义了枚举型字段，但只给了模糊描述（如"订单状态"、"维修类型"），没有穷举列出所有合法枚举值。

| 错误示例 | 为什么错 | 正确做法 |
|----------|----------|----------|
| `order_status` 说明写"订单状态" | 读者不知道有哪些合法值，可能杜撰"维修中""保养中"等不存在的状态 | 说明写"订单状态（进行中 / 已完成 / 已取消）"，穷举所有合法值 |
| `repair_type` 说明写"维修类型" | AI 或开发者可能随意填写不存在的类型 | 说明写"维修类型（免费常规保养 / 常规保养 / 一般维修 / 延保维修 / 事故维修）" |
| PRD 验收标准写"当 order_status ∈ {维修中, 保养中}" | PRD 引用了不存在的枚举值，导致测试用例和 SQL 全部用错值 | 先查 Schema 确认合法枚举值，再引用正确的值 |

**真实案例**：`bss_work_orders.order_status` 在实际系统中只有"进行中""已完成"等值，但 PRD 验收标准中写了"维修中""保养中"（不存在的值）。导致测试 SQL 写入错误数据、测试用例预期错误。实际的维修/保养区分靠 `repair_type` 字段，与 `order_status` 无关。

**核心原则**：枚举型字段是业务规则的边界定义。未穷举枚举值 = 给下游留了杜撰空间。Schema 中每个枚举型字段的"说明"列必须用括号列出全部合法值，PRD 引用这些字段时必须与 Schema 定义一致。
