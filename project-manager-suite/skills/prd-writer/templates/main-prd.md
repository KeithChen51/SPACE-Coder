## 五、PRD 文档结构设计

### 5.1 每个子区域的统一写法

```
§N. [区域名称]
  ├── 用户体验    — 用户看到什么、怎么交互
  ├── 数据链路    — 字段级追溯表：UI元素 → API字段 → 计算规则 → 数据源 + 配置源
  ├── 配置能力    — 运营可配什么、哪个管理页、存哪张表
  ├── 接口契约    — 该区域涉及的 API 请求/响应片段
  └── 异常与兜底  — 缺数据怎么办、降级策略
```

### 5.2 目标态与现状差异的写法策略

PRD 主体描述**目标态**，现状偏差用 `> 现状差异` 引用块标注。

| 情况 | PRD 中怎么写 |
|------|------------|
| 已实现且正确 | 只写目标态，不加标注 |
| 已实现但有偏差 | 目标态 + `> 现状差异` |
| 完全未实现 | 目标态 + `> 现状差异：当前无此实现` |

**固定格式**：

```markdown
> **现状差异**：[当前实现是什么，关键代码文件路径]。
> 需要：[简述改动方向]。
```

## 六、子 PRD 内容大纲

<!--
  每份子 PRD 用表格列出章节 + 内容要点。
  写完子 PRD 后必须回来同步更新此处（保持一致性）。

  ─── 拆分原则 ────────────────────────────────────────────────────

  列大纲前，先评估每个区块是否需要拆分为多份子 PRD。
  小模块解耦可以减少单份文档的上下文量，让 AI 实现某个功能时
  只需读一份文档就获得完整信息，而不是在一份大文档中筛选相关段落。

  拆分信号（满足 2 项以上即应拆分）：
  - 横切规则引擎：某子系统（如标签、徽章）跨多个 UI 区域生效，有独立的计算规则
  - 独立管理台配置：该功能有自己的管理台配置页
  - 独立可测：可以单独验收，不依赖其他功能子区域的实现
  - 章节数多：大纲预估超过 10 个章节

  拆分后的约定：
  - 命名：prd-区块{N}-{区块名}-{子模块名}.md（如 prd-区块2-保养卡片区-徽章.md）

  - 拆出的 PRD 自包含：读这一份就能了解前端渲染 + 规则 + 配置 + 接口 + 验收
  - 共享接口的字段定义保留在主体 PRD 的接口契约中，拆出的 PRD 引用它
  - 在本章为拆出的 PRD 新增独立大纲条目（如 PRD 2-B）

| 验证方法 | 操作 |
|----------|------|
