# Open Core Strategy

## 1. 目的

本文件定义 `project-manager-suite` 的开源策略。

目标不是讨论“要不要开源”，而是明确：

1. 哪些内容可以公开
2. 哪些内容必须保留
3. 如何让套件对外开放但不暴露核心竞争力
4. 如何让公开版与内部增强版共存

---

## 2. 基本判断

这套 AI coding 模型可以开源，但不应把核心逻辑一并公开。

同时必须承认一个前提：

**公开版不能只是工具空壳。**

因为目标用户是业务团队，他们通常不具备从需求分析到项目上线的完整研发认知。如果公开版只开放结构、不开放基础闭环能力，那么他们依然无法完成全流程 AI coding。

因此，本套件的开源策略不是：

- 开一个骨架
- 把关键能力几乎全部留私有

而应该是：

- 公开一个可独立工作的基础产品
- 私有保留更高质量的智能判断层

应采用的总体策略是：

**开源外壳层 + 私有策略层 + 可插拔执行层**

这个策略的目标是同时满足：

- 对外：别人可以真正使用
- 对内：核心工作成果不被轻易复制

一句话原则：

**开源能力边界，私有能力深度。**

更准确地说，应升级为：

**公开完整闭环能力，私有增强判断能力。**

---

## 3. 三层模型

### 3.1 开源基础能力层

作用：

- 解决“业务团队能不能独立跑完整流程”

这一层建议公开：

- 套件目录结构
- 套件 README
- 主入口 `SKILL.md` 的基础版
- 基础子 skill 的基础版
- 通用模板的基础版
- 通用接口约定
- 稳定能力名定义
- 项目全局文件模型
- 主入口运行模型
- 最小可用工作流
- 基础访谈机制
- 基础阶段判断
- 基础需求、方案、计划、执行、验收、日志能力

特点：

- 可运行
- 可学习
- 可扩展
- 必须保证业务团队可以从想法推进到完整流程
- 但不追求内部版的最高质量上限

不应在这一层公开：

- 完整 heuristics
- 高质量内部模板库
- 经验化决策逻辑
- 高价值反模式库

### 3.2 私有策略层

作用：

- 解决“为什么内部版更强”

这一层建议保留私有：

- 访谈树与追问策略
- 阶段判断 heuristics
- 任务拆分策略
- 路由优先级
- 提问压缩策略
- 反模式库
- 高价值提示词与经验规则
- 高质量模板与案例映射

特点：

- 这是核心工作成果
- 这是内部长期竞争力
- 不应直接写进公开 `SKILL.md`、公开 `assets/` 或公开 docs

### 3.3 可插拔执行层

作用：

- 让公开版与内部增强版可以共存

这一层的实现方式是：

- 公开默认子 skill
- 私有增强子 skill
- 通过稳定能力名覆盖默认实现

例如：

- 开源：`requirements-starter`
- 私有：`requirements-starter-pro`
- 开源：`delivery-planner`
- 私有：`delivery-planner-pro`

这样做的好处是：

- 开源版可以独立运行
- 内部版可以明显更强
- 架构上不需要推翻重来

---

## 4. 推荐公开内容

推荐公开内容不应只覆盖“结构”，还必须覆盖“基础闭环能力”。

建议对外公开的内容包括：

### 4.1 结构类

- 套件目录结构
- 分发方式
- 命名规范
- 稳定能力名

### 4.2 模型类

- 项目全局文件模型
- 主入口运行模型
- 基础子 skill 的职责边界

### 4.3 基础闭环能力类

- 主入口基础版
- 基础子 skill 基础版
- 基础访谈机制
- 基础阶段判断
- 基础需求摘要模板
- 基础方案模板（页面原型与 PRD）
- 基础任务拆解模板
- 基础执行规则
- 基础测试用例模板
- 基础验收模板
- 基础日志模板
- 最小示例

### 4.4 文档类

- README
- package conventions
- open core 策略本身

这些内容的共同特点是：

- 能保证业务团队完整走通基础流程
- 不直接暴露最核心的判断力
- 提供的是基础产品能力，而不是最强智能层

---

## 5. 推荐保留内容

建议保留为私有内容的包括：

### 5.1 决策逻辑

- 访谈树
- 阶段判断逻辑
- 路由优先级
- 任务拆分 heuristics

### 5.2 实战经验

- 反模式库
- 失败案例归纳
- 高价值纠偏规则
- 复杂边界条件处理

### 5.3 高质量资产

- 高质量模板
- 优化后的提示模板
- 私有案例映射
- 内部质量门禁

### 5.4 增强能力

- `*-pro` 版本子 skill
- 私有增强版路由规则
- 私有协作识别规则

这些内容的共同特点是：

- 直接决定效果上限
- 是项目实战反复迭代的结果
- 是最不应被随手公开的部分

这里保留的不是“基础能力存在性”，而是：

**能力优化深度。**

---

## 6. 双版本策略

推荐将产品形态拆成两类。

### 6.1 Community / Open

定位：

- 面向外部使用者
- 提供基础闭环能力

建议包含：

- `project-manager-suite` 基础骨架
- 主入口基础版
- 基础子 skill
- 基础模型文档
- 通用模板
- 基础运行规则
- 基础全流程能力

能力目标：

- 能运行
- 能学习
- 能扩展
- 业务团队即使没有完整研发知识，也能跑完基础流程

### 6.2 Pro / Internal

定位：

- 面向内部团队
- 提供高质量增强能力

建议包含：

- 私有规则库
- 私有决策树
- 私有提示模板
- 私有案例映射
- 私有 routing 策略
- 私有质量门禁
- 私有增强版子 skill

能力目标：

- 输出更稳定
- 提问更精准
- 路由更聪明
- 更贴近真实业务落地

结论：

- 开源版解决“完整基础闭环可用”
- 内部增强版解决“高质量、稳定、可复制”

---

## 7. 与稳定能力名的关系

开源 / 私有分层不应依赖人工切换，而应依赖稳定能力名与默认实现覆盖机制。

推荐机制：

1. 开源套件定义稳定能力名
2. 默认映射到公开版基础子 skill
3. 内部环境中再映射到私有增强版子 skill

例如：

- `requirements` -> `skills/requirements-starter/`
- 内部环境可覆盖为 `requirements-starter-pro`

这样可以做到：

- 对外公开的是接口和默认能力
- 对内保留的是更强实现
- 开源 / 私有分层依赖“稳定能力名 + 默认实现可替换”，而不是重新发明一套内部专用能力名

---

## 8. 四类内容清单

为了兼顾“业务团队能用”与“核心逻辑保留”，建议将内容划分为 4 类。

### 8.1 必须公开的基础闭环能力

这部分必须公开，否则业务团队拿到套件后依然无法独立完成全流程 AI coding。

建议包括：

- 主入口 `ai-project-manager`
- 项目画像能力
- 基础访谈机制
- 基础阶段判断
- 基础需求澄清能力
- 基础方案整理能力
- 基础任务拆解能力
- 基础开发执行规则
- 基础测试与验收规则
- 基础日志与状态回写能力
- 默认模板与默认工作流

### 8.2 可公开的低配模板与说明

这部分可以公开，但建议只给基础版。

建议包括：

- 项目画像模板基础版
- 需求摘要模板基础版
- 页面原型与 PRD 模板基础版
- 任务拆解模板基础版
- 测试用例模板基础版
- 验收清单模板基础版
- 默认日志模板基础版
- 部分参考示例

### 8.3 必须保留的私有增强逻辑

这部分是核心竞争力，不建议公开。

建议包括：

- 动态追问策略
- 精细阶段判断
- 高级任务拆分逻辑
- 高级协作角色识别
- 高级质量门禁
- 高级 routing 策略
- 复杂场景纠偏规则
- 高价值反模式库

### 8.4 必须保留的私有增强模板与案例

这部分不是基础存在性，而是质量差异来源。

建议包括：

- 高质量模板库
- 私有提示模板
- 私有案例映射
- 增强版子 skill

---

## 9. 禁止事项

以下做法应避免：

1. 将完整 heuristics 写进公开 `SKILL.md`
2. 将高质量私有模板直接放入公开 `assets/`
3. 将实战判断规则完整写进公开 docs
4. 用配置文件明文暴露全部核心决策逻辑
5. 将私有增强版与公开版混放在同一公开目录中

---

## 10. 推荐实施顺序

为了避免过早泄露核心逻辑，建议按以下顺序推进：

1. 先完成公开层的结构定义
2. 再完成公开层的最小可用骨架
3. 再盘点私有层内容清单
4. 最后用稳定能力名接入私有增强版

不建议：

- 在公开版尚未收敛时就把私有 heuristics 写进文档
- 在套件结构未稳定时就设计复杂的授权或加密机制

---

## 11. 当前建议

对当前阶段最务实的建议是：

1. 继续完善 `project-manager-suite` 的公开层
2. 暂时不把私有层内容写入公开仓结构
3. 先在团队内部盘点“哪些内容属于核心逻辑”
4. 等公开骨架稳定后，再设计内部增强版接入方式
5. 始终确保公开版是一套完整基础产品，而不是只会导航的空壳

---

## 12. 一句话结论

`project-manager-suite` 的开源策略不应是“全开”或“全闭”，而应是：

**公开完整基础闭环能力；保留增强判断逻辑、经验规则和高质量资产。**
