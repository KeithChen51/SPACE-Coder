# 项目目录脚手架设计（讨论中）

## 背景

本文件讨论的不是 `project-manager-suite` 套件自身目录，而是：

**项目经理模型在与用户完成初始访谈后，应具备规划宿主项目默认文件目录结构的能力。**

也就是说，这里定义的是：

- AI 在用户项目中应识别和规划什么目录和文件
- 哪些文件应作为宿主项目的长期权威入口
- 哪些内容来自 `ai-project-manager` 内置模板层

而不是：

- `project-manager-suite` 套件自身的源码目录结构
- 套件内部 `docs/`、`skills/` 的分层方式
- 主入口内部资源文件如何组织

当前边界应固定为：

- 套件内部模板源位于 `skills/ai-project-manager/assets/global-files/`
- 本文描述的是这些模板在未来正式应用到宿主项目时，应落在什么位置、如何与宿主项目目录协同
- 当前阶段先把脚手架构建规则沉淀进模型，由主入口在命中条件时按规则补齐宿主项目骨架

## 选定方案：方案 A（参考文档式）

在 `ai-project-manager/references/` 增加 `project-scaffold.md`，由主入口读取后完成宿主项目脚手架判断与构建。

**选 A 的理由**：
- 符合"先识别宿主项目已有文件，再补缺失"的设计哲学
- AI 擅长灵活判断，脚本反而限制它
- 对已有项目可做角色映射而非强制覆盖
- 维护成本低
- 便于先在模型内完成能力建设，而不直接影响当前宿主项目

## 执行计划

### Step 1：创建 `references/project-scaffold.md`

内容应包含：
1. **触发时机** — 初始访谈完成、项目画像基本成型后
2. **宿主项目标准目录结构** — 定义用户项目应有的目录和文件清单（待讨论确认 ⬇️）
3. **检查与补齐规则** — 先扫描宿主项目已有结构 → 做角色映射 → 只补缺失部分
4. **初始文件来源** — 标注哪些未来从 `ai-project-manager/assets/global-files/` 复制、哪些新建空目录
5. **构建输出方式** — 输出已补齐的目录结构、缺口判断和当前暂不创建的目录
6. **执行边界** — 一旦主入口触发到该能力，就按条件补齐宿主项目骨架；只对未到触发阶段的目录延后创建

### Step 2：更新 `ai-project-manager/SKILL.md`

在"资源入口"章节增加一行：
```
- 初始访谈完成后需要补齐宿主项目目录和文件骨架时，读取 `references/project-scaffold.md`
```

## `execution-plan` 的定义与多计划处理

这里的 `execution-plan` 不应再理解为：

- 宿主项目里永远只有一个固定文件名的计划文件
- 所有阶段都持续写同一份 `execution-plan.md`

更合适的定义是：

**`execution-plan` 是“当前激活计划角色”，而不是“永远唯一的计划文件名”。**

这意味着：

- 宿主项目中允许存在多份计划文件
- 不同阶段可以有不同的主计划文件
- 任一时刻只应有一个“当前激活计划入口”
- 主入口和各子 skill 默认只围绕这一个入口读取和回写

### 设计结论

当前采用以下口径：

1. 宿主项目允许多份计划文件并存
2. 多份计划默认按阶段拆分，而不是强制把所有内容写在一份文件里
3. 任一时刻只认一份“当前主计划”
4. 当前主计划入口写在 `project-profile.md`，不写在 `project-rules.md`
5. `project-rules.md` 只负责声明计划文件的组织规则，不负责记录当前激活的是哪一份
6. 阶段切换后，旧计划文件默认保留为历史参考，不再作为默认写入目标

### 文件分工

- `project-rules.md`
  - 定义计划文件的目录、命名约定和切换原则
  - 例如：计划文件默认放在 `docs/plans/`，允许按阶段拆分，旧计划默认保留

- `project-profile.md`
  - 记录当前激活计划入口
  - 例如：`计划入口文件：docs/plans/stage-2-delivery-plan.md`

- `docs/plans/*.md`
  - 承载具体某一阶段或某一轮的任务、下一步、完成标准和依赖
  - 其中只有当前激活的那一份承担 `execution-plan` 角色

### 运行时处理原则

当主入口启动时：

1. 先读取 `project-profile.md` 中的 `计划入口文件`
2. 若该入口存在，则默认认定其为当前执行计划文件
3. 若宿主项目中存在多份计划文件，但画像未指明当前入口，则主入口先做角色映射或最小澄清，再确定当前主计划
4. 未确定当前主计划入口前，不应在多份计划之间来回混写

当项目阶段切换时：

1. 可以新建一份新的阶段计划文件
2. 由主入口更新 `project-profile.md` 中的 `计划入口文件`
3. 旧计划文件保留，但默认冻结为历史参考

这一设计的目标是：

- 允许项目在不同阶段使用不同计划形态
- 保持主入口和子 skill 的默认读取入口稳定
- 避免把规则层变成频繁更新的“当前状态文件”
- 避免多份计划并存时出现读写目标不稳定

## 宿主项目目录结构分层方案（草案 v4，讨论中）

参考来源：Claude Code 项目结构图 + Prime-Trace 现有实践 + 全局文件模型

当前不再把宿主项目目录理解为“首次访谈结束后一次性建满的完整结构”，而拆成 3 层：

1. 启动必建骨架
2. 阶段触发目录
3. 实现触发目录

这样做的目的不是减少目录，而是让宿主项目结构的生长顺序与主入口的运行顺序保持一致：

- 先建立最小可持续推进骨架
- 再按阶段补文档目录
- 最后在进入真实开发后补实现目录

### 第一层：启动必建骨架

这层的标准是：

**没有这些目录和文件，主入口就无法稳定恢复上下文、识别当前计划入口、继续推进下一轮。**

默认应规划为：

```text
<项目根目录>/
├── project-profile.md              # 项目画像（AI 第一入口；记录当前主计划入口）
├── project-rules.md                # 项目规则（长期有效的运行规则）
├── docs/                           # 渐进式披露
│   ├── plans/
│   │   └── execution-plan.md       # 初始主计划载体；后续允许切换到其他计划文件
│   └── rules/                      # 项目过程中沉淀的专项规则（由根目录 project-rules.md 引用）
├── logs/                           # 状态回写与日志目录
└── .agent/                         # 本地 AI 配置与本地 skill 挂载根目录
    └── skills/
```

补充说明：

- `project-profile.md`
  - 必须存在，因为它不仅承接项目画像，也承接 `计划入口文件`
- `project-rules.md`
  - 必须存在，因为它承接长期规则、计划组织规则和专项规则入口
- `docs/plans/execution-plan.md`
  - 作为最小主计划载体，建议在正式执行初始化时直接创建
  - 后续项目可切换到其它计划文件，但初始不建议只建空目录不建文件
- `docs/rules/`
  - 作为专项规则沉淀位，建议从一开始保留
- `logs/`
  - 正式执行初始化时先建目录即可
  - 不要求首次初始化时就同时建 `weekly/` 或独立状态总结文件
- `.agent/`
  - 作为宿主项目本地 AI 配置与后续能力挂载根目录，初始化时默认创建
- `.agent/skills/`
  - 作为宿主项目本地 skill、增强实现和本地覆写的统一入口，随 `.agent/` 一并创建

### 第二层：阶段触发目录

这层的标准是：

**只有进入对应阶段后，才有必要补齐这些文档目录。**

默认按阶段补建为：

```text
docs/
├── prd/                            # 进入需求整理阶段后创建
├── decisions/                      # 进入方案设计或关键决策阶段后创建
├── test-case/                      # 进入测试设计或验收设计阶段后创建
└── architecture.md                 # 确有架构设计沉淀需要时创建
```

触发原则：

- `docs/prd/`
  - 当需求需要结构化沉淀、拆分或持续迭代时创建
- `docs/decisions/`
  - 当出现方案选型、架构决策、关键口径决策需要长期留痕时创建
- `docs/test-case/`
  - 当进入测试设计、验收设计、回归设计时创建
- `docs/architecture.md`
  - 仅在项目确实需要架构总览文件时创建，不作为启动默认必建项

### 第三层：实现触发目录

这层的标准是：

**只有项目进入真实开发或工程化协作阶段后，才需要补齐。**

默认按实现需要补建为：

```text
src/                                # 源代码根目录
tools/                              # 开发辅助目录
```

其中：

- `src/`
  - 确认进入真实开发阶段后创建
  - 内部结构当前按已确认方案处理：

```text
src/
├── <项目名>-Toc/                   # C端（移动端）— 前端 + 后端
│   ├── frontend/
│   └── backend/
├── <项目名>-Config/                # B端（管理后台）— 前端 + 后端
│   ├── frontend/
│   └── backend/
└── shared/                         # 可选，仅放两端确有共享需求的工具/模型
```

- `tools/`
  - 出现脚本、自动化、迁移或辅助工具需求时再创建

### 完整形态参考

当项目进入真实推进且正式应用该能力后，宿主项目最终可能长成如下形态：

```text
<项目根目录>/
├── project-profile.md
├── project-rules.md
│
├── docs/
│   ├── prd/
│   ├── plans/
│   ├── rules/
│   ├── decisions/
│   ├── test-case/
│   └── architecture.md
│
├── logs/
│   ├── YYYYMMDD_*.md
│   └── weekly/
│
├── tools/
│   └── scripts/
│
├── src/
│   ├── <项目名>-Toc/
│   │   ├── frontend/
│   │   └── backend/
│   ├── <项目名>-Config/
│   │   ├── frontend/
│   │   └── backend/
│   └── shared/
│
└── .agent/
```
