## 2. 产品定位与目标

### 2.1 产品目标

`project-manager-suite` 不是单次需求整理工具，也不是文档生成器，而是一个面向业务团队的“项目经理产品”能力包。

它的产品目标是：

- 可开源
- 可分层
- 可持续商业化
- 可复用
- 可移植

这意味着：

- 需要有真实可用的公开版
- 需要有保留核心竞争力的增强版
- 开源策略不能破坏后续持续商业化空间
- 需要能在不同 AI IDE 中复用，而不绑定单一工具
- 关键能力应沉淀到可迁移的文件体系和协议中，而不是依赖工具私有机制

### 2.2 业务目标

这套模型的业务目标是：

**帮助业务方把想法整理清楚，并由懂产研一体化体系的“项目经理模型”推动项目往前走。**

因此它不只是前期访谈助手，而是要承担：

- 将模糊业务想法转成可执行项目推进路径
- 让项目在统一骨架上持续往前推进
- 让 AI 输出不只停留在对话，而能沉淀为项目资产

### 2.3 目标用户

第一批典型用户是：

- 不懂从需求分析到需求上线完整流程的业务方
- 会使用 AI IDE，但缺少完整产研流程意识和交付件意识的团队

这些用户通常不是完全不会动手，而是：

- 会开始做
- 但不知道应该先产出什么
- 不知道不同阶段该用什么交付件约束项目
- 不知道怎么让 AI 持续稳定地产出一致结果

### 2.4 核心痛点

这类用户最核心的卡点不是“不会调用 AI”，而是：

- 没有体系化的开发流程
- 没有稳定的项目交付件
- 难以保障项目的可持续性
- 难以保障方案和实现的可维护性
- 难以保障 AI 输出的一致性

因此，`project-manager-suite` 的价值重点不在“替用户多写几份文档”，而在：

- 给用户一套能让项目持续推进的默认骨架
- 给 AI 提供稳定上下文载体
- 给项目提供可持续回写和滚动推进机制

### 2.5 基础版最低能力下限

基于上述目标和用户画像，基础版形成如下边界：

- 不能退化为单次需求摘要工具
- 不能只是模板包
- 必须提供最小可用闭环，能够支撑项目从启动走到执行与回写

当前基础版最低能力下限为：

- 项目启动
- 项目画像
- 需求摘要
- 基础方案
- 基础任务拆解
- 基础执行规则
- 基础验收
- 基础日志回写

这组能力的重要性在于：

- 缺少项目画像，后续阶段没有统一上下文
- 缺少执行规则，AI 输出容易快速漂移
- 缺少验收，任务无法形成明确完成标准
- 缺少日志回写，项目无法持续沉淀和滚动推进

结论上，基础版应公开的是：

**轻量闭环骨架**

不是：

- 若干静态模板
- 若干独立 skill
- 若干一次性文档产出

### 2.6 增强版边界

增强版的核心价值不应来自“是否有闭环”，而应来自“闭环质量有多高”。

当前倾向增强版重点保留：

- 动态追问策略
- 精细阶段判断
- 高级任务拆分
- 高级协作识别
- routing 优先级
- 反模式库
- 高质量模板
- 行业案例映射
- 增强版子 skill

分层原则不是“基础版有没有闭环”，而是：

- 基础版公开骨架能力
- 增强版保留高质量判断能力、经验规则、模板质量和案例密度

### 2.7 开源版 1.0 定义

当前将本次阶段版本定义为：

**`project-manager-suite` 开源版 1.0**

这个版本的定位不是“能力已经完整”，而是：

- 已经具备首个可对外说明的公开版产品形态
- 已经形成统一骨架、统一入口和统一设计口径
- 已经能够证明这套模型不是文档生成器，而是轻量项目推进闭环

开源版 1.0 的范围聚焦于：

- 一个稳定的总入口：`ai-project-manager`
- 一套统一的 4 类全局文件骨架
- 一组最小基础子能力
- 一套最小可用的运行协议与回写闭环
- 一套清楚的公开版 / 增强版边界

开源版 1.0 不以“覆盖所有场景”作为目标，而以“证明产品骨架成立”作为目标。

### 2.8 开源版 1.0 目标

开源版 1.0 的阶段目标定义为：

**让业务团队能够从模糊想法出发，在统一骨架上完成一次从启动、澄清、路由到执行回写的最小闭环。**

具体来说，这个版本至少应达到：

1. 用户能从模糊业务想法进入项目启动
2. 主入口能建立最小统一上下文，而不是只停留在对话里
3. 项目能沉淀统一全局文件骨架，而不是每轮重新拼接
4. 主入口能判断当前阶段、最小交付物和下一步能力
5. 套件能完成至少一次可执行、可回写、可承接的轻量闭环
6. 对外能清楚说明基础版解决什么、增强版保留什么

这个目标的验证标准不是“文档数量够不够多”，而是：

- 产品骨架是否稳定
- 闭环是否真实成立
- 用户是否能理解并持续使用
- 后续增强版是否还有清晰的升级空间

### 2.9 当前阶段性结论

当前已经形成的上位判断包括：

- `project-manager-suite` 是“项目经理产品”，不是“需求文档工具”
- 它服务的是“会用 AI IDE 但没有完整产研流程认知”的业务方
- 它要解决的是“项目持续推进和交付件体系缺失”问题，而不是只解决“首轮想法整理”
- 基础版必须能形成轻量闭环
- 增强版必须保留足以支撑持续商业化的判断能力与内容资产
- 它还必须具备可复用、可移植能力，能够适配不同 AI IDE

## 3. 设计总思路

### 3.1 为什么不是单次需求工具

判断结论：

- 这套产品不是为生成一次性需求文档而设计

原因：

- 用户真正缺的是项目推进能力，而不是单份文档产出
- 单次需求整理无法解决阶段判断、持续承接和回写问题
- 如果只产需求文档，项目仍然会在执行和验收阶段失去一致性

对结构的影响：

- 主入口必须承担项目级编排职责
- 全局文件体系必须成为产品骨架
- 每轮都要有回写，而不是只保留一次性回答

### 3.2 为什么不是先堆 skill

判断结论：

- 当前阶段优先做“主入口 + 全局文件体系 + 路由协议 + 回写闭环”，而不是先补很多 skill

原因：

- 如果没有统一骨架，skill 只会变成一组零散能力
- 用户仍然不知道当前项目处于什么阶段
- 没有统一承接位置，阶段性输出难以持续推进

对结构的影响：

- 主入口必须成为唯一总入口
- 子 skill 不平铺罗列，而由主入口按阶段路由
- 实施顺序优先是边界、骨架、协议、模板，再到内容能力

### 3.3 为什么主入口必须围绕全局文件体系

判断结论：

- `ai-project-manager` 的核心价值首先是项目路由器，而不是大一统执行器

原因：

- 没有全局文件体系，主入口只能依赖聊天临时记忆
- AI 每轮重新进入项目时无法稳定恢复上下文
- 阶段判断、下一步动作和回写目标都会漂移

对结构的影响：

- 主入口先识别全局文件
- 再读取最小必要上下文
- 再补当前最小缺口
- 最后才决定是否进入具体子 skill

### 3.4 为什么采用 4 类全局文件

判断结论：

- 当前采用 4 类全局文件，是产品目标下的最小稳定答案

4 类文件分别回答：

- 全局规则文件：项目怎么运行
- 项目画像文件：项目当前是什么
- 当前执行计划文件：现在做什么
- 项目状态回写文件：最近发生了什么

原因：

- 这 4 类刚好覆盖主入口最稳定的读、判、路由、回写需求
- 再往上拆会增加复杂度，不适合目标用户
- 再往下压缩会导致职责混写，不利于判断与回写

对结构的影响：

- 全局文件体系成为产品最小路由骨架
- 模型、字段合同、读写协议都围绕这 4 类文件组织
- 模板层和协议层都必须以这 4 类角色保持一致

### 3.5 为什么采用渐进式披露

判断结论：

- 面向业务团队时，系统必须一次只暴露当前轮必须知道的内容

原因：

- 目标用户不是专业项目经理或架构师
- 如果一上来展开全部 skill、阶段、模板、字段和规则，产品会退化成复杂方法论工具包
- 过度暴露会直接降低使用意愿和推进效率

对结构的影响：

- 主入口优先读取最小必要上下文
- 访谈只补当前最关键缺口
- 当前轮只输出最小交付物
- 只有必要时才进入子 skill

### 3.6 为什么采用“统一骨架，能力分层”

判断结论：

- 开源版和增强版不应分裂文件体系，而应共享统一骨架，只在能力深度上分层

原因：

- 如果按版本拆文件体系，后续最容易出现判断口径分叉、回写目标分叉和升级路径不兼容
- 统一骨架有利于维护稳定、用户升级无迁移、跨 IDE 复用

对结构的影响：

- 4 类全局文件必须共享同一套角色模型和最小公共协议
- 差异应收敛到 heuristics、模板质量、案例密度和增强子 skill
- 开源 / 私有边界应通过内容分层管理，而不是通过分裂骨架来实现

## 4. 产品结构与设计分工

### 4.1 套件范围

当前套件范围可分为 5 层：

1. 套件层
2. 主入口层
3. 项目全局文件层
4. 基础子能力层
5. 开源 / 私有分层层

### 4.2 各层职责

- 套件层
  - 定义整体产品形态、文档入口和标准交付单位

- 主入口层
  - 由 `ai-project-manager` 承担
  - 负责建立上下文、判断阶段、决定下一步能力、触发回写

- 项目全局文件层
  - 由 4 类全局文件构成统一项目骨架
  - 为主入口和子 skill 提供共同上下文

- 基础子能力层
  - 承担需求、方案、拆解、执行、验收、日志回写等阶段能力
  - 不再作为平铺技能集合，而作为岗位能力单元存在

- 开源 / 私有分层层
  - 通过骨架共享、能力分层的方式定义公开版与增强版边界

### 4.3 主入口职责边界

`ai-project-manager` 负责：

- 建立统一上下文
- 识别 `solo / 团队协作`
- 判断当前阶段
- 决定下一步能力
- 明确当前轮最小交付物
- 把结果写回正确的全局文件

`ai-project-manager` 不负责：

- 直接承载全部阶段性细节执行
- 替代全部子能力
- 将对话临时结论替代权威文件

### 4.4 全局文件体系与 role

全局文件体系当前按 4 类定义：

1. 全局规则文件
2. 项目画像文件
3. 当前执行计划文件
4. 项目状态回写文件

它们共同构成：

- 主入口的最小路由骨架
- 项目级持续上下文
- AI 可跨轮恢复的项目记忆容器

详细模型与协议不在本文件重复展开，统一索引到：

- `../../skills/ai-project-manager/references/global-files-model.md`
- `../../skills/ai-project-manager/references/global-files-minimum-shared-protocol.md`
- `../../skills/ai-project-manager/references/global-files-readwrite-protocol.md`
- `../../skills/ai-project-manager/references/entry-runtime-model.md`

### 4.5 开源 / 私有分层原则

当前原则为：

- 公开版必须提供最小可用闭环骨架
- 私有增强版保留高质量判断能力与内容资产

基础版应公开：

- 主入口基础能力
- 基础子 skill
- 全局文件模板
- 基础阶段路由
- 基础运行协议

增强版适合保留：

- 动态追问策略
- 精细阶段判断 heuristics
- 高级任务拆分策略
- 高级 routing 优先级
- 反模式库
- 高质量模板
- 行业案例映射

### 4.6 当前标准交付单位

对外分发时，标准交付单位是：

`project-manager-suite/`

不是：

- 单独复制 `ai-project-manager/`
- 单独复制某几个子 skill
- 单独复制说明文档

原因：

- 这套体系的价值来自统一约束下的产品化能力包
- 拆散交付后，总入口、边界和回写机制都会失去统一约束

## 5. 实施策略与当前推进顺序

### 5.1 当前实施目标

当前实施目标不是继续堆功能，而是先把 `project-manager-suite` 从讨论推进到可分发的产品化能力包。

聚焦点包括：

1. 明确产品边界
2. 明确主入口、全局文件、基础子能力和开源策略的关系
3. 为后续实现提供稳定顺序
4. 将高频讨论收敛为单一主文档
5. 将当前阶段收口为“开源版 1.0”的可对外说明形态

当前版本目标应统一理解为：

- 先把开源版 1.0 做成一个真实成立的轻量闭环产品
- 再在该骨架之上继续扩展增强版判断能力和更高质量资产

### 5.2 推荐实施顺序

当前推荐顺序为：

1. 固化产品定位与边界
2. 固化全局文件体系
3. 固化主入口运行协议
4. 固化字段标准与读写协议
5. 固化基础版最小闭环实物
6. 再逐步补齐基础子能力内容

一句话概括：

**先把这套模型做成一个有骨架、能路由、能持续沉淀的产品，再继续扩张能力深度。**

### 5.3 当前优先级

当前最重要的不是“多做几个 skill”，而是：

- 保持产品定位稳定
- 保持 design / references / templates / skills 的边界稳定
- 保持 4 类全局文件骨架稳定
- 继续验证基础版最小闭环是否真实成立

### 5.4 当前最需要评审的议题

团队当前最值得持续评审的问题包括：

1. 基础版最低能力下限是否仍然合理
2. 哪些内容必须保留为私有增强能力
3. 公开骨架与增强能力之间的边界是否清楚
4. 全局文件体系、模板层和 references 层是否仍存在重复定义
5. 基础版是否已经具备足以对外说明的闭环实物

### 5.5 何时需要回看本主文档

在讨论以下问题时，应优先回看本文件：

- 基础版最低能力下限
- 开源 / 私有边界
- 内容分层清单调整
- 是否新增某个子 skill 到公开版
- 主入口 `ai-project-manager` 的职责边界

### 5.6 哪些变化会触发本主文档更新

若后续以下任一前提变化，应优先更新本主文档：

- 目标用户发生变化
- 产品商业化路径发生变化
- 基础版定位从“轻量闭环”改为其他定位
- 增强版核心竞争力定义发生变化
- 套件的标准交付单位或顶层结构发生变化

## 6. 关键设计演进摘要

### 6.1 0-1 设计演进如何记录

0-1 设计演进只记录以下内容：

- 改变模型理解的关键讨论
- 改变产品结构的关键结论
- 改变优先级的关键转折
- 后续会反复引用的设计判断

它不记录：

- 日常实现细节
- 每天做了什么
- 所有零散讨论
- 当前迭代待办清单

### 6.2 已确认的关键演进主题

以下主题已经进入 0-1 阶段的关键设计范围：

1. `project-manager-suite` 到底是 skill 集合，还是产品化能力包
2. 主入口为什么必须围绕全局文件体系设计
3. 为什么不先堆 skill，而先做路由骨架
4. 为什么全局文件体系采用 4 类角色
5. 开源版 / 增强版为什么采用“统一骨架，能力分层”
6. 为什么模型应理解为“岗位能力 + 交付标准 + 项目骨架”
7. 为什么这套模型具备“项目级持久化记忆系统”雏形

### 6.3 核心演进节点摘要

#### 节点 1：从“skill 组合”收敛到“项目经理产品”

- 背景：
  - 最初容易把这套模型理解成需求、方案、计划、执行、测试相关 skill 的组合
- 候选方向：
  - skill 组合包
  - 需求整理或文档生成工具
  - 能推动项目持续往前走的项目经理产品
- 最终结论：
  - `project-manager-suite` 不是单次需求整理工具，也不是普通 skill 集合，而是项目经理产品
- 收敛原因：
  - 目标用户缺的是项目推进方法和可持续承接骨架，不是单一 skill
- 影响：
  - 主入口必须承担项目级编排职责
  - 基础版必须提供闭环，而不是工具空壳
- 剩余开放问题：
  - 对外包装和不同成熟度用户的入口分层如何继续优化

#### 节点 2：从“先做很多 skill”收敛到“先做主入口 + 全局文件骨架”

- 背景：
  - 早期自然倾向是先补需求、方案、计划、执行、验收等多个 skill
- 候选方向：
  - 先快速堆多个 skill
  - 先做主入口、全局文件体系和路由协议
- 最终结论：
  - 当前阶段优先做“主入口 + 全局文件体系 + 读写协议 + 路由条件”
- 收敛原因：
  - 没有统一骨架，skill 无法形成持续推进闭环
- 影响：
  - 先建立 4 类全局文件体系
  - 先建立主入口运行协议
  - 实施顺序转向原则、边界、协议、模板、职责收紧
- 剩余开放问题：
  - 何时进入各基础子 skill 的深度内容设计

#### 节点 3：从“可能按版本分文件体系”收敛到“统一骨架，能力分层”

- 背景：
  - 在讨论开源版与增强版时，自然会出现是否要分裂文件体系的问题
- 候选方向：
  - 开源版和增强版分别维护不同文件体系
  - 文件角色统一，只在能力深度上分层
- 最终结论：
  - 统一全局文件骨架，分层 skill 能力深度
- 收敛原因：
  - 分裂文件体系会导致主入口判断口径和回写目标分叉
- 影响：
  - 4 类全局文件必须定义最小公共协议
  - 增强版差异收敛到 heuristics、模板、案例和增强子 skill
- 剩余开放问题：
  - 哪些字段应进入最小公共协议，哪些增强内容允许灰度开放

#### 节点 4：从“多能力路由”收敛到“岗位能力 + 交付标准”

- 背景：
  - 如果只用“需求、方案、计划、测试”等词来组织 skill，容易退回到功能点集合
- 候选方向：
  - 将子 skill 理解为功能模块
  - 将子 skill 理解为岗位能力单元
- 最终结论：
  - 这套模型承载的是岗位能力，每个岗位能力背后都要有最小交付标准
- 收敛原因：
  - 没有最小输入、最小交付物和完成标准，就仍然只是多 agent 列表
- 影响：
  - 后续 skill 设计必须围绕岗位职责、交付物和回写关系展开
- 剩余开放问题：
  - 每个基础子 skill 的岗位边界和最小交付标准还需要继续细化

#### 节点 5：从“全局文件体系”收敛到“项目级持久化记忆系统雏形”

- 背景：
  - 随着主入口、全局文件和回写机制逐步收敛，开始出现“是否已在解决 AI 失忆问题”的判断
- 候选方向：
  - 它只是项目文件体系
  - 它已经具备项目级持久化记忆系统雏形
- 最终结论：
  - 当前模型已经具备项目级持久化记忆系统的核心骨架，但还未进入强约束完成态
- 收敛原因：
  - 关键上下文写入项目文件，主入口每次启动优先识别全局文件，结果要求写回统一骨架
- 影响：
  - 全局文件体系的价值被进一步提升
  - 后续需要继续研究快照、历史决策和回写稳定性
- 剩余开放问题：
  - 如何进一步标准化记忆分层和上下文恢复成本

#### 节点 6：从“结构可用”收敛到“规范层 / 模板层硬分层”

- 背景：
  - 在继续检查目录和文档时，暴露出重复模板、副本维护和边界不清问题
- 候选方向：
  - 允许重复模板副本继续存在
  - 固定成“规范层 / 模板层”双层结构，并清理重复副本
- 最终结论：
  - `skills/ai-project-manager/references/` 是规范层，`global-files/` 是模板层，模板只有一个权威来源
- 收敛原因：
  - 如果层次不固定，协议、模板和子 skill 资源都会继续漂移
- 影响：
  - 后续新增全局模板优先进入模板层
  - 后续新增运行约束优先进入 references 层
- 剩余开放问题：
  - 增强版模板未来是否也要在同一层继续分层管理
